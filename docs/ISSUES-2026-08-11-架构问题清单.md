## P0 — 静默故障与安全边界

### ISSUE-01:静默降级被滥用为"静默吞错",组件故障无感知 🆕

**位置**:
- `teage_liu/app.py` 共 **14 处** `except Exception`(行 50 / 71 / 113 / 178 / 355 / 377 / 387 / 402 / 411 / 420 / 439 / 471 / 480 / 501),其中 12 处是工厂函数内的 `try: ... except Exception: return None`
- `teage_liu/lifespan.py` 共 **34 处 `try:` / 29 处 `except Exception`**

**问题**:"降级优先"理念正确(可选组件缺失时主对话不中断),但实现粒度太粗——**无差别捕获 `Exception` 而非具体的依赖缺失异常**,且捕获后不记 error 日志。后果:
1. 真实代码 bug 被吞掉,服务"看起来正常"但功能静默消失;
2. 排查问题时无从下手(没有日志线索)。

**已发生的实例**:`app.py:484-501` `_create_health_checker` —— 注释自述 "HealthChecker.__init__ 的 orchestrator 必填参数会抛 TypeError,被 except 静默吞掉导致工厂永远返回 None",即健康检查组件曾长期静默失效。

**修复方向**:
1. 工厂函数改为捕获**具体异常**(如 `ImportError` / `ModuleNotFoundError` 表示依赖缺失 → 降级;其余异常 → 记 `logger.error` 并**让启动失败暴露**,或至少让 `/health` 反映组件缺失);
2. 建立组件注册表健康报告:容器内每个组件记录"创建成功/失败+原因",HealthChecker 聚合展示;
3. 全局禁止新增裸 `except Exception: return None`,可在代码 review 清单中固化。

**影响面**:所有依赖"工厂返回 None 表示降级"的调用方(路由、lifespan)。

### ISSUE-02:API 认证 Key 在模块加载时读取,热更新不生效 🆕

**位置**:`teage_liu/app.py:67-72`(`_security_api_key` 在模块顶层从 config 读取);对比 `config.py:204-227`(`_update_env_file` 支持热更新后同步 os.environ)。

**问题**:`PUT /config` 修改 `security.api_key` 后,中间件仍持有旧值直到**进程重启**;而配置系统其余部分已支持热更新,行为不一致。且认证是**单 Bearer token 硬比较**(`app.py:89`),无用户体系、无轮换机制(个人项目可接受,但应显式记录为已知边界)。

**修复方向**:
1. 中间件改为每次请求经容器取当前生效的 key(或维护 `_security_api_key` 全局变量并在 `PUT /config` 时刷新),纳入热更新;
2. 将"单 key 无轮换"写入 README/DEPLOY 的安全说明,明确这是个人部署边界;
3. 若 CORS(同样模块级读取,`app.py:43-51`)一并处理:改为动态读取或明确标注"需重启"。

## P1 — 可维护性与扩展性

### ISSUE-03:worker_adapter.py 3280 行上帝类,60+ 方法 🆕

**位置**:`teage_liu/multiagent/worker_adapter.py`(共 3280 行,`class WorkerAdapter` 起于 273 行;方法统计 60+,含 `_handle_collab_message`(1447-1707)、`_handle_request`(1707-1818)、`_trigger_urgent_llm`(2294-2486)、`_check_director_health`(2831-2939)等)。

**问题**:协作核心逻辑(消息路由、双队列、LLM 触发、重试队列、健康检查、选举、自治模式、休眠状态机)全部堆在一个类里,单一职责失效:
1. 任何修改都要通读 3000 行上下文,回归风险高;
2. 测试只能靠构造完整 WorkerAdapter 实例,单元化困难;
3. 该类是全书最大的文件,且协作是当前演进最活跃的领域(6 个 Phase),膨胀还在继续。

**修复方向**(建议拆分为 3-4 个协作类,复用现有测试做行为基线):
1. `CollabMessageRouter`(消息路由/双队列/幂等标记,抽取 `_handle_*` 系列);
2. `CollabLLMDriver`(LLM 上下文构建/触发/重试队列,抽取 `_build_collab_*`、`_trigger_*`、`_llm_retry_consumer`);
3. `CollabLiveness`(心跳/休眠/健康检查/选举,抽取 `_heartbeat_loop`、`_sleep_probe_once`、`_check_director_health`);
4. WorkerAdapter 保留为外观层(生命周期 start/stop + 组合上述组件)。

**风险提示**:此为**行为敏感重构**,需以现有 68 个 multiagent 测试文件为回归基线,分步迁移(先抽只读方法,再抽状态)。

### ISSUE-04:组件装配双轨制,DI 未彻底接管 🆕

**位置**:
- `teage_liu/app.py:659-703` `inject_lifespan_instances` —— lifespan 创建的实例经 `container.set_instance` 绕过工厂塞回容器(`container.py:98-107`);
- `teage_liu/lifespan.py:320-324` —— `app.state.cron_scheduler / orchestrator / proposal_store` 供未迁移路由使用,注释自述 "仅作向后兼容";
- 路由层两种取组件方式并存:`Depends(get_xxx)`(`app.py:210-267`)与 `app.state.*`。

**问题**:同一组件存在"工厂创建路径"与"lifespan 预创建路径"两套逻辑。热重载时工厂重建的实例与启动注入的实例**行为可能不一致**(例如 lifespan 注入时做了 ONNX 预热/MCP 连接的组件,工厂重建时未必复现同样的初始化)。双轨制是架构重构的过渡态,长期保留会让"组件如何被创建"成为需要记忆的隐性知识。

**修复方向**:
1. 明确唯一创建路径:要么工厂承担全部初始化(把预热/连接移入工厂),要么容器只接受显式注入(移除工厂,`get()` 未注入即抛错);
2. 路由统一走 `Depends(get_xxx)`,删除 `app.state.*` 兼容层;
3. 同步清理 `lifespan.py` 中 `container.get()` 与工厂重建之间重复的初始化代码。

### ISSUE-05:三套 A2A 协议并存,条件注册代码重复 🆕

**位置**:
- 协议三套:legacy JSON-RPC 网关(`teage_liu/multiagent/a2a_gateway.py`)+ 标准 A2A v1.0(`teage_liu/multiagent/a2a_std/`)+ standard mode 切换(配置 `a2a.standard.mode`);
- 客户端两个:`A2AClient`(`a2a_client.py`)与 `StdA2AClient`(`a2a_std/client.py`);
- 重复代码:`lifespan.py` 中 a2a_client / std_client 的获取与降级逻辑在 `_register_a2a_tools`(562-587 行)与 `_register_main_session_collab_tools`(642-651 行)**几乎逐字重复**;`worker_cfg.agent_id` 读取在 lifespan 中重复 3 次(254-255 / 574-575 / 639-640 行)。

**问题**:协议演进是合理的,但并存期没有收敛:
1. 新增一个"从配置取客户端"的入口就要复制一段 try/except 降级代码,演进成本显形;
2. 新读者难以判断"legacy 是否还被需要""standard mode 覆盖哪些场景"。

**修复方向**:
1. 抽出统一工厂 `get_a2a_client(config) -> (legacy_client, std_client)` 或单一 `A2AChannel` 抽象,消灭重复;
2. 在 ARCHITECTURE.md 明确"legacy ↔ standard"的**退役计划**(哪个版本后移除 legacy),而不是无限并存;
3. 记录标准 A2A 与 legacy 的功能覆盖差异(标准模式缺什么),避免"以为切了 standard 实际还走 legacy"的隐性行为。

**位置**:
- 根目录:`config.yaml.bak`、`server.py`(注释自述"仅保留给旧脚本",`teage_liu/server.py`)、`config2.yaml` / `config-a2a-1.yaml` / `config-a2a-2.yaml` 多份并存配置;

### ISSUE-08:测试库存在"过时"与"指向未实现功能"的测试 🆕

**位置**:
- git log 连续三条 `test(collab): S1/S2/S3 修正测试为生产行为`(测试过时,生产闸门正确)——说明测试曾与生产行为脱节;
- `CHANGELOG-开发日志.md:135-136`:全量测试 437 passed / **4 failed**,4 个失败被定性为"预先存在 WIP 失败"(untracked 测试文件依赖**未完成的 `append_collab_message` 函数`**)。

**问题**:测试是"契约",但库里存在指向未实现功能的测试(要么补实现,要么删除测试)。"WIP 失败长期挂着"会让 CI 对失败脱敏——新引入的失败会混入已知失败无人关注。

**修复方向**:
1. 清点 4 个 WIP 失败测试:功能补完(实现 `append_collab_message`)或删除测试,二选一,不留"已知红";
2. 建立机制:测试行为与生产行为不一致时,优先改生产(除非生产确实是错的),并在提交信息中显式记录契约变更(现有 S1/S2/S3 的做法是对的,继续保留);
3. 可选:CI 加 `--deselect` 已知失败清单,保证默认全绿。

### ISSUE-10:前端 25k 行无框架 JS,长期维护成本上升(观察项) 🆕

**位置**:`web/static/js/` 17 个 JS 文件(chat-core/chat-main/chat-session/... 共约 25k 行),全局作用域通信,无构建、无类型、无前端测试;另有 `web/js/`、`web/css/` 顶层模块(multiagent-sse.js 等)与 static 目录**两处 JS 共存**。

**问题**:无框架路线在功能少时最轻,但功能增长后:全局命名冲突风险、SSE 三通道各自为政、无回归手段。`web/js` 与 `web/static/js` 并存进一步增加"资源该放哪"的认知成本。

**修复方向**:
1. 至少合并 `web/js` 与 `web/static/js` 为一处,统一挂载;
2. 若保持无框架:引入 JS 模块化(ESM)与极简 lint,前端核心路径(chat SSE 消费)补 1-2 个端到端冒烟;
3. 若功能继续膨胀:评估渐进引入轻量框架或至少组件化(记录为长期方向,不强制)。

### ISSUE-11:协作系统性能天花板为已知约束(记录,非缺陷) 🆕

**位置**:`docs/plans/2026-07-31-N-Worker扩展性验证方案.md` 性能瓶颈预测表:LLM 风暴(N>3)、A2A HTTP(N>5)、文件锁争用(N>3 同机)、audit I/O(N>5)、watchdog fd 耗尽(N>10);`worker_adapter.py` `_llm_lock`(asyncio.Lock)使单实例内 LLM 调用全局串行化。

**说明**:N≤10 中规模是**用户已明确的决策**(不引入 Redis/etcd,CHANGELOG 2026-07-30 用户决策 5)。此处记录为显式架构边界,避免未来误判为缺陷:
1. 若未来需要 N>10:优先引入外部消息总线(Redis Streams / NATS)替换文件黑板,而非在文件层继续加锁;
2. 若需要单实例并发协作吞吐:`_llm_lock` 改为按会话/按 collab 分片锁,或引入协作专用 LLM 连接池;
3. 优化前先跑 `scripts/collect_perf_metrics.py` 采集基线,避免拍脑袋优化。
