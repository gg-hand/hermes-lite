# 调度执行强化设计

> **日期**: 2026-07-15（2026-07-17 grilling 修订）
> **状态**: Draft（待用户终审）
> **关联 bug**: cron 调度任务 `blog_monitor_joyehuang` 因 `context.cron_tool_registry` 未注入 + `cron_tool__` 前缀不一致，连续失败 15+ 天未被发现
> **设计哲学**: 分层增强（方案 A+）+ 协议通用化（保留未来提升为 Middleware 的可能）

## 1. 背景与问题

### 1.1 故障复盘

云服务器 `123.207.30.71` 上的周检任务 `Joye博客周检`（`48972c8a`）连续失败，根因是两层缺陷叠加：

1. **context 注入遗漏**：`scheduler.py` 构建 `WorkflowContext` 时未注入 `cron_tool_registry`，导致 `type: tool` step 的 `ToolCallExecutor._resolve_registry` 找不到 registry，抛 permanent 错误
2. **命名前缀不一致**：`schedules.yaml` 用 `cron_tool__blog_monitor_joyehuang`（带前缀），但 `CronToolRegistry` 注册名是 `blog_monitor_joyehuang`（无前缀），即使注入了也 `has_tool` 返回 False

已临时修复（注入 + `_normalize_name` 补丁），但暴露了 6 个系统性脆弱点。

### 1.2 六个脆弱点

| # | 脆弱点 | 严重度 | 根因 |
|---|--------|--------|------|
| 1 | 无启动时 missed schedule 补偿 | P1 | `_load_persisted` 不检查 `next_run < now` |
| 2 | context 注入靠手动 setattr，易遗漏 | P0 | 两个工厂路径各列一份 setattr |
| 3 | 无执行前工具校验 | P0 | 创建/启动时不校验 `config.tool` 存在性 |
| 4 | 失败无通知无重试 | P1 | `on_failure: skip` 直接跳过 |
| 5 | 命名前缀不一致 | P2 | 注册名无前缀，配置/LLM schema 带前缀 |
| 6 | runs.jsonl 持久化可能静默失败 | P2 | `runs_store is None` 时静默 return |

## 2. 设计目标

- **可观测性**：失败即时通知（邮件 + Webhook），执行历史可视化，连续失败告警
- **容错能力**：固定间隔重试（transient 错误），停机漏执行补偿，工具校验前置拦截
- **架构健壮性**：context 集中注入消除遗漏，命名前缀统一，持久化失败告警
- **轻量化**：不引入中间件管道/事件总线等过重抽象（YAGNI）
- **可独立开关**：每层 hook 通过 `config.cron.hooks.{name}.enabled` 独立开关，支持热更新回滚
- **扩展性**：`ScheduleHook` 协议设计保持通用签名（不绑定 schedule 特有概念），未来可平滑提升为跨模块 `Middleware`；支持注册自定义 hook（见第 14 章）

## 3. 架构概览

### 3.1 方案选型

采用**方案 A+：分层增强 + 可扩展层接口**。在现有 `_trigger` 流程上叠加 4 个独立 hook 层，每层实现 `ScheduleHook` 协议，通过配置独立开关。

不引入 Pipeline 编排器（YAGNI），`_trigger`（重命名为 `_run_schedule`）仍持有主流程，hooks 通过明确调用点接入。`ScheduleHook` 协议保留未来提升为通用 `Middleware` 的可能（见第 14 章）。

### 3.2 分层结构与数据流

```
_run_schedule(schedule)  ← 由 _trigger 重命名，保留全部现有逻辑
  │
  ├─ ① ValidateHook.before_execute(ctx)
  │     校验 workflow spec（工具存在性、step type 合法性）
  │     失败 → 抛 ValidationError，进 on_failure
  │
  ├─ ② CatchUpHook.before_execute(ctx)  [仅启动时 scan_and_compensate]
  │     next_run < now 时按 catch_up_policy 处理
  │     skip → 跳过，更新 next_run 到下个周期
  │     execute_once → 串行 await 补跑一次
  │
  ├─ ③ RetryHook.on_failure(ctx, error)  ← 包裹核心执行
  │     error.is_permanent → 不重试，返回 give_up
  │     error.is_transient → 固定间隔重试（默认 5min，max 3 次）
  │     整次重跑（不做 step 级 checkpoint，YAGNI）
  │
  ├─ 核心执行：_execute_workflow(orchestrator, schedule, ...)
  │     WorkflowEngine.execute 末尾 if not result.success: raise WorkflowExecutionError(result)
  │     ↑ Q1 决策 C：移除 WorkflowEngine 内的 RetryBudget，RetryHook 是唯一重试层
  │
  ├─ ④ NotifyHook.after_execute(ctx, result)
  │     result.success → 无操作（清零连续失败计数）
  │     result.failed → 邮件 + Webhook 双通道通知
  │     连续失败 ≥ threshold → 自动 disable + 告警
  │
  └─ _append_run_summary(schedule, ...)
        无论成功失败都持久化 RunSummary + StepTraces 到 runs.jsonl
```

### 3.3 ScheduleHook 协议 + ScheduleHookBase 基类（通用签名，便于未来提升为 Middleware）

**设计原则**：
- 签名通用（before/on_failure/after），不绑定 schedule 特有概念
- ctx 类型为 WorkflowContext（复用现有，不引入新 context 类型）
- result 类型为 WorkflowResult（复用现有，不引入 RunResult）
- 未来提升为 Middleware 时，仅需新增适配层，hook 实现无需改动

**实现要求**（P0 修复）：4 个 hook 实现均**只实现协议三方法中的一个子集**（ValidateHook 只实现 before_execute、RetryHook 只实现 on_failure、NotifyHook 只实现 after_execute）。Python Protocol 不提供方法继承，默认实现仅作为文档。为避免 HookRegistry 循环调用时抛 `AttributeError`，引入 `ScheduleHookBase` 基类提供 no-op 默认实现，所有 hook **必须继承此类**：

```python
class ScheduleHook(Protocol):
    """调度执行钩子协议（类型声明，不可直接继承）。"""
    name: str  # "validate" | "catchup" | "retry" | "notify" | 自定义

    async def before_execute(self, ctx: "WorkflowContext") -> "WorkflowContext": ...
    async def on_failure(self, ctx: "WorkflowContext", error: Exception) -> "RetryDecision": ...
    async def after_execute(self, ctx: "WorkflowContext", result: "WorkflowResult") -> None: ...


class ScheduleHookBase:
    """ScheduleHook 协议的 no-op 默认实现基类。

    所有 hook 实现必须继承此类，按需 override 对应方法。
    未 override 的方法为 no-op，避免 HookRegistry 循环调用时 AttributeError。
    """
    name: str = ""

    async def before_execute(self, ctx: "WorkflowContext") -> "WorkflowContext":
        return ctx

    async def on_failure(self, ctx: "WorkflowContext", error: Exception) -> "RetryDecision":
        return RetryDecision.give_up()

    async def after_execute(self, ctx: "WorkflowContext", result: "WorkflowResult") -> None:
        pass
```

**hook 实现要求**（4.1/5.1/5.2/6.1 的 hook 类声明改为继承 ScheduleHookBase）：

```python
class ValidateHook(ScheduleHookBase): ...   # 仅 override before_execute
class CatchUpHook(ScheduleHookBase): ...    # 仅 override before_execute（运行时 no-op）+ scan_and_compensate
class RetryHook(ScheduleHookBase): ...      # 仅 override on_failure
class NotifyHook(ScheduleHookBase): ...     # 仅 override after_execute
```

### 3.6 _run_schedule 主流程（Q4 决策：替换 _trigger，插入 hook 调用点）

**不重新实现主流程**，而是把现有 `_trigger` 重命名为 `_run_schedule`，在以下 3 个接入点插入 hook 调用：

| 接入点 | 位置 | hook 调用 |
|--------|------|-----------|
| ① 执行前 | `archive_callback` 覆盖之后、`_execute_workflow` 之前 | `await self.hooks.before_execute(ctx)` |
| ② 核心执行 | `_execute_workflow` 调用处 | 包 `while True` 重试循环 + `await self.hooks.on_failure(ctx, e)` |
| ③ 执行后 | `RunSummary` 持久化之前 | `await self.hooks.after_execute(ctx, result)` |

**保留 `_trigger` 的全部现有逻辑**：① archive_callback 覆盖/恢复（try/finally）；② session_logger 写入；③ task_text 时间变量渲染；④ last_run 时间解析；⑤ RunSummary 持久化；⑥ cron 会话标题设置；⑦ next_run 更新 + _persist。

```python
async def _run_schedule(self, orchestrator, schedule, started_at_dt, ...):
    # P1 修复：签名与现有 _trigger(self, orchestrator, schedule) 对齐（scheduler.py:545-547），
    # orchestrator 是构造 ctx 的必填第一参数（_build_workflow_context 第 1 参数）
    # === 现有 _trigger 逻辑保持不变（session_logger / task_text 渲染 / archive_callback 覆盖等）===
    run_id = ...
    ctx = self._build_workflow_context(orchestrator, schedule, started_at_dt, ...)
    ctx.schedule = schedule  # Q2: 新增字段填充
    ctx.retry_max = self.hooks.get_retry_max()  # Q11: 供 NotifyHook 读取

    # ① before_execute（校验 + 补偿运行时空操作）
    # P0 修复：ValidationError 与 HookAbortError 都路由到 _finalize_failure（含 after_execute 通知）
    try:
        ctx = await self.hooks.before_execute(ctx)
        if ctx.validation_errors:
            raise ValidationError(ctx.validation_errors)
    except (HookAbortError, ValidationError) as e:
        return await self._finalize_failure(ctx, e, wf_result=None)

    # ② 核心执行 + 重试（Q1 决策 C：RetryHook 是唯一重试层）
    wf_result: Optional[WorkflowResult] = None  # P1 修复：显式初始化，避免 give_up 时 NameError
    while True:
        try:
            wf_result = await asyncio.to_thread(self._execute_workflow, ...)
            break
        except Exception as e:
            # Q3 决策 D：WorkflowExecutionError 与其他异常统一处理
            # （WorkflowExecutionError 是 Exception 子类，无需单独分支；差异化处理在 _is_permanent_error 内完成）
            ctx.last_error = e
            decision = await self.hooks.on_failure(ctx, e)
            if decision.retry:
                ctx.retry_count += 1
                logger.info(
                    "调度 %s 第 %d 次重试（%ds 后），原因: %s",
                    schedule.id, ctx.retry_count, decision.delay_seconds, decision.reason,
                )
                await asyncio.sleep(decision.delay_seconds)
                continue
            break

    # ③ after_execute（通知）
    # P0 修复：无条件调用 after_execute，由 NotifyHook 内部按 result.success 分支处理
    # （成功时清零 _failure_counts，失败时累加 + 通知）
    result = wf_result if wf_result is not None else WorkflowResult(
        success=False, errors=[str(ctx.last_error) if ctx.last_error else "未知错误"]
    )
    await self.hooks.after_execute(ctx, result)

    # === 现有 _trigger 逻辑保持不变（RunSummary 持久化 / next_run 更新 / _persist）===
    await asyncio.to_thread(self._append_run_summary, ...)
    self._persist()


async def _finalize_failure(self, ctx, error, wf_result: Optional[WorkflowResult] = None):
    """P1 修复：校验/钩子终止时的统一收尾。

    职责：
    1. 构造失败的 WorkflowResult（若 wf_result 为 None）
    2. 调用 after_execute（触发通知）
    3. 持久化 RunSummary
    4. 更新 next_run + _persist
    """
    result = wf_result if wf_result is not None else WorkflowResult(
        success=False, errors=[str(error)]
    )
    ctx.last_error = error
    await self.hooks.after_execute(ctx, result)
    await asyncio.to_thread(self._append_run_summary, ctx.schedule, result, ...)
    self._persist()
```

- 3.6 的两个 `except` 分支已合并为单一 `except Exception`（`WorkflowExecutionError` 是 `Exception` 子类，差异化处理在 `_is_permanent_error` 内完成）

### 3.7 HookRegistry

```python
class HookRegistry:
    """管理所有 hook 实例，按 config 开关启用/禁用。

    Q8 决策：_failure_counts 不放在 HookRegistry（避免重建时迁移），
    而是放在 CronScheduler 实例上（长生命周期）。
    """
    def __init__(self, config: dict, scheduler_ref: Optional[Any] = None):
        self.hooks: Dict[str, ScheduleHook] = {}
        self._scheduler_ref = scheduler_ref  # 弱引用，用于访问 scheduler._failure_counts
        if config.get("validate", {}).get("enabled", True):
            self.hooks["validate"] = ValidateHook(config["validate"])
        if config.get("catchup", {}).get("enabled", True):
            self.hooks["catchup"] = CatchUpHook(config["catchup"])
        if config.get("retry", {}).get("enabled", True):
            self.hooks["retry"] = RetryHook(config["retry"])
        if config.get("notify", {}).get("enabled", True):
            self.hooks["notify"] = NotifyHook(config["notify"], scheduler_ref=scheduler_ref)

    async def before_execute(self, ctx: WorkflowContext) -> WorkflowContext:
        for hook in self.hooks.values():
            ctx = await hook.before_execute(ctx)
        return ctx

    async def on_failure(self, ctx: WorkflowContext, error: Exception) -> RetryDecision:
        # 只调用 retry hook
        if "retry" in self.hooks:
            return await self.hooks["retry"].on_failure(ctx, error)
        return RetryDecision.give_up()

    async def after_execute(self, ctx: WorkflowContext, result: WorkflowResult) -> None:
        for hook in self.hooks.values():
            await hook.after_execute(ctx, result)

    def get_retry_max(self) -> int:
        """Q11: 供 ctx.retry_max 填充，NotifyHook 通知模板读取。"""
        retry_hook = self.hooks.get("retry")
        return getattr(retry_hook, "max_retries", 0) if retry_hook else 0
```

## 4. L1 校验层 + 架构健壮性

### 4.1 ValidateHook（Q12/Q14 决策）

```python
class ValidateHook:
    """L1: 执行前校验 workflow spec。

    Q14 决策：validate.enabled=False 只跳过执行前校验（③），
    创建时（①）与启动时（②）仍校验（数据完整性不受运行时开关影响）。
    """
    name = "validate"

    def __init__(self, config: dict):
        self.config = config

    async def before_execute(self, ctx: WorkflowContext) -> WorkflowContext:
        schedule = ctx.schedule
        if not schedule or not schedule.workflow:
            return ctx  # legacy 路径不校验

        errors = validate_workflow_spec(
            spec=schedule.workflow,
            cron_tool_registry=ctx.cron_tool_registry,
            tool_registry=ctx.tool_registry,
        )
        if errors:
            ctx.validation_errors = errors
            logger.warning("调度 %s 校验失败: %s", schedule.id, errors)
        return ctx


def validate_workflow_spec(spec, cron_tool_registry, tool_registry) -> List[str]:
    """校验 workflow spec，返回错误列表（空列表=通过）。

    Q12 决策：step.type 合法值为 5 种（与 spec.py ALLOWED_STEP_TYPES 对齐）。
    """
    errors = []
    if not spec.name:
        errors.append("workflow.name 为空")

    ALLOWED_STEP_TYPES = ("deterministic", "llm", "tool", "react", "subworkflow")
    for step in spec.steps:
        if step.type not in ALLOWED_STEP_TYPES:
            errors.append(f"step '{step.id}' 的 type '{step.type}' 不合法，允许: {ALLOWED_STEP_TYPES}")
            continue
        if step.type == "tool":
            tool_name = step.config.get("tool", "")
            if not tool_name:
                errors.append(f"step '{step.id}' 未配置 config.tool")
                continue
            found = False
            if cron_tool_registry and cron_tool_registry.has_tool(tool_name):
                found = True
            elif tool_registry and tool_registry.has_tool(tool_name):
                found = True
            if not found:
                errors.append(
                    f"step '{step.id}' 引用的工具 '{tool_name}' 未在任何 registry 注册"
                )
    return errors
```

**校验时机**（Q14 决策）：
1. **创建/更新调度项时**（`create_schedule` / `update_schedule`）：API 返回 400 + 错误详情（不受 `validate.enabled` 影响）
2. **服务启动加载时**（`_load_persisted`）：记 WARNING 日志，不阻止启动（不受 `validate.enabled` 影响）
3. **执行前**（`ValidateHook.before_execute`）：受 `validate.enabled` 开关控制，禁用时跳过

```python
class CatchUpHook:
    """L2: 启动时扫描过期调度项，按 catch_up_policy 处理。

    Q9 决策：串行 await 执行补偿任务（非 asyncio.create_task 并发），
    避免与正常 run_loop 触发的执行竞争同一 schedule 的 cron_tool_registry /
    archive_callback 覆盖。启动延迟可接受（每个 schedule 几秒，4 个最多 30 秒）。

    注意：scan_and_compensate 是本 hook 特有的启动时方法，
    不属于 ScheduleHook 协议（协议只有 before/on_failure/after）。
    before_execute 在运行时为空操作，仅保留协议一致性。
    """
    name = "catchup"

    def __init__(self, config: dict):
        self.default_policy = config.get("default_policy", "skip")

    async def before_execute(self, ctx: WorkflowContext) -> WorkflowContext:
        # 运行时不触发，仅启动扫描调用 scan_and_compensate
        return ctx

    async def scan_and_compensate(self, scheduler) -> List[str]:
        """启动时扫描所有过期调度项，按策略处理。返回处理的 schedule_id 列表。"""
        now = datetime.now()
        compensated = []
        for schedule in scheduler._schedules:
            if not schedule.enabled or not schedule.next_run:
                continue
            try:
                next_dt = datetime.fromisoformat(schedule.next_run)
            except (ValueError, TypeError):
                continue
            if next_dt >= now:
                continue  # 未过期

            policy = getattr(schedule, "catch_up_policy", None) or self.default_policy
            if policy == "execute_once":
                logger.info("补偿执行过期调度 %s (next_run=%s)", schedule.id, schedule.next_run)
                # Q9: 串行 await，非 create_task
                await scheduler._run_schedule_direct(schedule)
                compensated.append(schedule.id)
            # 无论 skip 还是 execute_once，都更新 next_run 到下个周期
            cron_expr = scheduler._cron_exprs.get(schedule.id)
            if cron_expr:
                schedule.next_run = cron_expr.next_run(now).isoformat()
        if compensated:
            scheduler._persist()
        return compensated
```

```python
class RetryDecision:
    """重试决策。"""
    def __init__(self, retry: bool, delay_seconds: int = 0, reason: str = ""):
        self.retry = retry
        self.delay_seconds = delay_seconds
        self.reason = reason

    @classmethod
    def give_up(cls, reason="") -> RetryDecision:
        return cls(retry=False, reason=reason)

    @classmethod
    def retry_after(cls, seconds: int, reason="") -> RetryDecision:
        return cls(retry=True, delay_seconds=seconds, reason=reason)


class RetryHook:
    """L3: 失败后固定间隔重试。permanent 错误不重试。

    Q1 决策 C：RetryHook 是唯一重试层（WorkflowEngine 内的 RetryBudget 已移除）。
    Q3 决策：整次重跑（不做 step 级 checkpoint，YAGNI）。
    """
    name = "retry"

    def __init__(self, config: dict):
        self.max_retries = config.get("max_retries", 3)
        self.interval_seconds = config.get("interval_seconds", 300)
        self.transient_only = config.get("transient_only", True)

    async def on_failure(self, ctx: WorkflowContext, error: Exception) -> RetryDecision:
        # 错误分类：permanent vs transient
        if self.transient_only and _is_permanent_error(error):
            return RetryDecision.give_up(
                reason=f"permanent 错误，不重试: {type(error).__name__}: {error}"
            )
        if ctx.retry_count >= self.max_retries:
            return RetryDecision.give_up(
                reason=f"已达最大重试次数 {self.max_retries}"
            )
        return RetryDecision.retry_after(
            seconds=self.interval_seconds,
            reason=f"transient 错误，第 {ctx.retry_count + 1}/{self.max_retries} 次重试: {error}"
        )


def _is_permanent_error(error: Exception) -> bool:
    """判断是否为不可恢复的 permanent 错误。

    permanent 错误类型（Q10 决策：异常类统一在 tool_error.py）：
    - ToolNotFoundError（工具未注册，重试也没用）
    - ValidationError（配置错误）
    - ParamError（参数校验失败）
    - HookAbortError（校验层主动终止）
    - WorkflowExecutionError 且含 permanent step trace（step 的 error_class 是 permanent）

    transient 错误类型（可重试）：
    - 网络超时 / ConnectionError
    - SMTP 发送失败
    - RSS 拉取失败
    - 子进程超时
    - 其他未分类异常（默认 transient，给一次机会）
    """
    from hermes.agent.tool_error import (
        ToolNotFoundError, ParamError, HookAbortError, ValidationError,
        AuthRequiredError,
    )
    # P1 修复：补充 AuthRequiredError 到顶层 isinstance 检查
    # （原仅检查 4 类，AuthRequiredError 在 workflow 之外直接抛出时会落入 transient 兜底，与 9.1 表格矛盾）
    if isinstance(error, (ToolNotFoundError, ParamError, ValidationError, HookAbortError, AuthRequiredError)):
        return True
    # WorkflowExecutionError 检查 step_traces 中是否有 permanent 错误
    if isinstance(error, WorkflowExecutionError):
        result = error.result
        for trace in getattr(result, "step_traces", []):
            if getattr(trace, "error_class", None) in ("permanent", "auth_required"):
                return True
    return False
```

## 6. L4 通知层

### 6.1 NotifyHook（Q7 决策：复用 WorkflowResult + Q8 决策：_failure_counts 提到 CronScheduler）

```python
class NotifyHook:
    """L4: 失败后邮件 + Webhook 双通道通知。连续失败自动 disable。

    Q7 决策：result 类型为 WorkflowResult（复用现有，不引入 RunResult）。
    Q8 决策：_failure_counts 放在 CronScheduler 上（非 HookRegistry / NotifyHook 实例），
            配置热更新时零迁移成本。
    Q11 决策：max_retries 从 ctx.retry_max 读取（由 RetryHook 通过 HookRegistry.get_retry_max() 写入）。
    """
    name = "notify"

    def __init__(self, config: dict, scheduler_ref: Optional[Any] = None):
        self.threshold = config.get("consecutive_failures_threshold", 3)
        self.channels = config.get("channels", {})
        self._scheduler_ref = scheduler_ref  # 弱引用 CronScheduler，访问 _failure_counts

    def _get_failure_count(self, schedule_id: str) -> int:
        """Q8: 从 CronScheduler._failure_counts 读取。"""
        scheduler = self._scheduler_ref() if callable(self._scheduler_ref) else self._scheduler_ref
        if scheduler is None:
            return 0
        return scheduler._failure_counts.get(schedule_id, 0)

    def _set_failure_count(self, schedule_id: str, count: int) -> None:
        """Q8: 写入 CronScheduler._failure_counts。"""
        scheduler = self._scheduler_ref() if callable(self._scheduler_ref) else self._scheduler_ref
        if scheduler is None:
            return
        if count == 0:
            scheduler._failure_counts.pop(schedule_id, None)
        else:
            scheduler._failure_counts[schedule_id] = count

    async def after_execute(self, ctx: WorkflowContext, result: WorkflowResult) -> None:
        if result.success:
            self._set_failure_count(ctx.schedule.id, 0)  # 清零
            return

        count = self._get_failure_count(ctx.schedule.id) + 1
        self._set_failure_count(ctx.schedule.id, count)

        # 发送通知（邮件 + Webhook 并行）
        tasks = []
        if self.channels.get("email", {}).get("enabled"):
            tasks.append(self._send_email(ctx, result, count))
        if self.channels.get("webhook", {}).get("enabled"):
            tasks.append(self._send_webhook(ctx, result, count))
        if tasks:
            results = await asyncio.gather(*tasks, return_exceptions=True)
            for i, r in enumerate(results):
                if isinstance(r, Exception):
                    logger.warning("通知渠道 %s 发送失败: %s", i, r)

        # 连续失败达阈值 → 自动 disable
        if count >= self.threshold:
            logger.warning(
                "调度 %s 连续失败 %d 次，自动 disable",
                ctx.schedule.id, count
            )
            ctx.schedule.enabled = False
            await self._send_alert(ctx, count)
```

## 12. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| hook 执行异常导致整个调度崩溃 | 中 | 高 | 每个 hook 调用包裹 try/except，hook 异常只记日志不传播 |
| `runs.jsonl` 文件膨胀 | 低 | 中 | 定期归档（超过 10MB 时滚动到 `runs.{date}.jsonl`） |
| 邮件/Webhook 发送阻塞调度线程 | 中 | 中 | 通知异步发送（`asyncio.gather`），设 10s 超时 |
| 配置热更新时 `_failure_counts` 丢失 | 低 | 低 | Q8：计数放 CronScheduler 上，HookRegistry 重建零迁移 |
| catch_up 补偿执行导致启动时负载突增 | 中 | 中 | Q9：补偿任务串行 await（非并发），且只补一次 |
| Q1 移除 RetryBudget 破坏现有 multi-step workflow | 中 | 高 | Q3：on_failure.action 简化为 3 种，现有配置无 retry，零迁移；WorkflowExecutionError 携带完整 step_traces 便于诊断 |
| Q5 命名前缀统一破坏旧 schedules.yaml | 低 | 中 | 现有 schedule 无 cron_tool 的 snapshot 配置，零迁移；register 兼容传入带/不带前缀名 |

## 14. 扩展性设计

### 14.1 ScheduleHook 协议的通用性

`ScheduleHook` 协议的 3 个方法签名（`before_execute` / `on_failure` / `after_execute`）不绑定 schedule 特有概念：

- `ctx` 类型为 `WorkflowContext`（通用 workflow 上下文，非 schedule 专属）
- `result` 类型为 `WorkflowResult`（通用 workflow 结果）
- `error` 类型为 `Exception`（通用异常）

这意味着 hook 实现与「调度」解耦，未来可被任意「执行-失败-重试」流程复用。

### 14.2 未来提升为 Middleware 的路径

当第二个模块（如 chat 流程 / tool 执行流程）需要类似的「校验-重试-通知」能力时，可按以下路径演进：

1. **提取 Middleware 协议**：将 `ScheduleHook` 重命名为 `Middleware`，签名不变
2. **提取 MiddlewareRegistry**：将 `HookRegistry` 重命名为 `MiddlewareRegistry`，移除 `get_retry_max` 等调度特有方法
3. **适配层**：各模块实现自己的 `MiddlewareRunner`，负责从自己的 ctx 构造 `WorkflowContext` 并调用 `MiddlewareRegistry`

演进成本：仅重命名 + 移除少量调度特有方法，hook 实现零改动。

### 14.3 自定义 hook 注册机制

`HookRegistry` 预留 `register_custom_hook` 方法，支持未来通过配置注册自定义 hook：

```python
# 未来扩展（当前不实现，YAGNI）
class HookRegistry:
    def register_custom_hook(self, name: str, hook: ScheduleHook) -> None:
        """注册自定义 hook（未来扩展，当前不实现）。"""
        self.hooks[name] = hook
```

配置示例（未来）：

```yaml
cron:
  hooks:
    custom:
      - name: my_metrics_hook
        module: my_package.hooks
        class: MetricsHook
        config:
          metric_prefix: "cron_"
```

**当前不实现**，仅保留协议层面的扩展可能。

### 14.4 扩展点清单

| 扩展点 | 当前状态 | 未来扩展方式 |
|--------|----------|--------------|
| 新增 hook 层（如 MetricsHook） | 协议支持，未实现 | 实现 ScheduleHook + 配置开关 |
| 跨模块复用（chat / tool 流程） | 协议通用，未实现 | 提取 Middleware + 适配层 |
| 自定义 hook 注册 | 预留接口，未实现 | register_custom_hook + 配置 |
| 新增通知渠道（如 Slack） | NotifyHook 支持多渠道 | channels 配置新增 slack 段 |
| 新增校验规则 | validate_workflow_spec 可扩展 | 函数内新增检查项 |
