# 架构重构收尾设计规格

## 背景

前一轮重构（10个commit, Task 1-6）完成了 DI 容器、错误体系、5个子管理器提取、热重载机制接入。但深度审查发现三类问题：
1. routes/schemas 脚手架是死代码且有5个导入bug
2. server.py(4578行)、orchestrator.py(2100行)、react_loop.py(2164行)、builtin_tools.py(2304行) 均未实际拆分
3. 容器初始化了但是空的，热重载空转

## 目标

完成架构重构收尾：清理死代码、注册组件到容器、拆分巨型文件、让热重载真正生效。

## 执行顺序

**1 → 3 → 2 → 4**（容器注册先于路由拆分，因为路由通过容器访问组件）

## 阶段1：清理死代码

删除有bug的 routes/schemas 脚手架：
- 删除 `src/routes/`（12文件，~2600行死代码，5个导入bug）
- 删除 `src/schemas/`（8文件，~296行死代码）
- 删除 `scripts/split_server.py`
- 删除 `tests/test_schemas_import.py`
- 保留 `src/app.py`（有容器管理 + 异常处理器）

验证：全量测试无回归（脚手架未接入，删除零影响）。

## 阶段3：容器注册

### 组件注册策略

Orchestrator 作为整体注册（方案B），内部组件（llm_client/chroma_store/policy_engine等）对容器透明。

### CONFIG_TO_COMPONENTS 映射

```python
CONFIG_TO_COMPONENTS = {
    "llm":        ["orchestrator"],
    "security":   ["approval_manager", "orchestrator"],
    "storage":    ["session_logger", "orchestrator"],
    "memory":     ["orchestrator"],
    "monitoring": ["metrics_collector", "metrics_store", "audit_logger"],
    "tasks":      ["task_manager", "cron_scheduler"],
    "skills":     ["mcp_manager"],
    "files":      ["upload_manager", "etl_engine"],
    "guardrails": ["orchestrator"],
    "cron":       ["orchestrator"],
    "history":    ["orchestrator"],
    "tools":      ["orchestrator"],
    "server":     [],
}
```

几乎每个配置段变更都会重建 Orchestrator。重建成本1-2秒可接受（热重载是低频操作）。

### 组件注册清单

| 组件名 | 配置依赖 | 组件依赖 | hot_reloadable |
|--------|----------|----------|----------------|
| session_logger | storage | 无 | True |
| metrics_collector | monitoring | 无 | True |
| metrics_store | monitoring | session_logger | True |
| audit_logger | monitoring | 无 | True |
| approval_manager | security | metrics_collector | True |
| task_manager | tasks | 无 | True |
| orchestrator | 全局 | approval_manager, task_manager, metrics_collector, audit_logger | False |
| stream_manager | 无 | 无 | False |
| skill_loader | 无 | 无 | False |
| mcp_manager | skills | skill_loader | True |
| upload_manager | files | 无 | True |
| etl_engine | files | upload_manager, orchestrator | True |
| cron_scheduler | tasks | orchestrator | False |
| proposal_store | 无 | 无 | False |
| health_checker | 无 | orchestrator, session_logger, mcp_manager | False |

### 路由访问组件方式

路由通过 `get_container().get("component_name")` 访问组件。过渡期 lifespan 同时设全局变量兼容。

## 阶段2：分层拆分 server.py

### Step 2a：提取 Pydantic 模型到 schemas/

按域分组提取 ~27个 BaseModel 子类到 schemas/{chat,config,schedules,approvals,proposals,memory,files,common}.py。零行为变更。

### Step 2b：提取 lifespan 到 app.py

lifespan + 全局组件变量移到 app.py。server.py 变成 `from app import app`。

### Step 2c-2n：按域提取路由

12个域逐个迁移到 routes/{domain}.py，使用 APIRouter + app.include_router()。

迁移顺序（依赖复杂度从低到高）：
1. misc 2. health 3. sessions 4. config 5. approvals 6. proposals
7. skills 8. files 9. cron_tools 10. memory 11. schedules 12. chat

每个域迁移后运行全量测试。最终 server.py <100行。

## 阶段4：Orchestrator + react_loop + builtin_tools 清理

### Step 4a：移除 Orchestrator 委托 wrapper

18个委托方法移除，调用方改为直接访问 manager（如 `orchestrator.msg_persistence.persist_new_messages()`）。

### Step 4b：从 react_loop.py 提取 ToolExecutor + StreamHandler

- `agent/tool_executor.py` — 工具执行逻辑（重试检测、卡死检测、安全拦截）
- `agent/stream_handler.py` — SSE 流处理逻辑
- react_loop.py 保留主循环，<500行

### Step 4c：从 builtin_tools.py 迁移代码到 tools/

实际代码按域迁移到 tools/{file,shell,web,memory,plan}_tools.py。builtin_tools.py 删除。
