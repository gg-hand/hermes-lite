## 3. 整体架构:模块化单体 + DI 容器

### 3.1 依赖方向

```
routes/  →  container  →  agent.Orchestrator  →  各领域模块
(表现层)     (DI 容器)       (瘦编排器)           (llm/memory/tasks/...)
                                                  ↓
                                              storage/infra
```

核心规则:外层依赖内层,领域模块之间不直接导入,只通过容器注入的接口通信。

### 3.3 基础设施层

- **container.py** — DI 容器:组件注册/获取/热重载重建
- **config.py** — 保留现有配置加载 + 增加热重载分类标记
- **routes/** — 按领域拆分路由(8+ 文件,从 server.py 拆出)
- **schemas/** — Pydantic 模型(从 server.py 提取,20+ 模型独立)

### 3.4 扩展性保障

后续功能扩展时的约束与约定:

1. **新增领域模块** — 创建新目录,在容器中 register(),遵循"不直接导入其他领域模块"规则。第 3.2 节表格是开放的,可追加。

2. **新增容器组件** — 必须:
   - 实现 `close()` 方法(如持有资源:连接、线程、文件句柄)
   - 在容器 `register()` 时声明 `deps` 和 `hot_reloadable`
   - 如可热重载,在 `CONFIG_TO_COMPONENTS` 中添加配置段映射
   - 启动时容器自动验证:所有 deps 已注册、所有 hot_reloadable 组件有配置段映射

3. **新增配置段** — 在 `config.py` 中定义 schema,在 `CONFIG_TO_COMPONENTS` 中添加映射,如需热重载则实现对应组件的 factory 重建逻辑。

4. **Orchestrator 膨胀防护** — Orchestrator 只做协调,不实现业务逻辑。新增功能应放入对应领域模块或新建子管理器,不应往 Orchestrator 堆代码。CI 检查 orchestrator.py 不超过 300 行。

5. **领域模块间通信** — 只通过容器注入的接口通信,不直接 `import`。新增模块在 factory 中通过 `c.get()` 获取依赖。

## 4. DI 容器设计

### 4.1 容器结构

```python
class Container:
    """轻量 DI 容器:组件单例 + 工厂延迟创建 + 热重载重建。"""

    def __init__(self, config: dict):
        self._config = config
        self._instances: dict[str, Any] = {}       # 单例缓存
        self._factories: dict[str, Factory] = {}    # 工厂注册
        self._deps: dict[str, list[str]] = {}       # 依赖图(谁依赖谁)
        self._lock = threading.RLock()              # 保护热重载并发

    def validate(self):
        """所有组件注册完成后调用,验证依赖图无环。"""
        self._validate_no_cycles()
        self._validate_deps_registered()

    def _validate_no_cycles(self):
        """DFS 三色标记检测循环依赖,发现环则抛 ContainerConfigError。"""
        WHITE, GRAY, BLACK = 0, 1, 2
        color = {name: WHITE for name in self._factories}

        def dfs(name, path):
            if color[name] == GRAY:
                cycle = " → ".join(path + [name])
                raise ContainerConfigError(f"检测到循环依赖: {cycle}")
            if color[name] == BLACK:
                return
            color[name] = GRAY
            for dep in self._deps.get(name, []):
                dfs(dep, path + [name])
            color[name] = BLACK

        for name in self._factories:
            dfs(name, [])

    def _validate_deps_registered(self):
        """验证所有 deps 引用的组件都已注册。"""
        for name, deps in self._deps.items():
            for dep in deps:
                if dep not in self._factories:
                    raise ContainerConfigError(
                        f"组件 '{name}' 依赖未注册的组件 '{dep}'"
                    )
```

### 4.3 热重载流程(原子性重建 + 延迟关闭)

```python
# CLOSE_GRACE_PERIOD 动态计算:覆盖最坏情况(单次 LLM 超时 × 最大循环数)
# 默认值 = config.llm.timeout * config.tools.max_loops(如 60s * 10 = 600s)
# 可通过 config.server.hot_reload_grace_period 显式覆盖
def _get_grace_period(config) -> int:
    explicit = config.get("server", {}).get("hot_reload_grace_period")
    if explicit:
        return explicit
    llm_timeout = config.get("llm", {}).get("timeout", 60)
    max_loops = config.get("tools", {}).get("max_loops", 10)
    return llm_timeout * max_loops

def reload(self, changed_sections: set[str], new_config: dict):
    """原子性重建:先创建全部新实例,全部成功后才替换,失败则回滚。

    1. 映射配置段→受影响组件
    2. 拓扑排序计算级联
    3. 先创建所有新实例(临时持有,不写入 _instances)
    4. 全部成功 → 批量替换,旧实例进入延迟关闭队列
    5. 任何失败 → 丢弃已创建的新实例(close()),_instances 保持不变,抛 ConfigReloadError
    """
    with self._lock:
        directly_affected = self._map_config_to_components(changed_sections)
        to_rebuild = self._topo_sort_dependents(directly_affected)

        # 阶段1:先创建所有新实例(不替换 _instances)
        new_instances = {}
        try:
            self._config = new_config  # factory 通过 c.config 读取新配置
            for name in to_rebuild:
                new_instances[name] = self._factories[name](self)
        except Exception as e:
            # 创建失败:丢弃已创建的新实例,恢复旧 config,_instances 不变
            self._config = {k: self._instances  # 恢复旧配置
                            for k in self._instances}  # 简化:实际需保存旧 config 引用
            for inst in new_instances.values():
                if inst and hasattr(inst, "close"):
                    try: inst.close()
                    except Exception: pass
            raise ConfigReloadError(f"热重载重建失败: {e}") from e

        # 阶段2:全部成功,批量替换
        old_instances = {}
        for name in to_rebuild:
            old_instances[name] = self._instances.get(name)
            self._instances[name] = new_instances[name]

        # 阶段3:延迟关闭旧实例(动态 grace period)
        grace = _get_grace_period(self._config)
        for name, old in old_instances.items():
            if old and hasattr(old, "close"):
                timer = threading.Timer(
                    grace,
                    lambda o=old, n=name: self._safe_close(o, n)
                )
                timer.daemon = True
                timer.start()
```

### 4.7 热重载失败回滚策略

热重载失败时的磁盘/内存不一致处理(方案 B:磁盘保留 + 重启时兜底):

| 层面 | 处理 |
|------|------|
| **内存** | 原子性回滚:_instances 保持旧实例不变,旧 config 恢复,抛 ConfigReloadError |
| **磁盘** | 保留新配置(用户编辑内容不丢失),`.bak` 已有旧配置备份 |
| **HTTP 响应** | `PUT /config` 捕获 ConfigReloadError,返回 500 + 错误详情(如"LLM 客户端热重载失败:API Key 无效") |
| **重启兜底** | 启动时 `validate_required_env_vars` 校验失败,自动加载 `.bak` 备份配置,记录 warning |
| **用户操作** | 用户看到错误后可修改配置重新提交;若不修改就重启,启动兜底保证不崩 |

```
PUT /config (新配置)
  ├─ 1. 写盘 + 备份 .bak
  ├─ 2. container.reload() 原子性重建
  │    ├─ 成功 → 200, reloaded=[...], needs_restart=false
  │    └─ 失败 → 500, error="ConfigReloadError", message="..."
  │              (磁盘=新配置, 内存=旧配置, 用户可修改重试)
  └─ 3. 用户不修改就重启?
       └─ 启动时 validate 失败 → 自动加载 .bak → warning → 服务正常启动
```

### 4.8 有状态组件清单与热重载安全保障

基于代码审查,所有持有运行时状态的组件必须注册为独立容器组件(hot_reloadable=False),不参与不必要的级联重建:

| 组件 | 持有的状态 | 持久化 | 热重载处理 |
|------|----------|--------|----------|
| SessionManager | 会话 ID、标题、状态 | 会话内存 | 独立注册,不随 orchestrator 重建(Q5) |
| SkillManager | 技能激活状态 | 内存 | 独立注册(Q5) |
| CronIsolator | cron 上下文 | 内存 | 独立注册(Q5) |
| SignalPool | pending 信号 | JSON ✅ | 独立注册,重建时 _load() 加载(Q4 修正) |
| **CronScheduler** | _schedules、_stop_event、_last_triggered_minute、正在执行的 cron 任务 | YAML ✅(调度项) | 独立注册,**不参与任何级联重建**;运行时状态不可恢复,重建会中断正在执行的 cron 任务 |
| **TodoListRegistry** | _todos(session→TodoList) | 磁盘 ✅ | 独立注册,重建时从磁盘恢复 |
| **ApprovalStore** | pending 审批 | 内存 | 独立注册,PolicyEngine 通过 c.get() 获取同一实例 |
| **MCP Manager** | MCP 服务器连接池 | 内存 | 独立注册,orchestrator 通过 c.get() 获取同一实例 |
| **GuardrailEngine** | enabled flags | 内存 | 独立注册,enabled flags 已有 setter 支持热更新;规则变更需重建 |
| HistoryBuffer | 消息缓冲 | 内存 | 存储路径热重载时重建,但需先 flush 到磁盘 |
| HealthChecker | 无运行时状态 | N/A | 不注册为容器组件,每次 /health 请求时从容器获取当前组件引用 |

**CronScheduler 特殊保护:**
- 独立注册,deps=[](不依赖 chroma_store,通过 orchestrator 间接访问)
- 存储路径热重载时**不在级联链中**(_topo_sort_dependents 不会包含它)
- 安全权限热重载时:PolicyEngine 依赖 cron_scheduler,但 cron_scheduler 不重建(仅 policy_engine + orchestrator 重建)

**PolicyEngine 依赖修正:**
- PolicyEngine.__init__ 接收 cron_scheduler 参数(_check_cron_grant 方法依赖)
- deps: ["cron_scheduler"](单向依赖,policy_engine 重建时 cron_scheduler 不重建)

### 4.9 ComponentRef:不参与级联重建的组件访问可重建组件

不参与级联重建的组件(CronScheduler、HealthChecker、TodoListRegistry 等)需要在运行时访问可重建组件(orchestrator、llm_client 等)。使用代理引用模式,保持 DI 纯粹性:

```python
class ComponentRef:
    """代理对象:__getattr__ 转发到容器中最新的组件实例。
    用于不参与级联重建的组件访问可重建组件,避免引用过期。"""

    def __init__(self, container, name: str):
        self._container = container
        self._name = name

    def __getattr__(self, attr):
        return getattr(self._container.get(self._name), attr)
```

使用场景:

| 持有者(不重建) | 通过 ComponentRef 访问(可重建) | 调用场景 |
|----------------|-------------------------------|---------|
| CronScheduler | orchestrator_ref | _trigger() 调用 orchestrator.chat() |
| HealthChecker | orchestrator_ref、llm_client_ref、chroma_store_ref | /health 请求时检查各组件状态 |
| TodoListRegistry | orchestrator_ref | 续接 TODO 上下文注入 |
| 未来扩展组件 | 任何可重建组件 | 按需 |

注册方式:
```python
# 不参与级联重建的组件,注入 ComponentRef 而非直接引用
container.register("cron_scheduler",
    factory=lambda c: CronScheduler(
        orchestrator_ref=ComponentRef(c, "orchestrator"),
        ...
    ),
    deps=[],  # 不依赖 orchestrator(通过 ComponentRef 延迟获取)
    hot_reloadable=False,
)
```

核心原则:
- 不可重建依赖 → 构造时直接注入(c.get("xxx"))
- 可重建依赖 → 构造时注入 ComponentRef(c, "xxx"),运行时延迟获取

### 4.5 并发安全策略

| 场景 | 处理方式 |
|------|----------|
| 热重载期间新请求到达 | RLock 保护,新请求获取重建后的新实例 |
| 正在处理的旧请求 | 持有旧实例引用(Python 引用计数),动态 grace period 内旧实例资源不释放 |
| factory 内部获取依赖 | RLock 可重入,不会死锁 |
| 旧实例 close() 时机 | 延迟动态 grace period(llm.timeout × max_loops,可显式覆盖)后执行,确保流式请求完成;超时后强制关闭资源 |
| 旧实例 close() 失败 | 守护线程执行,失败仅记日志 |

### 4.6 组件接口约定

可热重载组件必须实现:
- `__init__(self, config, ...)` — 从配置创建实例
- `close(self)` — 释放资源(关闭连接、停止线程、flush 数据)

## 8. 热重载具体流程

### 8.0 配置变更检测

PUT /config 端点在写盘前保存旧 config,写盘后深度比较顶层段,计算 changed_sections:

```python
def _detect_changed_sections(old: dict, new: dict) -> set[str]:
    """比较新旧 config 的顶层段,返回变更的段名集合。"""
    changed = set()
    for key in set(old) | set(new):
        if json.dumps(old.get(key), sort_keys=True) != json.dumps(new.get(key), sort_keys=True):
            changed.add(key)
    return changed
```

完整 PUT /config 流程:

```
PUT /config (new_config)
  ├─ 1. Schema 校验(失败 → 400,不写盘)
  ├─ 2. 保存旧 config 引用(old_config)
  ├─ 3. 备份 config.yaml → config.yaml.bak
  ├─ 4. 敏感字段分离:
  │    ├─ 非敏感字段 → 写入 config.yaml(保持 ${ENV_VAR} 占位符)
  │    └─ 敏感字段 → 实际值写入 .env 文件,config.yaml 中保持 ${ENV_VAR} 占位符
  ├─ 5. 重新加载 config.yaml + 解析 ENV_VAR(resolved_config)
  ├─ 6. changed = _detect_changed_sections(old_config, resolved_config)
  ├─ 7. 需重建组件 = changed 中映射到 CONFIG_TO_COMPONENTS 的组件
  ├─ 8. container.reload(changed, resolved_config)
  │    ├─ 成功 → 200, reloaded=[...], needs_restart=(server段变更)
  │    └─ 失败 → 500, ConfigReloadError(见第 4.7 节回滚策略)
  └─ 9. 响应
```

敏感字段处理(防止 API Key 硬编码到 config.yaml):

```python
# config_schema.py — 标记敏感字段及其 ENV_VAR 名称
SENSITIVE_FIELDS = {
    "llm.api_key": "LLM_API_KEY",
    "llm.api_secret": "LLM_API_SECRET",
}

# PUT /config 写盘逻辑
def _write_config(new_config: dict, config_path: Path, env_path: Path):
    """非敏感字段写 config.yaml,敏感字段实际值写 .env,config.yaml 保持占位符。"""
    config_to_write = deepcopy(new_config)
    env_updates = {}

    for field_path, env_var in SENSITIVE_FIELDS.items():
        actual_value = _get_nested(config_to_write, field_path)
        if actual_value and not actual_value.startswith("${"):
            # 用户通过前端输入了实际值 → 写入 .env,config.yaml 用占位符
            env_updates[env_var] = actual_value
            _set_nested(config_to_write, field_path, f"${{{env_var}}}")

    # 写 .env(追加或覆盖对应行)
    _update_env_file(env_path, env_updates)
    # 写 config.yaml(原子写,含占位符)
    _atomic_write(config_path, config_to_write)
```

原则:
- config.yaml 永远不含实际密钥,只有 ${ENV_VAR} 占位符
- .env 文件管理实际密钥(.gitignore 已排除)
- 用户通过前端修改 API Key → .env 更新 → 热重载生效,无需重启

变更检测粒度:顶层段(llm/security/storage/memory/tasks/guardrails/server)。顶层段的任何子值变更都标记该段为 changed。memory/tasks/guardrails 段在 CONFIG_TO_COMPONENTS 中映射为空([]),只做属性级热更新不触发重建。

### 8.1 LLM 热重载

触发:config.yaml 中 llm 段变更(provider/model/api_key/base_url/timeout)

1. PUT /config 写盘 + 校验
2. 容器映射: {"llm"} → ["llm_client"]
3. 拓扑排序级联: llm_client → orchestrator
4. 重建 llm_client(创建新 AsyncOpenAI/AsyncAnthropic + 新 HTTP 连接池)
5. 重建 orchestrator(注入新 llm_client,其他依赖不变)
6. 旧 llm_client 延迟动态 grace period 后 close()(等待流式请求完成)

边界处理:
- 正在进行的流式聊天 → 旧 Orchestrator 继续处理,grace period 内旧 llm_client 连接池仍可用
- 新聊天请求 → 获取新 Orchestrator(新 llm_client)
- grace period = max(config.server.hot_reload_grace_period, config.llm.timeout * config.tools.max_loops)

### 8.2 安全权限热重载

触发:config.yaml 中 security 段变更(rules/enabled/timeout)

1. 容器映射: {"security"} → ["policy_engine"]
2. 拓扑排序: policy_engine → orchestrator
3. 重建 PolicyEngine(重新加载 rules、重建黑/白名单)
4. 重建 orchestrator(注入新 policy_engine)
5. 旧 policy_engine 无状态资源,延迟动态 grace period 后无操作(无 close 需要)

改进:当前 rules/enabled 变更需重启,新架构下可热重载。

### 8.3 存储路径热重载(最复杂)

触发:config.yaml 中 storage 段变更

1. 容器映射: {"storage"} → ["chroma_store", "sqlite_log", "history_buffer"]
2. 拓扑排序级联(基于实际依赖图):
   - chroma_store → consolidation_engine → signal_pool → orchestrator
   - chroma_store → retrieval → orchestrator
   - sqlite_log → metrics_store
   - history_buffer → orchestrator, context_manager
3. 重建顺序: [底层存储] → [中间层(consolidation/retrieval)] → [signal_pool] → [orchestrator]
4. 旧存储延迟动态 grace period 后 close()(flush + 关闭连接)

signal_pool 重建安全性:
- SignalPool 有 JSON 持久化(`data/profile_signal_pool.json`,debounce 1 秒写入),重建时 `_load()` 加载 pending 信号
- **pool_path 不变时**:重建不丢失数据(从原 JSON 文件加载)
- **pool_path 变更时(data 目录迁移)**:新路径下无 JSON 文件 → 空池启动 → 丢失 pending 信号
- 处理:存储路径热重载时,自动复制 `profile_signal_pool.json` 和 `memory.md` 到新 data 目录

数据迁移策略:
- 新路径不存在 → 创建空库,旧数据保留在原位置
- 新路径已有数据 → 直接打开使用
- 不做自动数据迁移(chroma/sqlite 数据不迁移,仅迁移 signal_pool JSON 和 memory.md)

UX 保护:前端修改存储路径时弹窗提示。

| server.host | 同上 | 同上 |
