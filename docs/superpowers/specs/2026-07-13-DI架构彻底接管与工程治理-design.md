# DI 架构彻底接管与工程治理设计

> **日期**：2026-07-13
> **状态**：设计阶段
> **目标**：让 DI 容器真正承担依赖注入职责，彻底解决三重状态存储、工厂路径错误、导入样板三大系统诟病，达成"可扩展、易管理、干净简洁"的架构目标。

---

## 一、背景与动机

### 1.1 深度审查发现的致命问题

经 2026-07-13 架构深度审查，发现当前系统存在三层诟病：

**P0 致命（架构正确性）**：
1. **DI 容器名存实亡**：[container.py](file:///e:/Java/webser/web_app/webme/hermes-lite/src/container.py) 设计优秀（DFS 环检测、原子重建、延迟关闭），但全项目仅 1 处通过容器取组件（`routes/config.py` 热重载）。路由实际走 `sys.modules.get("src.server")` 反射 + server.py 全局变量 + state.py PEP 562 代理。
2. **10 个工厂导入路径错误**：[app.py](file:///e:/Java/webser/web_app/webme/hermes-lite/src/app.py) 的 `_create_*` 工厂使用错误路径（如 `monitoring.session_logger` 实际应为 `storage.sqlite_log`，`agent.stream_manager` 实际应为 `stream_manager`）。当前能运行只因 `inject_lifespan_instances` 用 `set_instance` 绕过工厂；**首次热重载即静默用 None 替换正在运行的组件**。
3. **三重状态存储**：同一组件存于 server.py 全局变量 + state.py 代理 + container._instances 三处。[lifespan.py:717-797](file:///e:/Java/webser/web_app/webme/hermes-lite/src/lifespan.py#L717-L797) 把同一批组件同步到三处，热重载时可能不一致。

**P1 重要（冗余与技术债）**：
4. **51 处双重 try/except 导入样板**：28 个文件出现 `try: from .x import Y / except: from x import Y` 样板。根因：同时支持 `python src/server.py`（直接运行）和 `uvicorn src.server:app`（包导入）。
5. **lifespan 与 app.py 工厂逻辑重复**：lifespan.py 796 行手工创建所有组件，app.py 的 `_create_*` 工厂只在热重载时调用，两套创建逻辑必须手动同步，已出现路径漂移。
6. **根目录散落 19 个调试脚本 + 52K 文件备份目录**：工程卫生问题。

### 1.2 已确认的核心决策

经 brainstorming 澄清，确认 5 个核心决策：

| 决策项 | 选择 |
|--------|------|
| DI 接管深度 | **彻底接管** — 删除 server.py 全局变量、state.py 代理、sys.modules 反射 |
| 工厂逻辑统一 | **工厂唯一源** — app.py `_create_*` 修复路径，lifespan 调 `container.get()` |
| 路由访问方式 | **FastAPI Depends** — 11 个路由用 `Depends(get_xxx)` 注入组件 |
| 导入样板根治 | **统一包入口** — `python -m hermes`，删除 51 处 try/except 样板 |
| 实施策略 | **分 3 阶段提交** — 每阶段可独立验证，回滚风险低 |

### 1.3 架构合理性评估结论

**骨架合理，血肉未成形。** 模块划分、错误体系、Container 设计、Orchestrator 装配模式均合理；但 DI 实际未接入、状态三重冗余、工厂路径错误、导入样板泛滥。当前不是"架构设计不合理"，而是"架构设计合理但未落地"。

修复后架构将达到：单一真相源（Container）、工厂唯一源（app.py）、类型安全注入（FastAPI Depends）、样板清零（统一包入口）。

### 2.3 已知妥协（非本次范围）

1. **Orchestrator 整体注册**：内部子组件（LLMClient/ReactLoop/ToolRegistry）不单独进容器。热重载时整个 Orchestrator 重建（1-2 秒延迟）。这是 project_memory 中已明确的决策，可接受。
2. **工厂带 try/except 降级**：`_create_*` 内 `except Exception: return None` 保留，用于可选组件（MCP/Skill）缺失时降级。
3. **跨设备路径处理**：Tauri sidecar 的 `HERMES_ROOT` 环境变量定位资源，桌面端 vs 服务端路径差异，属部署问题非架构问题。

#### 4.2.3 修改 lifespan.py：从 796 行降至 ~150 行

**删除**：所有手工 `new` 创建逻辑（SessionLogger、MetricsCollector、AuditLogger、ApprovalManager、TaskManager、Orchestrator、UploadManager、ETLEngine 等）。

**保留并改造**：
```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    config = load_config(CONFIG_PATH)
    container = init_container(config)
    register_components(container)

    # 触发工厂创建 + 异步预热
    orch = container.get("orchestrator")
    await _warmup_onnx(container)
    await _warmup_chromadb(orch)
    await _init_mcp_servers(container, config)
    _start_background_loops(container, app)
    _register_skill_tools(container)
    _register_cron_tools(container)
    _register_file_tools(container)

    yield

    # 关闭
    container.close()
```

**异步预热函数**（新增辅助函数）：
- `_warmup_onnx(container)` — ONNX 嵌入模型预加载
- `_warmup_chromadb(orch)` — ChromaDB 向量索引预热
- `_init_mcp_servers(container, config)` — MCP server 连接 + 工具注册
- `_start_background_loops(container, app)` — cleanup_loop / file_cleanup_loop / metrics_persist_loop
- `_register_skill_tools(container)` — Skill stub 注册 + 状态恢复
- `_register_cron_tools(container)` — cron 工具 + cron_tool_registry
- `_register_file_tools(container)` — file_tools 注册

#### 4.2.4 修改 app.py：添加 Depends 函数

在 [app.py](file:///e:/Java/webser/web_app/webme/hermes-lite/src/app.py) 添加 11 个依赖函数：

```python
from fastapi import Depends

def get_container_or_raise() -> Container:
    """获取已初始化的容器，未初始化时抛 RuntimeError。"""
    c = get_container()
    if c is None:
        raise RuntimeError("DI 容器未初始化")
    return c

def get_orchestrator(c: Container = Depends(get_container_or_raise)) -> Orchestrator:
    return c.get("orchestrator")

def get_session_logger(c: Container = Depends(get_container_or_raise)):
    return c.get("session_logger")

# ... 其余 9 个：metrics_collector / metrics_store / audit_logger /
#     approval_manager / task_manager / stream_manager / skill_loader /
#     mcp_manager / upload_manager / etl_engine / cron_scheduler /
#     proposal_store / health_checker
```

#### 4.2.5 改写 11 个 routes/*.py

每个路由文件：
1. 删除 `sys.modules.get("src.server")` 反射
2. 删除 `import state` 或 `from state import xxx`
3. 在 handler 签名添加 `Depends(get_xxx)`

示例（routes/chat.py）：
```python
# 修复前
@router.post("/chat")
async def chat(req: ChatRequest):

    orch = server_mod.orchestrator
    ...

# 修复后
from app import get_orchestrator

@router.post("/chat")
async def chat(req: ChatRequest, orch: Orchestrator = Depends(get_orchestrator)):
    ...
```

from hermes.app import app

## 八、实施约束

遵循 project_memory 中的工程约定：

1. **TDD 流程**：每个改动先写失败测试 → 验证失败 → 最小实现 → 验证通过 → 重构 → 提交
2. **没有失败测试就不写生产代码**

5. **几乎所有配置段变更都会重建 Orchestrator**（1-2 秒延迟可接受）
6. **容器注册阶段应在路由拆分阶段之前执行**
7. **配置段到组件的映射**保持不变（见 container.py CONFIG_TO_COMPONENTS）
