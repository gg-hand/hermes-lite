## 一、背景与动机

### 1.1 深度审查发现的致命问题

经 2026-07-13 架构深度审查 + grill-me 质询验证，发现当前系统存在四层诟病：

**P0 致命（架构正确性）**：
1. **DI 容器名存实亡**：[container.py](file:///e:/Java/webser/web_app/webme/hermes-lite/src/container.py) 设计优秀（DFS 环检测、原子重建、延迟关闭），但全项目仅 1 处通过容器取组件（`routes/config.py` 热重载）。路由实际走 `import state`（**89 处，分布在 11 个路由文件**）+ server.py 全局变量 + state.py PEP 562 代理。
2. **10 个工厂导入路径错误**：[app.py](file:///e:/Java/webser/web_app/webme/hermes-lite/src/app.py) 的 `_create_*` 工厂使用错误路径（如 `monitoring.session_logger` 实际应为 `storage.sqlite_log`，`agent.stream_manager` 实际应为 `stream_manager`）。当前能运行只因 `inject_lifespan_instances` 用 `set_instance` 绕过工厂；**首次热重载即静默用 None 替换正在运行的组件**。
3. **三重状态存储**：同一组件存于 server.py 全局变量（10 个）+ state.py 代理（16 个属性）+ container._instances 三处。[lifespan.py:717-797](file:///e:/Java/webser/web_app/webme/hermes-lite/src/lifespan.py#L717-L797) 把同一批组件同步到三处，热重载时可能不一致。
4. **有状态后台 task 管理缺失**：4 个 asyncio 后台 task 持有组件引用，reload 不取消也不重启它们：
   - `cron_task = asyncio.create_task(cron_scheduler.run_loop(orchestrator))` — 持有 Orchestrator
   - `metrics_persist_task` — 持有 metrics_collector / metrics_store
   - `cleanup_task` / `file_cleanup_task` — 持有 session_logger
   
   reload 后旧 task 继续用旧实例运行，新实例无 task 服务 → **热重载后调度失效、监控失效**。
5. **`hot_reloadable` 是死代码**：[container.py:63,75](file:///e:/Java/webser/web_app/webme/hermes-lite/src/container.py#L63) 存储了 `_hot_reloadable` 字段，但 `reload` 方法（[container.py:128-175](file:///e:/Java/webser/web_app/webme/hermes-lite/src/container.py#L128-L175)）**从未读取此字段**。设计者本意是让 `hot_reloadable=False` 的组件（Orchestrator/CronScheduler/StreamManager）不参与热重载，但实现缺失。

**P1 重要（冗余与技术债）**：
6. **51 处双重 try/except 导入样板**：28 个文件出现 `try: from .x import Y / except: from x import Y` 样板。根因：同时支持 `python src/server.py`（直接运行）和 `uvicorn src.server:app`（包导入）。
7. **lifespan 与 app.py 工厂逻辑重复**：lifespan.py 796 行手工创建所有组件，app.py 的 `_create_*` 工厂只在热重载时调用，两套创建逻辑必须手动同步，已出现路径漂移。
8. **软重启绕过容器 + 依赖 state**：[routes/misc.py:256-336](file:///e:/Java/webser/web_app/webme/hermes-lite/src/routes/misc.py#L256-L336) 的 `/restart` 端点直接 `new Orchestrator()` 绕过容器，并通过 `state.soft_restart_in_progress` / `_sync_to_server_globals()` 依赖三重状态。
9. **background_loops 依赖 state**：[background_loops.py:222](file:///e:/Java/webser/web_app/webme/hermes-lite/src/background_loops.py#L222) `import state as _state_check` 读取 `metrics_baseline_reset` 标志。
10. **根目录散落 19 个调试脚本 + 52K 文件备份目录**：工程卫生问题。

### 1.2 已确认的核心决策

经 brainstorming + grill-me 两轮质询验证，确认 7 个核心决策：

| 决策项 | 选择 | 理由 |
|--------|------|------|
| DI 接管深度 | **彻底接管** | 删除 server.py 全局变量、state.py 代理、sys.modules 反射，Container 成为唯一真相源 |
| 工厂逻辑统一 | **工厂唯一源** | app.py `_create_*` 修复路径，lifespan 调 `container.get()` |
| 路由访问方式 | **统一 FastAPI Depends** | 89 处 `import state` 全部改为 `Depends(get_xxx)`，不搞混合模式（保证一致性） |
| 测试访问方式 | **统一 dependency_overrides + TestClient** | 49 处 `patch("src.server.xxx")` 全部改为 `app.dependency_overrides[get_xxx]` |
| 有状态 task 管理 | **修复 hot_reloadable + 后台 task 注册** | reload 跳过 `hot_reloadable=False` 组件；软重启手动重建有状态组件并重启 task |
| 软重启改造 | **保留独立逻辑但改用容器** | 软重启不复用 reload（reload 级联重建 + 不支持异步预热），改用 `container.get()` + `set_instance()` |
| 导入样板根治 | **统一包入口** | `python -m hermes`，删除 51 处 try/except 样板 |

### 1.3 架构合理性评估结论

**骨架合理，血肉未成形。** 模块划分、错误体系、Container 设计、Orchestrator 装配模式均合理；但 DI 实际未接入、状态三重冗余、工厂路径错误、有状态 task 管理缺失、导入样板泛滥。当前不是"架构设计不合理"，而是"架构设计合理但未落地"。

修复后架构将达到：单一真相源（Container）、工厂唯一源（app.py）、类型安全注入（FastAPI Depends）、有状态 task 可控重建、样板清零（统一包入口）。

### 2.4 已知妥协

1. **Orchestrator 整体注册**：内部子组件（LLMClient/ReactLoop/ToolRegistry）不单独进容器。热重载时整个 Orchestrator 重建（1-2 秒延迟）。这是 project_memory 中已明确的决策，可接受。
2. **工厂带 try/except 降级**：`_create_*` 内 `except Exception: return None` 保留，用于可选组件（MCP/Skill）缺失时降级。
3. **metrics_persist_task 跨 reload 持有旧实例**：metrics_collector 是 `hot_reloadable=True`，reload 会重建它，但旧 task 持有旧引用。需在 reload 后重启 task（见 4.3 节方案）。
4. **跨设备路径处理**：Tauri sidecar 的 `HERMES_ROOT` 环境变量定位资源，桌面端 vs 服务端路径差异，属部署问题非架构问题。

```python
def reload(self, changed_sections: set[str], new_config: dict) -> list[str]:
    """原子性重建:先创建全部新实例,全部成功后才替换,失败则回滚。
    
    hot_reloadable=False 的组件不参与重建（由软重启手动处理）。
    """
    with self._lock:
        directly_affected = set()
        for section in changed_sections:
            directly_affected.update(CONFIG_TO_COMPONENTS.get(section, []))

        # 过滤掉 hot_reloadable=False 的组件
        reloadable_affected = {
            name for name in directly_affected
            if self._hot_reloadable.get(name, True)
        }

        to_rebuild = self._topo_sort_dependents(reloadable_affected)
        # ... 后续逻辑不变
```

**保留并改造**：
```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    config = load_config(CONFIG_PATH)
    container = init_container(config)
    register_components(container)

    # 触发工厂创建（无状态组件）
    session_logger = container.get("session_logger")
    metrics_collector = container.get("metrics_collector")
    # ... 其余无状态组件

    # 触发工厂创建（有状态组件）
    orch = container.get("orchestrator")
    cron_scheduler = container.get("cron_scheduler")
    stream_manager = container.get("stream_manager")

    # 异步预热（业务逻辑，留在 lifespan）
    await _warmup_onnx(container)
    await _warmup_chromadb(orch)
    await _init_mcp_servers(container, config)
    _register_skill_tools(container)
    _register_cron_tools(container)
    _register_file_tools(container)

    # 启动后台 task（注册到 registry 便于软重启重启）
    task_registry = BackgroundTaskRegistry()
    task_registry.register("metrics_persist", asyncio.create_task(metrics_persist_loop(...)))
    task_registry.register("cleanup", asyncio.create_task(cleanup_loop(...)))
    task_registry.register("file_cleanup", asyncio.create_task(file_cleanup_loop(...)))
    task_registry.register("cron", asyncio.create_task(cron_scheduler.run_loop(orch)))
    app.state.task_registry = task_registry

    yield

    # 关闭
    await task_registry.cancel_all()
    container.close()
```

#### 4.2.4 新增 BackgroundTaskRegistry

新增 `src/background_task_registry.py`：

```python
import asyncio
import logging
from typing import Dict, Optional

logger = logging.getLogger(__name__)


class BackgroundTaskRegistry:
    """后台 asyncio task 注册表，支持按名取消和重启。
    
    用于解决 reload/软重启 后台 task 持有旧组件引用的问题。
    """
    
    def __init__(self):
        self._tasks: Dict[str, asyncio.Task] = {}
    
    def register(self, name: str, task: asyncio.Task) -> None:
        """注册后台 task。若同名 task 已存在，先取消旧的。"""
        old = self._tasks.get(name)
        if old is not None and not old.done():
            old.cancel()
        self._tasks[name] = task
    
    def get(self, name: str) -> Optional[asyncio.Task]:
        return self._tasks.get(name)
    
    async def restart(self, name: str, factory) -> None:
        """重启指定 task：取消旧的，用 factory 创建新的。
        
        factory 是无参 callable，返回新 coroutine 或 task。
        """
        old = self._tasks.get(name)
        if old is not None and not old.done():
            old.cancel()
            try:
                await asyncio.wait_for(old, timeout=5.0)
            except (asyncio.TimeoutError, asyncio.CancelledError):
                pass
        
        new_task = asyncio.create_task(factory())
        self._tasks[name] = new_task
        logger.info("后台 task '%s' 已重启", name)
    
    async def cancel_all(self) -> None:
        """取消所有后台 task（用于关闭）。"""
        for name, task in self._tasks.items():
            if not task.done():
                task.cancel()
                try:
                    await asyncio.wait_for(task, timeout=5.0)
                except (asyncio.TimeoutError, asyncio.CancelledError):
                    pass
        self._tasks.clear()
```

### 9.3 架构特性

- **可扩展**：新组件只需 `container.register()` + 一个工厂函数 + 一个 `Depends` 函数
- **易管理**：单一真相源，状态一致性有保障
- **干净简洁**：lifespan 从 796 行降到 200 行，51 处样板清零
- **符合 DI**：容器真正承担依赖注入，不再是"挂名"
- **类型安全**：FastAPI Depends 提供完整类型提示和 IDE 补全
- **可测试**：`app.dependency_overrides` 支持测试 mock 注入
- **有状态可控**：`hot_reloadable=False` 过滤 + `BackgroundTaskRegistry` 重启，热重载后 task 不失效
- **软重启可控**：通过 `container.set_instance()` + `task_registry.restart()`，软重启复用容器基础设施
