# P2 立项评估：storage-stdio 批量消息写（log_messages）+ 代理双档聚合

> 日期：2026-09-09 → 2026-09-10。状态：评估完成，立项收敛（见 §5 结论）。
> 关联：`docs/plans/2026-09-10-扩展通道性能优化-执行计划.md`（P0/P1 已落地并提交 b1a5337，本评估是其"基线数据 → P2 决策"的后续）、`teage_liu2/PROTOCOL/PENDING.md`（P-7 登记处）。

## 1. 评估动机与数据基线

P0/P1 落地后实测（200 次/操作）：单条写经 stdio 通道 2.53ms（进程内 1.20ms，IPC 税 ~1.3ms）。本轮补测**成本构成**（N=300，同库同 schema）：

| 项 | 实测 | 结论 |
|---|---|---|
| (a) 逐条 log_message（每条一个事务提交） | 均值 1.491ms/条（p50 1.381） | 现状 |
| (b) 批量单事务（同事务 N 条 INSERT + 1 commit） | 0.029ms/条 | 上限 |
| **事务提交开销** | **1.463ms/条（占单条成本 98%）** | **结构性优化点** |

结论：单条写成本 ≈ 1.46ms 提交 + 0.03ms 插入 + 1.3ms IPC 帧。**合帧 + 合事务**同时消除两类大头，收益是乘法关系而非加法。

## 2. 收益量化（诚实口径）

**当前每轮对话写入面**（e2e 实测）：2 条 log_message + 3 次 doc write ≈ 5 帧 5 事务，后台线程耗时 ~11ms。

| 场景 | 现状 | 批量后 | 收益 |
|---|---|---|---|
| 每轮后台写耗时（写线程内） | ~11ms | ~6ms（2-3 帧 2-3 事务） | ~-45% |
| 每轮 SQLite 事务数（磁盘 IO） | 5 | 2 | -60% |
| 高频写入（多智能体/事件风暴，N 条/窗口） | N 帧 N 事务 | 1-2 帧 1 事务 | 近线性放大 |
| **主对话关键路径延迟** | 写路径本经 StorageWriter 异步 | 不变 | **0**（诚实声明） |

价值定位：不是让单轮对话更快，而是**写吞吐的结构性余量**（事务数减半 → 背压阈值余量、多扩展并发落盘不互相拖累）——与用户"架构本身"的定位一致。

## 3. 关键设计约束（评估中发现的契约雷区）

**断连不丢契约 vs 朴素缓冲不兼容**：`StorageWriter.enqueue_flush` 的 Future 在 `fn()` 返回时 resolve——若代理层无条件缓冲，user 前置落盘会在**未提交时就返回成功**，"断连不丢输入"契约被静默破坏。

因此**档位信息必须从调用侧带入**，收敛为双档设计：

```
pipeline._persist
  ├─ flush=True  → store.log_message(...)          （直发,现状不变,保契约）
  └─ background  → store.log_message_buffered(...) （可选能力,缓冲待合帧）
```

- 代理（stdio-proxy）：`log_message` 保持直发；新增 `log_message_buffered` 进缓冲区，触发合帧条件 = ①任意 flush 档调用到达（先冲刷缓冲保序）②缓冲 ≥ 32 条 ③窗口定时器（~25ms 守护线程）④close
- 失败语义：批量帧失败（P-4 条款③批量原子性）→ 整批降级逐条重发（复用 background 重试）
- **core 改动面**：`pipeline._persist` background 路径 1-2 行 duck-typing（`getattr(store, "log_message_buffered", store.log_message)`），向后兼容（默认 SQLite 无此方法自动走原路径）——**这是 core 最小兼容改动，不是零改动**，须如实声明
- 崩溃丢失窗口：缓冲中未落盘的 background 消息 ≤ 窗口时长——现状崩溃时写队列里的任务同样会丢，风险**持平不放大**

## 4. P2 原范围两项的分拆裁决

| 项 | 裁决 | 依据 |
|---|---|---|
| 批量 log_message op + 双档聚合 | **立项 → P-7** | 提交开销占 98% 的硬数据；协议红线通过（现有 write op 只覆盖 doc_* 表，无法组合出消息批量写——升级成立） |
| 条款⑥放宽为流水线 | **不立项，降级观察** | 收益上限 = 每帧 0.5-1.3ms 的 RTT 重叠隐藏（后端本就串行执行，总执行时间不变）；代价 = 所有同步调用点改异步提交的重构 + 超时/背压语义重设计，收益/复杂度比差 |

## 5. 立项结论

- **P2 收敛为 P-7**：storage-stdio 批量消息写 op（`log_messages`）+ 宿主侧双档缓冲聚合器，已登记 `PROTOCOL/PENDING.md`（proposed）。
- **实施边界**：Rust 后端 dispatch +1 op（~60 行，循环复用既有 insert 逻辑 + 单事务）；proxy 聚合器（~80 行）；pipeline._persist 兼容分支（~2 行）；行为套件用例 + e2e。
- **预期验收锚点**：`/health` storage_metrics 出现 `log_messages` op 且 `log_message.count` 相应下降；行为套件 17/17 不回归；断连不丢契约由既有 e2e 场景覆盖。
- **明确不做**：条款⑥流水线；doc write 聚合（write 已支持数组，调用侧天然批量时已受益，暂无实测瓶颈）。
