## 1. 结论速览

| 维度 | 结论 |
|---|---|
| 总体判断 | **core 不是延迟瓶颈**。单轮（一次 LLM 调用）core 侧 CPU 合计 **亚毫秒～数毫秒**；LLM 网络 IO（秒级）与跨进程存储 IPC 高出行星级。 |
| 事件循环阻塞 | **未发现同步 IO 落在事件循环**：core 内 `sqlite3` 仅存在于 `history.py` / `storage.py`，全部经 `asyncio.to_thread`（读）或 `StorageWriter` 专用写线程（写）；`config.py` 的文件读写只在启动/`PUT /config` 冷路径。✅ |
| 落盘成本 | 默认 SQLite 单条写 **1.2 ms 中位**（1 KiB 内容），**事务提交主导**（与 P-7 实测 1.46 ms 互相印证）；已完全移出事件循环。 |
| 唯一逐 token 成本 | `llm._with_activity_timeout` 用 `asyncio.wait_for` 包**每个 chunk**：**≈9.5 µs/chunk**（8000 chunk 额外 77 ms）。可优化，但相对秒级 LLM 延迟不构成瓶颈。 |
| 事件循环内 JSON 序列化 | 两处**全量序列化跑在事件循环里**：快照预算（0.61 MiB → 3.4 ms/批）、入站帧边界校验（≈4.4 ms/MiB）。配置上限（快照 2 MiB / 帧 4 MiB）封顶了最坏值，但最坏约 **10 ms / 18 ms** 停顿。 |
| 复杂度 | 一处 **O(轮数 × 消息数)** 结构：每轮对快照/消息列表做全量遍历。因 `history_window_messages` 默认 **100** 封顶，实测绝对值很小；仅当该配置被放大（上限 10000）才显形。 |
| 推荐动作 | 3 项 P1（低风险、收益明确）+ 4 项 P2（设计取舍，记录即可）。无 P0。 |

## 2. 热路径实测（本机 Windows / CPython 3.11）

### 2.1 每轮固定的 core 侧成本

| 环节（代码位置） | 实测 | 说明 |
|---|---|---|
| `hooks._call` 单次钩子调用（`hooks.py:222`） | **9.5 µs** | 含 `asyncio.wait_for` 建 Task + 定时器；10 枝干 × 4 钩子/轮 = 0.38 ms/轮 |
| `incremental_finalize`（`assembler.py:64`，每轮） | 0.014 ms @100 条 → **0.18 ms @1600 条** | 线性；远低于预期 |
| `_convert_messages`（`llm.py:618`，仅 OpenAI 兼容 provider，每次 LLM 调用） | 0.05 ms @100 → **0.98 ms @1600** | 三遍清洗 + 转换，线性 |
| `after_step_all` 含一次 action 落地（`hooks.py:401` → `snapshot.py:70`） | 0.27 ms @100 条 → **2.15 ms @1600 条** | 见 P2-1，成本来自快照预算全量 `json.dumps` |

结论：**默认窗口（100 条历史）下，每轮 core CPU 合计 < 1 ms**；`max_loops=50` 整场对话 core 侧累计 **约 20–50 ms**，相对 LLM 的秒级耗时（50 轮 ≈ 数十秒）可忽略。

### 2.2 逐 token 成本（流式）

| 实现 | 500 chunk | 2000 chunk | 8000 chunk |
|---|---|---|---|
| 原生 `async for` | 0.05 ms | 0.18 ms | 0.64 ms |
| `_with_activity_timeout` 包裹 | 4.37 ms | 19.40 ms | 76.96 ms |

**逐 chunk 额外 ≈ 9.5 µs**（`asyncio.wait_for` 每次调用构造 Task + TimerHandle + 取消机制）。一次 2000-token 流式回答 ≈ 19 ms 纯 CPU + 2000 个短命 Task。

事件透传链本身（`backend.chat_stream → 重试 wrapper_gen → chat_main_stream → step.execute → mode → _iter_events → pipeline.chat_stream`，6 层 `async yield` 逐层透传）经对比测算 **< 1 µs/chunk**，无需改（async generator 透传层是协议分层的正常代价）。

### 2.3 落盘成本（默认 SQLite 路径）

| 内容体积 | 含 FTS5/trigram（中位 / 最差） | 去掉 FTS 写入（中位 / 最差） |
|---|---|---|
| 1 KiB | **1.23 / 2.41 ms** | 1.17 / 1.93 ms |
| 10 KiB | 1.97 / 2.32 ms | 1.06 / 2.24 ms |
| 100 KiB | 3.06 / 17.36 ms | 1.98 / 9.60 ms |
| 500 KiB | **9.82 / 46.44 ms** | 3.04 / 14.87 ms |

- 1 KiB 即 1.2 ms ⇒ **固定成本（WAL 事务提交）主导**，与 `PENDING.md` P-7 记录（1.463/1.491 ms，提交占 98%）完全一致；
- FTS5 `trigram` 全文索引随内容线性放大：500 KiB 时把写成本从 3.0 ms 抬到 9.8 ms（×3.3）；
- 这些耗时**全部在 `StorageWriter` 写线程内**，不占事件循环 ✅。

### 2.4 事件循环内的序列化停顿

| 场景 | 实测 |
|---|---|
| `check_frame_limits`（`transport.py:180`，每次 `TransportFrame.decode`） | 0.13 MiB → 0.54 ms；0.64 MiB → 2.84 ms；1.27 MiB → **5.61 ms**（≈**4.4 ms/MiB**） |
| `_check_snapshot_budget`（`snapshot.py:59`） | 0.61 MiB 快照 → **3.41 ms/批** |
| 同上，按配置上限外推 | 快照 2 MiB ≈ **10 ms**；帧 4 MiB ≈ **18 ms** |

两者都在 `async def` 调用链内同步执行，属**事件循环停顿**（不是阻塞 IO，但同样占住 loop）。

## 3. 问题清单

### P1-1 逐 chunk `asyncio.wait_for`：流式响应白缴 10–80 ms CPU

- 位置：`teage_liu2/core/llm.py:84-109`（`_with_activity_timeout`），消费方 `llm.py:402`（Anthropic）/ `llm.py:862`（OpenAI 兼容）。
- 事实：语义需求是"**相邻 token 之间**最多等 `timeout_sec`"，当前用 `asyncio.wait_for(ait.__anext__(), timeout)` 逐次实现 ⇒ 每 chunk 一次 Task/定时器构造与销毁。
- 影响：2000 chunk ≈ 20 ms、8000 chunk ≈ 77 ms 纯 CPU；另产生 2000–8000 个短命 Task 的分配/回收压力。相对秒级 LLM 延迟不致命，但属"**纯浪费**"。
- 建议（保语义前提下）：改为**单定时器空闲检测**——维护一个 `loop.call_later` 定时器，收到 chunk 即重置、到期才 `raise ActivityTimeout`；或退一步用 `asyncio.timeout()` 上下文（仍逐次、但比 `wait_for` 少一层 Task 封装）。**必须保留**：超时触发 `on_timeout`（关流）后抛出 `ActivityTimeout`，且 `ActivityTimeout` 不可重试（`llm.py:76`）语义不变。
- 风险：低；但需以现有 LLM 超时用例 + 人为挂起注入驱动验证（`ActivityTimeout` / `StreamCancelled` 路径）。

### P1-2 `L3BatchSink` 全局缓冲用 `list.pop(0)`（O(n)）

- 位置：`teage_liu2/core/event_stream.py:202-205`。
- 事实：缓冲满（`buffer_max = 1024`）时每来一个事件做一次 1024 元素搬移 ⇒ 观测者持续受阻时退化为 **O(n²)**。同文件的 `L3ObserverQueue` 已用 `deque`（`event_stream.py:125`），此处不一致。
- 影响：仅"观测旁路被拖住 + 事件风暴"时触发；L3 是 best-effort，影响面小，但修复成本近乎为零。
- 建议：`self._buffer` 改 `collections.deque`，`pop(0) → popleft()`（`event_stream.py:230` 的 `self._buffer = []` 同步改 `clear()`）。

### P1-3 入站帧体积被重复测量（每帧多一次全量 `json.dumps`）

- 位置：`teage_liu2/core/transport.py:314`（`decode` 内 `if len(line) > FRAME_MAX_BYTES`）与 `transport.py:331`（`check_frame_limits(obj)` 内部**再** `json.dumps` 求 size）。
- 事实：**同一入站帧被量了两次体积**——一次按原始行字符数、一次按重新序列化结果（≈4.2 ms/MiB）。**2026-09-10 复核更正**：205.9 KiB 帧实测 `json_depth` 0.954 ms + `json.dumps` 0.982 ms —— 二者**各占 ≈50%**（此前"`json_depth` 是无分配遍历，占比极小"的判断错误）；迭代版 `json_depth` 0.478 ms（快 ≈2×）。三处（去重复 dumps + 迭代 depth + 按线上字节计体积）合计可省 ≈75%。
- 影响：每个入站帧多一次全量 dumps，在事件循环内；stdio 扩展（`remote_adapter`）与存储代理的每次往返都命中。
- 建议：`decode` 路径以 `len(line)` 作体积依据（帧已在 `_read_loop` 按 `len(line_bytes)` 拒绝超长，`stdio.py:312`），`check_frame_limits` 保留给宿主**出站**/编程式调用（其契约不变）；若担心两条路径语义不同，可在 docstring 明确"wire 体积以原始行长为准"。
- 风险：低 —— 需确认既有边界用例（超限帧必须被拒）仍绿。

### P2-1 每轮对快照/消息列表的全量遍历（O(轮数 × 消息数)）

- 位置：`snapshot.py:139`（每批 action 后 `_check_snapshot_budget` 全量 `to_dict()` + `json.dumps`）、`loop.py:166/181/287/292`（每轮 3–4 次 `list(cur.messages)` 全量浅拷贝）、`assembler.py:80/103`（每轮两次全量遍历）。
- 事实：`snapshot.py:4-5` 的注释声称"结构共享 O(n) 浅拷贝，禁 deepcopy"，实际是**每轮重复 O(n)**——单轮 O(n)，整场 O(轮数 × n)。实测绝对值小（100 条历史下每轮 < 1 ms）。
- 建议（不紧急）：①快照预算改**增量字节记账**（append 时累加、set 类不累加），彻底去掉每批 `json.dumps`；②`loop` 维护单一 `msgs` 引用，仅在需要不可变快照时才 `list()`。建议**先记录**，等 `history_window_messages` 有放大需求的实测信号再动。

### P2-2 远程扩展每钩子全量快照 + 每帧多次编解码

- 位置：`remote_adapter.py:98-103`（每次 `_invoke` 都 `snapshot.to_dict()`，全量消息列表）、`transport.py:304-306`（`encode` 一次 dumps）、`decode` 再一次 loads + 一次 dumps（P1-3）。
- 事实：一个实现 `before` + `after_step` 的 stdio 扩展，每轮 = **2 次全量快照序列化 + 2 次跨进程往返**；快照随对话线性增长。
- 定性：这是 `§18.2 分层实施` + delta 编码（`transport.py:367`，已定义未落地）**既定**的取舍，不是缺陷。建议在 P-2（异语言全链路验证）的验收数据里显式记录"每轮远端钩子数 × 快照体积"这一成本项，为 delta 落地提供触发依据。

### P2-3 单写队列的跨会话队首阻塞（设计取舍）

- 位置：`storage_writer.py:97/179`（全局单 `queue.Queue` + 单写线程）、`pipeline.py:459`（user 消息 `enqueue_flush` 等写线程 commit）。
- 事实：§18.1"全部 SQLite 写经写队列"是刻意的单写者设计；代价是**一条大 tool_result 写入（500 KiB 实测中位 9.8 ms / 最差 46 ms）会推迟其他会话 user 消息的 flush**。
- 定性：可接受（个人 Agent 场景、写入总量低）。建议保留 `dropped_count` / `queue_depth` 可观测（已具备，`storage_writer.py:134-147`），并在多智能体/事件风暴场景放大时再评估分片。

### P2-4 FTS5 trigram 对全部消息全文索引

- 位置：`history.py:250-254`（每条消息同步 `INSERT INTO messages_fts`），`history.py:151-181`（trigram 建表）。
- 事实：写入成本随内容线性放大（500 KiB：3.0 → 9.8 ms，×3.3），100 KiB 时最差 17 ms。
- 定性：trigram 是中文子串检索的正确选择（`history.py:154-157` 已论证）。若未来出现"超大工具结果拖慢落盘"，可选：**仅对 `message_type in (assistant, user)` 的纯文本入 FTS**，工具结果只留 `messages.content`（`search_messages` 已基于 `messages_fts`，条款可协商）。

### 附：无调用方的 token 估算接口

`llm.py:1163-1211` 的 `count_tokens` / `count_messages_tokens` 在 `teage_liu2/` 内**零调用方**（仅定义）。二者每次调用都 `import tiktoken` + `tiktoken.get_encoding("cl100k_base")`（库内 `lru_cache`，命中便宜）+ 逐段 `encode()`。**若将来接入 token 预算/裁剪热路径**，需先缓存 encoder 实例并避免逐块 `encode`（改为整段拼接后一次编码）。

## 4. 已验证的正常面（避免误判）

1. **无同步 IO 阻塞事件循环**：全仓 `teage_liu2/core/` 内同步 IO 仅 4 处 —— `history.py:99` / `storage.py:90` 的连接构造（装配期）、`config.py:271` 配置读取（启动/热重载）、`config.py:124/135/195` `.env` 写入（`PUT /config`）。请求路径上的 DB 读写分别经 `pipeline.py:147 asyncio.to_thread` 与 `storage_writer` 写线程。✅
2. **落盘不阻塞流式输出**：`pipeline._persist` 的 background 档走 `enqueue_background`（`pipeline.py:462`，入队即返），仅 user 前置档 `await`（`pipeline.py:459`，契约要求"断连不丢输入"）。✅
3. **SSE 不被落盘拖尾**：`done` 事件先 `yield` 给外壳，`after` / `on_error` 终态钩子在其后执行；`routes.py:95-98` 已刻意不提前关闭生成器（保审计扩展落盘）。代价是"done 后连接仍存活至终态钩子结束"——**尾延迟**属性，非缺陷，但 N 个枝干 × 5 s 钩子超时是 SSE 连接的最坏驻留上界。
4. **L1 热路径未被观测旁路污染**：`event_stream.route_l3` 仅做 `dict.get` + frozenset 判定（`event_stream.py:91-93`），无分配。✅

# 对比：原生 async for vs async for _ in _with_activity_timeout(gen, 60.0)

### 8.2 新增发现（本轮，原报告未列）

- **B1 落盘未设 `synchronous=NORMAL`（fsync 税）**：1 KiB 单条写 1.23 ms → `NORMAL` 0.10 ms（×12）；100 条积压 user flush 166.5 ms → 18.6 ms。`storage_writer.py:11-12` 的 docstring 已声明 NORMAL 语义，属"实现未兑现文档"。**处置：D-1 经用户裁决保持 FULL**（不启用 NORMAL，逐次 fsync 保全断电安全），docstring 改为如实描述，仅显式化 `busy_timeout=5000`。
- **A1 深嵌套帧 `RecursionError` 逃逸 → stdio 读循环终止（通道死亡）**：`json.loads(20000 层)` 抛 `RecursionError`；`decode` 只捕 `JSONDecodeError` → 逃到 `_read_loop` 的 `except Exception`（位于 `while` **之外**）→ 整循环退出。同理 `type` 字段不可哈希（`["x"] not in MESSAGE_TYPES`）抛 `TypeError` 亦逃逸。**已修**：迭代 `json_depth` + `RecursionError → ValueError` + 读循环逐帧容错。
- **A2 `L3BatchSink` 的"64 条先到触发"实际失效**：`_schedule_flush(immediate=True)` 在 `_flush_task` pending 时直接 return；`_timer` 的 `finally` 无条件置 None（可能清掉更新后的 task 引用）。**已修**：`_timer_task` 创建时登记 + 独立定时窗口引用 + 在途冲刷不取消。
