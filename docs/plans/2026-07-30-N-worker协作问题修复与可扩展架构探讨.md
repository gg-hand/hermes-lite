# N-Worker 协作问题修复与可扩展架构探讨

> 范围：从当前双 worker（teagent-lu / teagent-liu-2）推广到任意 N 个 worker 的横向扩展场景
> 目标：彻底解决当前观测到的 5 类问题，并为 N≥3 的扩展场景提供架构基础
> 立场：**优先接入已有基础设施**（election.py / watchdog_watcher.py / file_lock.py），而非重新发明

## 一、问题域重新定义：从"双 worker"到"N worker"

### 1.1 当前观测到的现象（双 worker）

| # | 现象 | 量化证据 |
|---|---|---|
| P1 | Agent 间交流延迟大 | director 广播 → worker 回复 = 39~73s |
| P2 | Director 心跳超时进入自治 | worker2 epoch=1，PID 6420 僵尸 |
| P3 | Trust_score 异常衰减 | 10 秒内 100→89，audit.jsonl 爆炸式增长 |
| P4 | A2A 启动重试浪费 30s | worker1→worker2 三次 10s timeout |
| P5 | 子进程僵尸持续持锁 | director.lock 被 portalocker.LOCK_EX 持有，无法重启 |

### 1.2 N-worker 视角下的问题推广

把"双 worker"视为 N=2 的特例，重新审视每个问题在 N 增大时的恶化趋势：

| 问题 | N=2 影响 | N=5 影响 | N=10 影响 |
|---|---|---|---|
| P1 交流延迟 | 39~73s | O(N) 级联 LLM 调用 → 5 分钟级 | 不可用 |
| P2 Director 心跳超时 | 单实例僵尸 | 同左，但单点故障影响所有 worker | 同左 |
| P3 Trust_score 衰减 | 单 agent 被砍 | 多 agent 同时被误判，雪崩 | 集群 trust 全 0 |
| P4 A2A 重试浪费 | 30s/对端 | 5 个对端 × 30s = 150s 启动延迟 | 300s 启动延迟 |
| P5 子进程僵尸 | 持 1 个锁 | 同左（每实例独立 director） | 同左 |

**关键洞察**：当前架构是"每个 worker 实例各自独立 director_engine 子进程 + 独立 blackboard"，N 增大时**独立 director 数量线性增长**，但**全局协调机制缺失**——这正是用户在上一轮反馈中点出的"不止双 worker，要求可以扩展"的核心矛盾。

### 1.3 N-worker 架构的关键问题域

| 维度 | 双 worker 当前实现 | N-worker 期望实现 |
|---|---|---|
| Director 数量 | 每实例一个独立子进程 | **集群唯一**（基于选举） |
| Blackboard | 每实例独立目录（`blackboard_a2a_X`） | 各实例本地协作视图 + 全局协调状态 |
| 消息广播 | director → call_all_endpoints → N 个对端 | 同左（已支持 N 端点） |
| 锁管理 | 进程内单例（file_lock.py 注释明确"不跨进程"） | **需引入跨进程锁** |
| Director 选举 | 代码已实现（election.py），但**未被调用** | 必须在心跳超时触发选举 |
| 文件监听 | 代码已实现（watchdog_watcher.py），但**callback 为空** | 必须接入协作消息推送 |

## 三、N-Worker 可扩展架构设计

### 3.1 核心设计原则

| 原则 | 含义 | 拒绝的反模式 |
|---|---|---|
| **D1 单一 Director 角色** | 集群内任意时刻只有一个 Director_engine 运行 | 每实例独立 director（当前实现） |
| **D2 Director 可迁移** | Director 可在任一 worker 实例上运行；宕机自动迁移 | Director 与某 worker 实例强绑定 |
| **D3 本地协作视图 + 全局协调状态** | 每个 worker 维护本地 collaboration.md（消息流），但 director.md / status.json 全局唯一 | 各实例独立 director.md（当前实现） |
| **D4 跨进程文件锁** | 所有跨进程共享文件（agent_card / director.md / status.json）写入前先获取锁 | 进程内 asyncio.Lock 不够（当前 file_lock.py） |
| **D5 事件驱动而非轮询** | 文件变更通过 watchdog 推送，worker 立即响应 | 2s 轮询（当前 _collab_poll_loop） |
| **D6 容错优先** | 单点故障不应导致集群不可用 | 子任务异常拖垮整个进程（当前 _run_loop） |

### 3.2 推荐架构：嵌入式 Director + 跨实例选举

```
┌─────────────────────────────────────────────────────────────────┐
│                       集群协调层（全局唯一）                       │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  Director_engine（仅在选举胜者实例上运行，作为内嵌协程）   │    │
│  │  - 写入共享 blackboard（共享目录或 A2A 同步）             │    │
│  │  - 监督所有 worker 心跳                                   │    │
│  │  - 调度 turn / 仲裁冲突                                   │    │
│  └─────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────┘
              ▲                          ▲
              │A2A: read_director_md     │A2A: read_director_md
              │                          │
┌─────────────┴──────────┐  ┌────────────┴──────────┐  ┌────────────────┐
│ Worker 1 (teagent-lu)   │  │ Worker 2 (teagent-liu-2)│  │ Worker N (...)  │
│  - 本地 collaboration.md │  │  - 本地 collaboration.md │  │  - 本地 collab  │
│  - 本地 agent_card       │  │  - 本地 agent_card       │  │  - 本地 card    │
│  - watchdog 监听协作消息 │  │  - watchdog 监听协作消息 │  │  - watchdog     │
│  - A2A gateway          │  │  - A2A gateway          │  │  - A2A gateway  │
│  - Election 抢占能力     │  │  - Election 抢占能力     │  │  - Election     │
└─────────────────────────┘  └─────────────────────────┘  └────────────────┘
```

#### 关键点

1. **Director 不再是子进程**：作为选举胜者实例的 asyncio 协程运行。消除僵尸子进程风险（D6）。
2. **Director 可迁移**：任一 worker 都有抢占能力，原 Director 心跳超时 → 触发 Election.run() → 新实例当选（D2）。
3. **共享 blackboard**：方案二选一
   - **方案 X**（推荐）：所有 worker 共享同一 `blackboard_dir`（NFS / SMB / 同机多端口），director.md / status.json / audit.jsonl 全局唯一，每实例仅本地 collaboration.md
   - **方案 Y**：每实例独立 blackboard，Director 通过 A2A 同步关键状态到所有实例
4. **跨进程文件锁**：agent_card.md / director.md / status.json 写入前必须获取 portalocker 文件锁（D4）。
5. **事件驱动协作**：watchdog_watcher.py 已实现，接入 `_collab_poll_loop` 即可（D5）。

### 3.3 选举算法详述（已有，需接入）

[election.py:1-14](file:///e:/Java/webser/web_app/webme/teage-liu/teage_liu/multiagent/election.py) 已定义：

```
1. 收集所有候选 Director 的 epoch（本地 + 远程端点）
2. 选择 epoch 最高的候选者
3. 若 epoch 相同，选择 agent_id 字典序更小者
4. 若当前 Director 心跳超时，本机可抢占（epoch + 1）
5. 选举结果写 audit.md
```

**接入点**：[worker_adapter.py:1492-1504](file:///e:/Java/webser/web_app/webme/teage-liu/teage_liu/multiagent/worker_adapter.py#L1492-L1504) `_check_director_health` 检测到 `age > timeout` 时，应：

```python
if age > timedelta(seconds=timeout):
    if not self._autonomous_mode and not self._autonomous.is_active:
        # 优先尝试选举抢占，而非直接进入自治
        election = Election(self._bb_root, self._agent_id, self._config)
        result = await election.run()
        if result.won:
            # 本机当选新 Director，启动内嵌 director_engine
            await self._start_embedded_director(epoch=result.epoch)
        else:
            # 其他实例当选，等待其 director 心跳
            await asyncio.sleep(self._director_config.get("election_wait_seconds", 5))
            # 重新检查，若仍超时则进入自治
            health = await self._check_director_health()
            if health == "offline":
                await self._autonomous.enter(reason="director_heartbeat_timeout", epoch=...)
    return "offline"
```

### 3.4 N-Worker 消息广播拓扑

```
Director 广播消息
        │
        ▼
   A2A Gateway.call_all_endpoints
        │
   ┌────┼────┬────┬────┬────┐
   ▼    ▼    ▼    ▼    ▼    ▼
 W1    W2   W3   W4   W5   Wn
 │     │    │    │    │    │
 │     │    │    │    │    │  ← 写入各实例 collaboration.md
 │     │    │    │    │    │
 ▼     ▼    ▼    ▼    ▼    ▼  ← watchdog 监听变更，立即唤醒 _poll_collab_once
LLM   LLM  LLM  LLM  LLM  LLM  ← 并发 LLM 调用
 │     │    │    │    │    │
 ▼     ▼    ▼    ▼    ▼    ▼  ← 回复 Director
A2A   A2A  A2A  A2A  A2A  A2A
```

**关键**：`call_all_endpoints` 已支持 N 端点并发（[a2a_client.py](file:///e:/Java/webser/web_app/webme/teage-liu/teage_liu/multiagent/a2a_client.py) `asyncio.gather`），N 增大时**总延迟不变**（并发而非串行）。但需要：

1. **LLM 并发限制**：每个 worker 内 LLM 调用用 `asyncio.Semaphore(N)` 限流，避免突发请求过载
2. **A2A 端点健康检查**：`call_all_endpoints` 失败的端点不应阻塞其他端点，已部分支持（`return_exceptions=True`）
3. **消息去重**：Director 广播 seq 必须全局唯一且单调，避免重复处理（已有 `messages_md.schema.yaml` 的 seq 字段）

**N-worker 收益**：N 增大时，单个实例 director 死亡不再触发误判，全局可用性 = 1 - P(所有 director 同时死亡)

#### 任务 3.3 共享 Blackboard 方案 X（推荐）

**前提**：所有 worker 同机部署或可访问共享文件系统

**改动**：
- config-a2a-X.yaml 的 `blackboard_dir` 改为同一目录 `data/blackboard_shared`
- 各实例 `agent_card.md` 仍在共享目录，跨进程文件锁保证并发安全
- 各实例 `collaboration.md` 仍在共享目录，watchdog 监听变更立即响应
- `director.md` / `status.json` / `audit.jsonl` 全局唯一

**风险**：
- 文件锁跨机器需 NFSv4 / SMBv2+ 锁语义（不推荐 NFSv3）
- 单点故障：共享存储挂 = 全集群挂

#### 任务 3.4 共享 Blackboard 方案 Y（备选）

**前提**：worker 跨机器部署，无共享文件系统

**改动**：
- 各实例独立 `blackboard_a2a_X`
- Director 通过 A2A `read_director_md` / `read_status_json` 查询其他实例
- 关键状态变更通过 A2A 广播到所有实例（最终一致性）
- 各实例维护本地 `collaboration.md` 副本

**风险**：状态同步延迟，可能出现短暂不一致

## 五、风险与回滚预案

### 5.1 风险点

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 加锁引入死锁 | 中 | director_engine 卡住 | 锁超时 5s + task_failure_counts 触发重启 |
| 选举算法错误（双 Director） | 中 | 全局状态冲突 | 用 epoch + 字典序 + lease 30s 续约；启动时强制 Election.run() |
| 自动重启无限循环 | 低 | CPU 100% | `_max_restarts=3` / 5 分钟窗口 |
| 嵌入式 Director 与 worker 主循环互相拖累 | 中 | worker 响应延迟 | 用 `asyncio.TaskGroup` 隔离，director 协程异常不影响 worker |
| 共享 blackboard NFS 锁不可靠 | 中（仅方案 X） | 数据损坏 | 优先方案 Y（A2A 同步），或限定同机部署 |
| N 增大时 A2A 调用风暴 | 中 | 网络拥塞 | `call_all_endpoints` 加 `Semaphore(10)` 限流 |

### 5.2 回滚预案

1. **代码级**：所有改动用 `if config.get("director_v2_enabled", True):` 包住，配置一键回退
2. **配置级**：保留 `config-a2a-X.yaml.bak`，可恢复旧 10s timeout / 3 retry
3. **进程级**：自动重启开关 `auto_restart_enabled`，可关掉回归手动管理
4. **架构级**：保留 `LocalDirectorManager`（子进程模式）作为 fallback，嵌入式 Director 失败时降级

## 六、需用户决策的关键问题

### 决策 1：共享 Blackboard 方案

| 选项 | 描述 | 适用场景 |
|---|---|---|
| X. 共享目录 | 所有 worker 共用 `blackboard_dir`（NFS/SMB/同机） | 同机多端口 / 高带宽网络 |
| Y. A2A 同步 | 各实例独立 blackboard，关键状态 A2A 广播 | 跨机器 / 网络不稳定 |

**推荐**：方案 X（同机部署优先）。若未来需要跨机器，再演进到方案 Y。

### 决策 2：Director 部署模式

| 选项 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. 嵌入式 + 选举（推荐） | Director 作为 worker 协程，选举决定运行实例 | 无僵尸子进程，故障检测快 | 工作量大 |
| B. 独立 Director 进程 + 选举 | 保留 director_cli，但集群唯一通过选举 | 改动小 | 仍有僵尸风险 |
| C. 单点 Director + 手动 failover | 仅 worker1 跑 director，故障手动重启 | 最简单 | 单点故障 |

**推荐**：A。

### 决策 3：N-Worker 扩展性目标

| 选项 | 目标 N | 适用场景 |
|---|---|---|
| 小规模 | N ≤ 3 | 同机部署，单团队 |
| 中规模 | N ≤ 10 | 同机或小集群，多团队 |
| 大规模 | N > 10 | 需要分布式协调（Redis/etcd） |

**推荐**：先支持 N ≤ 10（中规模），未来按需扩展。

### 决策 4：实施优先级

| 选项 | 路径 |
|---|---|
| 激进 | 阶段 0 → 1 → 2 → 3（全做） |
| 保守 | 阶段 0 → 1 → 2（仅根因 + 性能，暂不架构重构） |
| 渐进 | 阶段 0 → 1 → 2 → 5（验证稳定后再做阶段 3） |

**推荐**：渐进。
