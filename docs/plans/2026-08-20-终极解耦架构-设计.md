## 0. 设计原则(铁律,不可违反)

1. **契约单一源**:一切交互由**语言无关的协议**定义(文档 + schema + 行为描述)。代码是协议的实现,不是协议的来源。协议版本化。
2. **消息传递内核**:core 与扩展之间只交换 **不可变快照(Snapshot) → Action 消息**,不存在共享可变状态。
3. **扩展全权**:一切能力都以扩展形式存在,可扩展、可覆盖、可组合、可拔插。core 只保留"不可再减的对话动作 + 扩展机制本身"。**core 不内建任何"本可枝干化的策略"(如自动清理/TTL)——内建 = 堵死覆盖的可能。**
4. **演进内置**:协议是"稳定接口 + 演进机制"的复合体。**稳定面(交互模型)冻结,演进面(能力集合)永续开放**。core 对未知协议元素一律"透传/记录,绝不崩溃"。
5. **可落地**:每个抽象都有宿主实现(Python 先行);协议规范的任何一条都有对应的可执行行为定义。

**设计姿态**:不因个人项目降低标准,不因实现难度取舍正确性。追求最优实现;性能、安全不设上限,逐层讨论、逐层内化。

## 2. 值对象定义(types 协议)

一切交互值都是**不可变、可序列化、语言无关、schema 化的值对象**:

```
SessionId       : string
Message         : { role: user|assistant|system|tool, content: string | ContentBlock[] }
ContentBlock    : { type: text|tool_use|tool_result|thinking, ...payload }
ToolSchema      : { name, description, input_schema }   # input_schema = JSON Schema
Usage           : { input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens, ... }
Injection       : { layer: STABLE_SYSTEM|SYSTEM|PREFIX|MID|BEFORE_INPUT, content, priority, key }
```

- 所有值对象有 JSON Schema 定义(`types.schema.json`),宿主语言经 schema 生成静态类型(Python TypedDict / Rust struct);
- 运行时校验:入协议边界处校验,**拒绝而非静默容忍**非法结构(协议规定的兜底除外,见 §8);
- **持久文档例外(v1.6 定案)**:上述"一切交互值 schema 化"适用于**内核↔扩展边界传输的值**;扩展经 StorageProvider 自管的**持久文档**(doc)是显式例外——doc 为扩展私有数据,内部结构由**写入方自治**,内核只透传、不解析、不校验、不消费;扩展间若需共享 doc 结构,须经 RFC 新增协议级 kind schema,不得隐式依赖对方内部格式;
- **术语统一**:所有"覆盖类操作"的生效顺序一律称**注册序**(后注册的扩展覆盖先注册的),与 §4.1 action 应用规则、§2 注入 key 去重(后注册覆盖先注册)一致。

## 3. 事件协议(events)

### 3.1 事件集合(8+ 种,全部 schema 化)

事件是内核**唯一的对外输出通道**:

```
step_start      一次 LLM 调用开始
text_delta      文本增量
reasoning_delta 推理增量(可选)
step_end        一次调用结束(content_blocks / stop_reason / usage)
tool_use        LLM 请求工具
tool_result     工具结果回传(tool_use_id 配对)
done            对话结束(统一 9 键)
error           对话失败(不产生 done)
```

**done 事件统一 9 键**:`{type, session_id, response, messages, is_complete, termination_reason, usage, content_blocks, stop_reason}`

**事件演进**:`type: "custom:*"` 为自定义事件,core 透传不解析;成熟后经 RFC 升级为正式事件(minor 版本)。消费方对未知 type 的策略 = **透传或记录,不崩溃**(§10)。

### 3.2 事件流三层(定案:解决热路径与观测的边界)

| 层 | 内容 | 传输方式 | 消费方 |
|---|---|---|---|
| **L1 热路径** | `text_delta` / `reasoning_delta` 逐字增量 | **宿主实现内部直传,绝不外发**(协议只定格式、不定传输) | 外壳(与 host **同进程**时零拷贝引用,见下) |
| **L2 结构化摘要** | StepSummary / AfterResponse(after_step / after 钩子携带) | **钩子调用(冷路径,快照+action)** | 全部扩展(经钩子获取,含异语言) |
| **L3 观测通知** | `tool_use` / `tool_result` / `step_end` / 聚合事件(原始事件) | **异步批处理**(transport 的 `event` 消息,可背压) | 观测类扩展(含异语言) |

**不变量**:
- **L1 绝不进 transport**:逐字增量只活在宿主内,任何扩展(含同语言)都不接收 L1;
- **L2 是扩展获取对话内容的唯一语义通道**:文本呈现/审计用结构化摘要,不用逐字增量;
- **L3 是异步旁路**:观测通知允许批处理、允许背压丢帧(best-effort),**绝不影响主对话流程**;transport 的 `event` 消息类型 = L3 观测通知,非热路径透传;
- 异语言扩展观测 = 经 L3 订阅;此为其**唯一**事件入口;
- **外壳直通事件(v1.11 补)**:`step_start` / `done` / `error` 为**外壳直通事件**(与 L1 同列:宿主实现内部直传,不进 transport、不投 L3)——`done`/`error` 是终态事件,**必须可靠送达外壳(非 best-effort,不可丢弃)**,与 L3 的可丢帧 best-effort 语义不同;扩展观测"对话结束"走 after/on_error 钩子(L2)或 step_end(L3),**不经 L3 收 done/error**;
- **L3 订阅声明(v1.11 补)**:扩展声明 `capabilities: [..., "observe"]`(§12)即订阅 L3 观测通知,**无需额外订阅握手消息**;非 observe 扩展不接收 L3 观测通知——observe capability 是 L3 投递的声明面(§18.5"每观测扩展"即指含 observe 的扩展)。

**L2 与 L3 的 step_end 关系(定案)**:二者是同一事件的不同呈现形态,非重复投递——
- L2 = **`after_step` 钩子携带的 StepSummary**(结构化摘要,经钩子调用,同步语义通道);
- L3 = **原始 `step_end` 事件**(异步观测,best-effort);
- 扩展二选一订阅(经钩子拿摘要,或订阅 L3 拿原始事件),同一扩展不得同时从两条通道收取同一事件的重复副本。

**外壳进程边界(定案)**:外壳(FastAPI/Tauri)与 host **默认同进程**——L1 零拷贝引用成立的前提。若未来 Tauri 独立进程,外壳与 host 之间的通道由 **host 实现层自定**(不在扩展 transport 协议范围内,属实现层自由演进,§10.3)。

**观测类扩展只读约束(v1.5 定案,v1.9 字段名同步)**:观测 = 协议强制的只读能力,非扩展自律——
- 扩展在 `Extension` 声明的 `capabilities` 集合中含 `"observe"`(观测声明,§12);
- 观测声明下的钩子返回 action(含 SetExtra/AppendMessage/SetStop)由 core **忽略并记录**(error 级日志),对话状态不受任何影响;
- capabilities 不含 observe 的扩展 = 策略/工具类,可正常返回 action;
- L3 观测通知本身不承载 action;观测扩展若同时走 L2 钩子,统一受只读约束(与 L3 同规则);
- 此约束为 core 内核级安全 A4"capabilities 授权面强制"的组成部分(§15);扩展声明模型(§12)随之扩展。

## 4. 钩子协议(hooks)—— 核心交互模型

### 4.1 交互模型(推翻"共享可变 ctx")

```
core ── Invocation{ hook, snapshot, args } ──▶ 扩展
扩展 ── ActionResult{ actions[] } ──────────▶ core 应用
```

**ContextSnapshot**(不可变、只读、可序列化、schema 化):

```
session_id / user_input / round / started_at
history / system_text / messages / tools / extra / stop
```

**Action**(纯数据,扩展的变更请求):

| Action | 语义 | 应用规则 |
|---|---|---|
| `AppendMessage(m)` | 追加一条消息 | 叠加(按注册序) |
| `SetTools(tools)` | 覆盖工具 schema 列表 | 后注册覆盖先注册 |
| `SetExtra(key, value)` | 写入扩展间共享数据 | 覆盖,key 白名单 `^[a-z0-9_]+\.[a-z0-9_.]+$` |
| `SetStop(reason)` | 拦截整个对话 | 覆盖 |
| `SetSystem(text)` | 覆盖基础 system | 覆盖 |
| `ModifyToolSchema(...)` | 修改单个工具 schema | 覆盖 |

**覆盖语义即组合语义**:append 叠加、set 后覆盖先(注册序)——无需额外优先级语法,自由度由协议声明。

> **ModifyToolSchema 语义(v1.11 补)**:`ModifyToolSchema(name, ...)` 按工具名**定向修改**单个工具的 schema(区别于 SetTools 的整体列表覆盖);同名工具的多次修改按**应用序后覆盖先**;生效时机与 SetTools 同(影响下一轮工具列表)。与 §8 pre_tool_call 的 `modify(new_input)` 区分:前者改**工具声明**(schema),后者改**某次工具调用的入参**(input)——两个不同协议元素,勿混用。

### 4.2 钩子全集(11 钩子)

| 钩子 | 时机 | 输入 | 输出 |
|---|---|---|---|
| `setup(config, host)` | 启动一次 | 该扩展自己的配置段 + 宿主能力声明(含 storage 通道与 kind 前缀,见 §5/§6) | ok/error(失败=启动失败,逆序回滚) |
| `teardown()` | 关闭 | — | ok(幂等,异常仅告警;**无 action**) |
| `build_injections(snapshot)` | 每次对话组装前 | snapshot | Injection[] |
| `inject_round(snapshot)` | loop 每轮 step 前 | snapshot | Injection \| none(**layer 强制 BEFORE_INPUT**;每轮独立全收集,合并规则见下) |
| `before(snapshot)` | **注入声明收集后、组装收口前**(v1.6 定案,见 §4.4 收口四连) | snapshot | Action[](全部 6 种;SetStop 短路,见 §4.4) |
| `pre_tool_call(snapshot, name, input)` | 工具执行前(注册序,reject 短路/modify 叠加,见 §8 工具路径四连) | snapshot + 工具 | ToolDecision(allow/reject/modify,modify 语义见 §8) |
| `on_tool_call(snapshot, name, input)` | 工具执行 | snapshot + 工具 | result(NotImplemented = 不执行) |
| `post_tool_call(snapshot, name, input, result, duration)` | 工具执行后 | snapshot + 结果 | Action[](全部 6 种,增量收口校验) |
| `after_step(snapshot, StepSummary)` | 每轮 step 后 | snapshot + 轮摘要 | Action[](全部 6 种,增量收口校验) |
| `after(snapshot, AfterResponse)` | 对话完成 | snapshot + 完成摘要 | Action[](**一律忽略+记录**,数据写入走 storage 通道,见 §5) |
| `on_error(snapshot, error)` | 失败/断连/拦截 | snapshot + 错误 | Action[](**一律忽略+记录**,同上) |

**每钩子 Action 权限(v1.7 定案)**:
- **非终态钩子**(before / post_tool_call / after_step)统一允许**全部 6 种 Action**(AppendMessage[仅 role=user] / SetTools / SetExtra / SetStop / SetSystem / ModifyToolSchema)——轮中应用的消息类变更在下一次送 LLM 前过**增量收口**(§4.4),SetSystem/SetTools 影响下一轮;
- **终态钩子**(after / on_error)返回类型仍为 Action[](协议输出统一),但 core **一律忽略**(§5);
- `build_injections` / `inject_round` 输出 Injection(非 Action);`pre_tool_call` 输出 ToolDecision;`on_tool_call` 输出 result;`teardown` 无 action;
- **SetStop 短路规则统一**(v1.7 定案,与现状 `before_all` 短路行为一致,与 pre_tool_call 首个 reject 短路同风格):任一扩展返回 SetStop → **短路后续扩展的同名钩子调用** → before 场景跳过组装收口与 LLM、直接 done(intercepted,9 键齐整);轮中场景(post_tool_call / after_step)终止后续轮,同样 done(intercepted);
- before 的 SetSystem 为 **v1.0 新增能力**(现状 before 契约"只追加消息/置 stop/改 tools",不允许改 system——迁移时属能力扩展而非平移,行为套件锚定)。

**inject_round 多声明合并规则(v1.7 定案,解全收集语义缺口)**:多扩展各返回一条 Injection 时——① 按注册序拼接;② 参与同层 **key 去重**(与 §2 注入去重同规则:后注册覆盖先注册);③ 受 **BEFORE_INPUT 层预算裁剪**(与 build_injections 同层注入共用层预算);④ 与 build_injections 声明的 BEFORE_INPUT 注入叠加顺序 = **build_injections 先、inject_round 后**(对话级注入在前,轮级注入更靠近当前输入——延续"越动态越靠后"的五层设计哲学);⑤ 语义变更标注:现状为"首个非空返回"(后注册扩展不被调用),协议改为全收集合并(§17 迁移清单)。

**StepSummary**:`{ round, text, content_blocks, tool_uses, usage, duration }`
**AfterResponse**:`{ text, content_blocks, usage, done_event }`

> 注:`pre_tool_call`/`post_tool_call`/`after_step` 属**演进面的钩子集合新增**(§10),core 只定义触发点,扩展声明实现与否,老扩展零感知。

### 4.3 调用语义(协议强制)

- **顺序**:注册序正序调用;`after` / `on_error` / `teardown` 逆序(洋葱模型);
- **短路**:任一扩展返回 SetStop → 短路后续扩展的同名钩子调用(与现状 `before_all` 短路一致,与 pre_tool_call 首个 reject 短路同风格,§4.2/§4.4);
- **隔离**:单个扩展异常/超时 → 跳过该扩展 + 记录,**不中断对话**(错误协议 §8);
- **合法性双保险**:应用全部 action 后 + 组装后,校验消息结构(角色白名单/交替),非法 → `error` 事件,不发送 LLM。

### 4.4 Action 应用时序(定案:立即应用 + 原子批次)

> 本节约束 4.1 的"覆盖规则"与 4.3 的"快照可见性"为**同一模型的两面**——消除"快照递增 vs 覆盖语义"的歧义(评审 P1-1)。

- **立即应用**:每个扩展返回的 action 批次在调用下一个扩展前**立即、原子地**应用到快照;
- **原子批次(可见性原子性)**:单个扩展的**全部合法 action** 作为一批原子应用——同一扩展不得观察到自己的半批次状态;下一个扩展看到的是完整批次推进后的快照;
- **两层校验分离**(定案,消除"原子 vs 逐条拒绝"张力):
  - **schema 级校验**(结构合法性:SetExtra key 白名单 / 消息角色 / action op 合法):批次**应用前**逐条校验;非法条 → 拒绝 + error 级日志 + **跳过该扩展批次内剩余 action**;**合法条仍以批次原子推进**,快照对该扩展自身不呈现任何被拒 action 的部分状态;
  - **语义级校验**(上下文合法:消息交替 / tool_result 配对):组装后统一校验,失败 → `error` 事件,不发送 LLM(见 §4.3 合法性双保险);
- **快照递增(可见性)**:每个扩展收到的是"应用了前序扩展全部 action 的最新快照"——这是事实描述,不是目标;
- **覆盖规则(应用序;v1.7 收敛:仅非终态钩子适用)**:set 类 action **后应用者覆盖先应用者**——按调用(应用)序生效,而非绝对"注册序":
  - 正序钩子(before / post_tool_call / after_step 等):调用序 = 注册序 → 后注册覆盖先注册;
  - **终态钩子(after / on_error)不参与覆盖规则**——其 action 一律忽略并记录(§5,HOOK_TERMINAL_ACTION_IGNORED),被忽略的 action 无"覆盖"可言;`teardown` 无 action,不在此讨论范围;
- **叠加规则**:append 类 action 全部生效,顺序 = 调用(应用)序;
- **merge 协同时序(v1.3 定案,v1.6 扩为收口四连)**:`AppendMessage` 只负责"声明追加",**相邻 user 消息的合并时机固定在组装收口阶段统一执行**(保留 `merge_consecutive_user_messages` 语义),不随每条 action 即时合并——即 action 应用只做结构推进,交替保证由组装引擎在最后收口;扩展无法绕过交替校验;
- **收口四连(v1.6 定案,解 P1-1 的 before 时序矛盾)**:一次对话的完整时序 = ① **注入声明收集**(build_injections,注册序)→ ② **before**(注册序,action 立即应用)→ ③ **组装收口**(Assembler:注入分层叠加 → merge 相邻 user → 语义级校验)→ ④ 送 LLM。要点:
  - before 的 **SetSystem 覆盖基础 system**,注入的 STABLE_SYSTEM/SYSTEM 层在收口阶段叠加于其上(注入永远盖过 before 的裸 system,与注入"分层叠加"语义一致);
  - before 的 **AppendMessage(role=user) 插入 user_input 之后**,与注入的 BEFORE_INPUT/PREFIX 一起经收口 merge 合并,保证交替;
  - **禁止** AppendMessage 追加 assistant/tool 角色(冲突的是 user/assistant **交替约束**——连续 assistant 破坏交替,行为套件负断言锚定);扩展确有追加 assistant 需求 → 走 RFC 新语义;
  - **SetStop 分支(v1.7 补定案)**:② 中任一扩展返回 SetStop → 短路后续 before 调用 → **跳过 ③④** → done(intercepted,9 键齐整,不落盘系统提示文本)——与现状 `before_all` 短路 + `pipeline` 拦截路径行为一致;
- **增量收口不变量(v1.7 定案,解收口粒度缺口)**:**任何进入 LLM 的消息序列,必过 merge 相邻 user + 语义级校验**——这是协议级真不变量,不是"仅首轮保证":
  - **首轮**:全量收口四连(如上);
  - **后续轮**:inject_round 全收集(合并规则见 §4.2)→ 增量收口(merge + 语义校验)→ 送 LLM;
  - **轮中钩子**(post_tool_call / after_step)的 AppendMessage 应用后,同样在**下一次送 LLM 前**过增量收口;校验失败走 §8 非法 action 语义(HOOK_INVALID_ACTION → error 事件,不送 LLM);
  - **现状缺陷标注**:现状 `validate_messages` 仅在对话开头执行一次,每轮 inject_round 注入与轮中追加实际不过校验——协议定案为不变量后,属阶段 2 实现时必须修复的真实缺陷(非平移项);
  - 现状代码(pipeline:build_injections → before → assemble)即收口四连的**首轮骨架**——协议化不改变首轮交互顺序,仅把"before 写 ctx"形式化为"before 返回 action";差异两处(§17 迁移清单):现状 build_injections 调用时 messages 为空列表(迁移后快照含完整列表,属**语义增强**);inject_round 由"首个非空返回"改为"全收集合并";
- **可见性约束**:快照始终是"当前真实状态"的只读视图;扩展不得修改快照本身,只能通过返回 action 变更。

**两种模型的取舍(记录)**:曾考虑"延迟应用"(所有扩展看同一原始快照,action 收集后统一应用)——它更"纯",但丢失了"后扩展可基于前扩展的效果做决策"的顺序语义(如工具扩展检查 guardrails 是否已置 stop)。故弃用,定案**立即应用**。

## 5. 生命周期协议(lifecycle)

- `setup` 幂等可重入;任一失败 → 逆序 teardown 已成功者 → 启动失败(可读错误);
- `teardown` 幂等;异常仅告警,逆序继续;
- **热重载(同语言)**:build 新链 → 全部 setup 成功 → 原子替换;失败 → 回滚保持旧链;
- **扩展进程**(异语言):spawn → 握手 → 心跳 → 优雅关闭;崩溃自动重启(**监管语义归部署/外壳层,非 core 范围,§15-B1**);
- **终态钩子 action 一律忽略(v1.6 定案,解 P1-2)**:`after` / `on_error` 返回的 Action[] 协议强制**忽略并记录**(error 级日志,记 `HOOK_TERMINAL_ACTION_IGNORED`),不区分 observe/策略扩展——对话已结束、done 已定型、落盘已完成,不存在 action 的接收方;保留"终态 action 有效"只会制造幻觉语义。终态钩子的**数据写入一律经 storage 消息通道**(§6/§9):审计/记忆巩固枝干在 after 内直接 `storage_write`,不返回 action;observe 与策略扩展在终态行为等价(同为"只读快照 + 只写自己 kind 命名空间"),§3.2 只读约束在终态自动成立。若未来需要"终态影响下一次对话",经 RFC 新增 action 或状态写入消息,不在本轮协议范围;
- **宿主能力声明与 storage 通道(v1.6 定案,v1.7 修订,v1.11 术语定案)**:`setup(config, host)` 的 `host` 为**纯数据声明**(宿主→扩展的能力面),含:宿主提供的协议域列表、storage 域声明(通道 = transport `storage_*` 消息,§9)、**该扩展的 kind 命名空间前缀**(`{extension_name}.`,§6);**术语澄清(v1.11)**:`host`(宿主能力声明,宿主→扩展)与 §12 扩展能力声明 `capabilities`(扩展→宿主)是**两个方向相反的概念**,曾同名致歧义,故 v1.11 起 `setup` 第二参定名 `host`;扩展**不得**以对象引用方式访问宿主存储——**宿主存储的唯一访问通道** = transport storage 消息(同语言实现亦走消息,冷路径低频,性能可接受,§14.8);自持存储为经 capability 声明的显式例外(§6 存储三层模型);
- **扩展调 LLM 通道(v1.7 定案,最正确方案——invoke_llm 消息)**:扩展(同/异语言)调用 LLM 的**唯一协议通道** = transport 的 `invoke_llm` 消息(§9):
  - payload = `{ role, messages, system?, max_tokens?, ... }`,role ∈ {main, consolidation, ...} 经宿主 LLMAdapter **多角色路由**(对应 §17 B1 预留的 consolidation 通道)——多角色路由 v1.0 起**已落地**(`core/llm.py` `chat_role` + `_role_backends`:main 必配、consolidation 可选;未知 role 降级 main),复用的是宿主**多 provider 层与 API key 管理**(扩展侧零 LLM 配置);角色分池策略本身为**可枝干化策略**(§15-B4,非 core 范围);
  - 响应(成功时) = `{ content_blocks, usage, stop_reason }`(非流式;钩子内调用为补全/提取类场景,流式无必要);
  - **协议级防重入(硬不变量)**:invoke_llm 走 LLMAdapter 直调,**绝不进入 pipeline/钩子链**——把现行 X1 硬契约("钩子内禁调 chat_stream 防递归",原为代码层约定)升级为协议不变量,任何宿主实现必须遵守,行为套件负断言锚定("invoke_llm 不产生 hook 调用");
  - 调用前提 = 扩展声明 `capabilities: [..., "llm"]`(§12);**并发上限(防 DoS)为 core 内核级 A6、配额/计费/分池为非 core 范围 B4**(§15);
  - **失败语义(v1.9 补,v1.11 精确化)**:invoke_llm 失败 → 响应 = `{ error: { code, message } }`(错误码复用 §8 的 **invoke_llm 行** LLM_TIMEOUT / LLM_API_ERROR——invoke_llm 非流式,无 STREAM_FAILED/CANCELED);core **只透传失败、不替扩展兜底**——扩展自行降级(如记忆巩固失败仅告警、标题生成失败留空),责任矩阵归 LLM_TIMEOUT/LLM_API_ERROR(捕获层 = 扩展自身);
  - 典型场景:记忆巩固(老系统 `memory/consolidation.py` 实证——调 consolidation LLM 提取事实)、标题生成、审计摘要;
- **会话态协议化——快照 extra 会话内延续(v1.7 定案,最正确方案)**:三态之一的会话态正式进 hooks 域:
  - **构建时**:core 构建快照时,从 SessionStore 恢复同 session_id 的 extra 命名空间作为快照 extra 基座;
  - **写回时**:对话结束(done/error 路径)时,快照最终 extra 写回 SessionStore(§13);
  - 语义:扩展经 SetExtra 写入的数据**跨同 session 的多次对话延续**;对话内临时数据与延续数据**不做协议级区分**——extra 整体延续,扩展自决(需瞬时语义的扩展自行在 key 约定上处理,协议不管)——贯彻"扩展全权";
  - E8 契约(枝干实例全局共享必须无状态/只读)在新模型下自动成立:可变状态 = extra(对话+会话延续)/持久态(storage/自持),实例本身仍无状态;
  - **会话并发互斥(v1.9 补,v1.10 修正表述,v1.15 更新为已落地)**:同 session_id 的**并发对话由外壳串行化**(会话级互斥是外壳责任,非 core 能力)——core 快照单对话无共享,SessionStore 的 extra 恢复/写回在并发下由外壳保证不竞态;**阶段 4 已落地**:`server/session_locks.py` SessionLocks(session 级 `asyncio.Lock` LRU 有界缓存,持有/等待中的锁不可淘汰)+ `server/routes.py` /chat 与 /chat/stream 接线覆盖整个对话流——老系统 B3(会话并发无锁)遗留问题已根治(阶段 4 验收入项已通过);
  - **并发下的 core 行为语义(v1.10 诚实边界)**:core **不检测、不防御并发**——若外壳未串行化,extra 恢复/写回表现为 last-writer-wins 或丢失更新(**语义未定义**),历史"读→落盘 user"无原子性,可能出现重复读/丢消息;此为**契约前提**而非 core 缺陷:协议明确"会话串行化是外壳的前置责任",core 的并发安全以该前提成立为界,行为套件**不**为并发场景编写断言(并发正确性归外壳的运行时验收,非协议语义);
- **异语言进程重建语义(v1.5 定案,阶段 3 开工前置)**:
  - **进程归属粒度 = 每扩展一进程**(非链级进程池)——重建链只影响被替换扩展的进程,无级联重建;
  - **重建时序("接近原子")**:① spawn 并握手新进程 → ② 新扩展全部 setup 成功 → ③ 才 teardown + 优雅关闭旧进程(**含旧扩展后台任务取消:扩展自取消 + 宿主 cancel_all 兜底,§9**)→ ④ 原子替换引用;
  - ② 失败 → 杀新进程、保留旧进程与旧链(回滚保持可用;**回滚路径不取消旧链后台任务**);
  - 重建窗口期心跳/监管仍归旧链,替换完成后再移交新链;崩溃恢复在窗口期内按旧链处理;
  - **后台任务取消时序(v1.10 定案)**:旧链后台任务 cancel 严格挂接在③(teardown 阶段)——扩展 teardown 自取消自身任务(任务在扩展进程内,进程关闭即消亡)+ 宿主 cancel_all 兜底;替换(④)前不 cancel,替换后旧任务已随 teardown 消亡,无新旧任务并存、无重复副作用;
  - 因进程启动/关闭非原子,替换点定义为"旧链最后退出/新链全部就绪"之间的**切换瞬间**(引用切换),不追求进程级字面原子,但保证任一时间点至少一条完整可用链。

## 6. 存储协议(storage)

```
StorageProvider:
  write(kind, doc | docs[]) -> doc_id | doc_id[]   # 支持批量(§18.4)
  read(kind, doc_id) -> doc | null
  query(kind, filters, limit?) -> doc[]             # limit 防全量加载(§18.4)
  delete(kind, doc_id)
  close()
kind 白名单 ^[a-z0-9_.]+$(防注入,非法名拒绝)
MessageStore: 消息级落盘(content_blocks JSON / token_count / reasoning / message_type)
```

- 任何语言实现满足此 SPI 即可作为存储后端;
- 落盘时机(事件驱动):user 前置 → step_end 落 assistant → tool_result 聚合落 user(配对 tool_use_id)→ finally 兜底;注入永不落盘;
- **扩展存储三层能力模型(v1.7 定案,最正确方案——按老系统 audit/memory/metrics 三真实案例校准)**:
  1. **宿主通用存储**(经 transport `storage_*` 消息):结构化 doc,kind 前缀隔离;适用于低频读写;SPI 保持极简(write/read/query/delete)——core 只保持最基本的稳定高效的最小实现,复杂形态**不膨胀进宿主 SPI**;
  2. **自持存储**(显式声明 `capabilities: [..., "self_hosted_storage"]`):扩展自管文件/向量库/任何外部存储,进程自有——向量相似度检索(记忆)、高频实时写+轮转+游标增量读(审计)、按天 upsert(指标)等超出通用 SPI 表达力的场景全部落此层;**沙箱边界(路径白名单/网络白名单)归扩展+部署层,非 core 范围(§15-B2)**;
  3. **协议显式承认**:自持存储是经 capability 声明的显式例外,与 §14.6"当前无此协议是显式契约"同风格——不是空白,是声明制开放面;
- **kind 前缀隔离 = 读写都隔离(v1.7 定案)**:扩展只能**读写**自己前缀 `{extension_name}.` 的 kind;跨扩展数据查询走 RFC(新协议面),当前禁止——SetExtra 只承载对话内同步传递,不承载跨扩展持久查询;**前缀隔离为 core 内核级 A3,在 transport `storage_*` 消息层强制(§15)**;
- **extension_name 字符集(v1.7 定案,解前缀歧义)**:`^[a-z0-9_]+$`(**禁点**),与 §4.1 SetExtra key 白名单的分支段规则统一;前缀校验谓词 = `kind.startswith(f"{name}.")` 且 name 匹配 `^[a-z0-9_]+$`(禁点消除 "my.tool.facts" 同时匹配扩展 "my" 与 "my.tool" 的解析歧义);
- **会话态不在扩展存储范围**:会话态经快照 extra 延续承载(§5),不经 storage 消息;SessionStore(§13)仅宿主容器,会话级生命周期归外壳管理,与"core 不内建可枝干化策略"一致;
- **性能轮议题增补(v1.7)**:审计类高频写的落点分流(宿主 storage_write 批处理/异步化 vs 自持层)——"冷路径低频"假设对 audit 场景(每工具调用一条)不成立,列入性能轮。

## 8. 错误协议(errors)

> **范围标注(v1.3,v1.7 补)**:本节中的**错误码体系、`tool_rejected` 终止原因、`pre_tool_call` 触发点均为 v1.0 新增设计,非既有资产**(现有代码 `types.py` 仅有 6 个 `TERMINATION_*` 常量、无 `TERMINATION_TOOL_REJECTED`;`hooks.py` 无 `pre_tool_call` 方法)。v1.7 补列:**SetExtra key 白名单**(`^[a-z0-9_]+\.[a-z0-9_.]+$`)亦为 v1.0 新增——现状 `BranchContext.extra` 无任何运行时校验(仅 SPI 命名空间约定)。落地时按新增实现,不误判为"保留既有"。

- **终止原因枚举**:`normal / max_loops / user_cancel / no_tool_executor / llm_error / intercepted / tool_rejected`(可枚举扩展;`tool_rejected` 为 v1.0 新增);
- **错误码体系**:`LLM_* / LOOP_* / HOOK_* / TOOL_* / STORAGE_* / CONFIG_*`,每个错误码有捕获层、上报方式、兜底行为(错误责任矩阵协议化;v1.15 补 `LOOP_*` 前缀,与 errors 域一致);
- **工具执行语义边界**(定案,消除 NotImplemented / no_tool_executor / tool_rejected 歧义):

| 情形 | 判定 | 终止原因 | 行为 |
|---|---|---|---|
| `on_tool_call` 返回 NotImplemented | 该扩展不执行此工具 | — | dispatch 继续尝试后续扩展 |
| 全部扩展均 NotImplemented | 能力缺失(无执行者) | `no_tool_executor` | 友好终止,保留已产出文本 |
| `pre_tool_call` 返回 reject | 有执行者但被策略拒绝 | `tool_rejected` | 回喂 LLM(`tool_result is_error`),让其调整 |

> 二者区别:no_tool_executor = "没有执行者"(能力缺失,终止);tool_rejected = "有执行者但被拦"(意图阻断,可回喂再试)。

**modify 分支语义(v1.6 定案,解 P2-3)**:`pre_tool_call` 返回 `modify(new_input)` = 工具调用管道中的**变形器**——
- 修改后的 input 作为**该工具实际执行输入**(传给后续 pre_tool_call 与 on_tool_call);
- 多级 modify 按**应用序后覆盖先**(与 set 类 action 同规则):注册序在后的 pre_tool_call 看到已修改的 input;
- 修改后**重过工具 input_schema**(schema 级校验);非法 → 视同策略拒绝(`tool_rejected`,`tool_result is_error` 回喂,消息注明"pre_tool_call modify 产出非法 input");
- 审计可见:`tool_use` 事件携带 `original_input` 与 `effective_input`(发生修改时),`tool_result` 带 `modified: true` 标记;
- allow/reject 的位置语义:首个 reject **短路**(后续 pre_tool_call 不再调用);allow **不短路**(全部 pre_tool_call 依次执行,后序仍可 reject/modify)。

**工具路径四连时序(v1.7 定案,与收口四连对偶——工具链的协议级时序锚点)**:

```
tool_use 检测 → ① pre_tool_call 链(注册序;reject 短路;modify 叠加)
             → ② tool_use 事件(携带 original_input + effective_input[发生修改时])
             → ③ on_tool_call / invoke_tool 执行(tool_executor 专用通道)
             → ④ tool_result 事件(modified 标记)→ 回喂 → 下一轮前过增量收口(§4.4)
```

- **② 先于 ③ 的必然性**:tool_use 事件要携带 `effective_input`,pre_tool_call 链必须**整体前移到 tool_use 事件发出之前**——这是 loop 重构的真实时序变更(现状 `loop.py` 的 tool_use 事件在 dispatch 之前 yield、仅携带 LLM 原始 input),行为套件按此时序锚定;
- ① 的 reject 短路后,仍发 tool_use 事件(携带原始 input)与 tool_result 事件(is_error,tool_rejected)——观测完整性要求事件流不缺环。

- **责任矩阵**(协议强制,禁止裸 except 静默吞错——捕获点必须带日志):

| 错误 | 捕获层 | 上报 | 兜底 |
|---|---|---|---|
| LLM 失败/超时/取消 | step 层 | error 事件 | pipeline finally 落盘 |
| 钩子异常/超时 | HookChain | logger.error | 跳过该扩展 |
| 工具拒绝 | pre_tool_call | ToolDecision → tool_result is_error 回喂 | loop 回喂继续 |
| 工具执行失败 | dispatch 层 | tool_result is_error 回喂 | loop 回喂继续 |
| 落盘失败 | persist 层 | logger.error | 对话继续 |
| 扩展 setup 失败 | 装配层 | 抛错(先逆序回滚) | 启动失败 |
| 用户取消 | cancel_event | done(user_cancel) | finally 落盘 partial |
| 非法 action | HookChain 应用层 | logger.error + 跳过该条 | 批次内剩余 action 跳过,对话继续 |

**错误码体系 ↔ 终止原因映射(v1.6 定案,解 P2-4)**:二者非一一对应——终止原因描述"对话如何结束",错误码描述"具体失败点":

| 终止原因 | 关联错误码(v1.0) | 事件呈现 |
|---|---|---|
| `normal` | —(无错误) | done(is_complete=true) |
| `max_loops` | LOOP_MAX_REACHED(记录级) | done(is_complete=false) |
| `user_cancel` | —(用户动作,非错误;流中断时补 LLM_CANCELED) | done(is_complete=false) |
| `no_tool_executor` | TOOL_NO_EXECUTOR | done(is_complete=false) |
| `llm_error` | LLM_TIMEOUT / LLM_CANCELED / LLM_STREAM_FAILED / LLM_API_ERROR | error 事件(不产生 done) |
| `intercepted` | —(枝干策略,非错误) | done(is_complete=false) |
| `tool_rejected` | TOOL_REJECTED_BY_POLICY / TOOL_MODIFY_INVALID | tool_result is_error 回喂(可能继续至 done) |

**v1.0 错误码全集**(捕获层 / 上报方式 / 兜底行为,落地时行为套件逐条锚定):

| 错误码 | 捕获层 | 上报 | 兜底 |

| TOOL_NO_EXECUTOR | dispatch 层 | logger.warning | done(no_tool_executor) |
| TOOL_EXEC_FAILED | dispatch 层 | tool_result is_error 回喂 | loop 回喂继续 |
| TOOL_REJECTED_BY_POLICY | pre_tool_call | tool_result is_error 回喂 | loop 回喂继续 |
| TOOL_MODIFY_INVALID | pre_tool_call | tool_result is_error 回喂 | loop 回喂继续 |
| STORAGE_WRITE_FAILED | persist/storage 层 | logger.error | 对话继续(旁路) |
| STORAGE_READ_FAILED | persist/storage 层 | logger.error | 扩展 setup 失败或降级 |
| CONFIG_UNKNOWN_KEY / CONFIG_INVALID_VALUE / CONFIG_MISSING_KEY | 配置加载 | 抛错(启动失败) | 可读错误 |

## 9. 传输协议(transport,细节归性能轮)

- **通道(定案 2026-08-20;v1.7 精确化)——传输绑定双形态**:
  - **stdio 绑定**(子进程,LSP 模式):**跨进程(异语言)扩展的唯一通道**;
  - **进程内绑定**(同语言):`Branch` 协议绑定 = 消息语义的**零成本实现**(直接函数调用,序列化豁免,行为套件同一用例覆盖)——"消息语义"指扩展侧仍只能经快照+action / storage_* / invoke_llm / task_* 消息与宿主交互,**不得绕过协议直接抓宿主对象引用**(零拷贝引用仅限快照/值对象,§14.8);
  - core 与协议**只负责本地这一端的传输协议**,不承载任何远程网络通信;
- **远程调用(A2A)由扩展自己实现**:扩展有远程协作需求时自行实现远程协议(连接/认证/编解码),
  core 对"扩展内部如何与远端通信"零感知、零约束;
- 帧格式:**可插拔编码层**(JSON 起步 / MessagePack / protobuf),协议边界清晰时换格式是内部实现细节;
- 消息类型(v1.7 全集):`invoke_hook / invoke_tool / invoke_llm / storage_write / storage_read / storage_query / storage_delete / task_register / task_cancel / event / heartbeat / shutdown`;
  **`event` = 事件流 L3 观测通知(异步批处理,非 L1 热路径透传,见 §3.2)**;
  **`storage_*` = 宿主通用存储访问通道(v1.6/§6):宿主存储的唯一合法入口;payload 含 kind + 数据,kind 必须带 `{extension_name}.` 前缀且 extension_name 匹配 `^[a-z0-9_]+$`,非法前缀拒绝(schema 级校验)**;
  **`invoke_llm` = 扩展调 LLM 的唯一协议通道(v1.7,§5):payload 含 role/messages;走 LLMAdapter 直调,协议级防重入(不进钩子链)**;
  **`task_register / task_cancel` = 扩展后台任务通道(v1.7 定案,v1.9 补语义)**:payload = `{ task_id, description }`(task_cancel = `{ task_id }`);**后台任务归属扩展进程**——宿主只登记(可观测/取消协调),不承载执行;扩展 teardown 时自取消其任务,宿主 shutdown 与热重载重建时 cancel_all 兜底(§11 TaskRegistry);进程内绑定 = 零成本实现,跨进程经消息;
- **`invoke_tool` vs `invoke_hook` 分工(v1.6 定案,解 P3-3)**:`invoke_hook` 为通用钩子调用(参数 = Invocation{hook, snapshot, args},返回 ActionResult);`invoke_tool` 为**工具执行专用消息**(payload 仅 name+input,**免快照序列化**),语义 = 扩展声明 `capabilities: [..., "tool_executor"]` 时 core 派发工具的首选通道;未声明 tool_executor 的扩展,工具执行退化为 invoke_hook(on_tool_call);两种路径结果等价,行为套件同一用例覆盖,仅传输开销不同(§14.8 异语言冷路径成本的有意优化);**多扩展派发聚合(v1.11 补)**:工具派发按**注册序**遍历全部扩展(含 tool_executor 者走 `invoke_tool`,未含者走 `invoke_hook(on_tool_call)`),单个扩展不执行该工具(语义等价 §8 的 NotImplemented)则继续下一扩展,全部均不执行 → `no_tool_executor` 友好终止——两种通道的"不执行"信号统一计入 no_tool_executor 判定;
- 异语言扩展经 `RemoteBranchAdapter` 接入,对 core 是普通扩展,core 不感知对方语言。

## 10. 演进机制(evolution)—— 解耦不放弃发展

### 10.1 稳定面 vs 演进面

| 面 | 内容 | 策略 |
|---|---|---|
| **稳定面** | 快照/action 交互模型、事件流语义(§3.2 三层)、生命周期语义、错误责任矩阵 | **冻结**(v1.0 起,改动 = major 版本 + 双版本共存过渡期) |
| **演进面** | hook/event/action 的**集合** | **永续开放**,经三阶机制演进 |

### 10.2 三阶演进

```
第一阶: 自定义扩展点(不改协议即可用)
  Event.type → "custom:*"   # core 透传,观测扩展可消费
  Hook.name → "custom:*"    # 扩展声明实现,core 通用触发点调用
  Action.op → "custom:*"    # 扩展间传递,core 记录+忽略

第二阶: semver 版本化(受控添加)
  protocol_version: "1.2.0"(semver)
  minor = 向后兼容添加(新 hook/event/action,老扩展不声明不调用,零破坏)
  major = 破坏性变更(双版本共存过渡期,core 与扩展互验版本)

第三阶: RFC 流程(防协议膨胀)
  新元素提案 → 评审"能否由现有 custom/组合实现"
  能 → 不升级,留在 custom;不能(新时机/新语义) → 入 minor
```

**与协议域的关系**:evolution 不是与 types 平级的"独立协议域",而是**横切属性**——它规定"其余所有域如何演进"(新增/变更/废弃/版本)。9 域中的 evolution 是其余 8 域的元规则,评审/实现时以此为准。

### 10.3 core 演进自由度

- **实现层**(性能/存储/LLM 适配/序列化):自由演进,不影响协议;
- **语义层**(新 hook/event/action):走 RFC + 版本化;
- 新增钩子 = 新增触发点:core 定义触发时机,扩展声明实现与否,老扩展零感知。

## 12. 扩展接入模型

```
Extension = { name, lang, transport, protocol_version, hooks_implemented[], capabilities[] }
# name 匹配 ^[a-z0-9_]+$(禁点,§6 前缀隔离的可判定前提)
```

- **声明式钩子**:扩展声明实现哪些钩子,core 只调用已声明的(减少无效交互);
- **能力声明(v1.5 单值 → v1.7 集合模型)**:`capabilities` 为**集合**(可组合,自由声明),v1.0 枚举:
  - `observe`:观测只读——钩子返回的 action 被 core 忽略并记录(§3.2);
  - `tool_executor`:工具执行者——启用 transport 的 `invoke_tool` 专用消息(§9);
  - `llm`:可调用 `invoke_llm` 消息(§5/§9);
  - `self_hosted_storage`:自持存储——扩展自管文件/向量库/外部存储(§6 三层模型,**沙箱归扩展+部署层,§15-B2**);
  - 组合示例:`observe + tool_executor` = 只读执行者(允许执行工具、不允许改对话状态);`observe + llm` = 观测型 LLM 消费者(审计摘要);
  - 缺省(空集)= 策略/工具类,可正常返回 action;
  - 能力是**授权面**而非行为面:**core 只强制声明面(未声明 llm 却调 invoke_llm → 拒绝等,§15-A4)**;细粒度 action 权限 / invoke_llm 配额 / 自持沙箱均为非 core 范围(§15-B),capabilities 仅作其最小权限**声明**基座;
- 同语言:`Branch` 即协议绑定(参数=快照/返回值=action);
- 异语言:`RemoteBranchAdapter` + transport;
- 版本协商:core 与扩展互验 `protocol_version`,降级兼容或拒绝(可读错误)。

## 13. 状态三态模型(协议化)

| 态 | 容器 | 生命周期 | 重启后 |
|---|---|---|---|
| 对话态 | Snapshot 内传递 | 一次对话 | 消失(契约) |
| 会话态 | SessionStore(宿主实现,仅容器);**经快照 extra 延续承载(v1.7,§5)** | 一个会话 | 消失(契约);生命周期由调用方管理 |
| 持久态 | StorageProvider(宿主通用)或自持存储(§6 三层模型) | 扩展自管 | 保留(setup 自恢复) |

> **会话态协议化(v1.7 定案)**:会话态的扩展访问通道 = **快照 extra 会话内延续**(构建时恢复/结束时写回,§5)——三态全部有协议级落点,不再存在"三不管"通道;会话态读写不经 storage 消息。

> **会话级生命周期边界(v1.5 定案)**:会话/对话级生命周期由外壳管理,**不在扩展生命周期协议范围内**(§5 只覆盖扩展进程级 setup/teardown/热重载)。

> **变更标注(2026-08-20 评审修订)**:SessionStore 只提供容器,**core 不内建自动清理/TTL**——清理策略(如 TTL)由外壳/扩展自管,与现行契约(`teage_liu2/core/session.py` "drop 由调用方负责,core 不自动清理")保持一致。TTL 属于"可枝干化的策略",core 内建即违背扩展全权理念(§0.3)。此修订为对早期草案的更正,非新增能力。

## 14. 架构边界与不变量(v1.0 冻结项)

1. **热路径不变量**:事件流 L1 逐字增量只在宿主实现内部传递——协议只定事件格式,不定传输机制;任何扩展(含同语言)不接收 L1(§3.2);
2. **冷路径不变量**:所有扩展交互一律快照+action(协议强制);扩展通过 L2 钩子摘要、L3 观测通知获取上下文;
3. **行为一致性(语言无关)**:协议级**黄金用例集**——每个用例以 JSON 定义,**不依赖任何语言的测试框架**;每个宿主实现(Python/Rust)运行同一套用例并报告通过率;套件随协议演进(新增协议元素必须同时新增用例,否则不进协议);用途 = v1.0 冻结前提 + 新宿主实现验收门槛 + 协议-实现漂移的持续审计工具(维护归 evolution 域);**建立时机 = 阶段 0/1 产出初版(随协议域落地同步),阶段 2/3 增补,阶段 4 全绿冻结(见 §16)**——阶段 2/3 的验收直接对拍行为套件,而非临时内部对拍;
   **用例格式(v1.6 扩展,解 P2-1)**:`{ id, protocol_version, description, setup{extensions[]}, inputs, expected{...} }`;`expected` 含四类断言(缺省类型 = 主事件流断言):
   - `event_stream`: 主断言,有序期望事件(含 payload 匹配);**列表中 `absent: true` 的项为全程负断言(断言该事件在整条事件流任意位置都不出现),不参与有序逐项匹配;其余项按序逐项匹配**——`absent: true` 是 L1"绝不出 transport"、`text_delta` 绝不出现在扩展通道等"不出现"类断言的基础;
   - `invocations`: **钩子调用序断言**(正序/逆序/跳过/短路),逐条 = `{ hook, extension, order?, snapshot_assert?, actions_assert?, isolation?(timeout/error → skip) }`——`snapshot_assert` 断言该扩展收到的快照视图(§4.4"下一个扩展看到前序 action 应用后的快照"逐条锚定,含收口四连时序);
   - `final`: 收尾断言(termination_reason / is_complete / persisted 落盘断言,选配);
   - `absent` 类断言对 events / invocations 通用(断言某事件或某钩子调用**不出现**)。

   **断言匹配器规范(v1.7 定案,黄金用例集语言无关性的可执行保障——所有宿主实现内置同一语义的匹配器解释器)**:
   - **字段寻址**:点路径表达式(JSONPath 子集:`.` 分隔 + 数组下标,如 `snapshot.messages.0.role`、`usage.output_tokens`);
   - **对象匹配**:默认**子集匹配**(期望对象 = 实际对象的递归子集;期望未列出的字段不断言——锚定关键行为而不锁死无关细节);
   - **数组匹配**:默认**逐项有序匹配**;`{length: n}` 匹配器单独支持长度断言;
   - **标量匹配器**:字面量 = 相等;`{regex: "..."}`(字符串正则);`{range: [lo, hi]}`(数值闭区间);`{type: "string|int|..."}`(类型);
   - **`absent: true` 负断言作用域 = 全程**(整条事件流 / 全部 invocations,自用例开始至结束),不做窗口语义(窗口断言有需求走 RFC);
   - 匹配器本身 **schema 化**,成为行为套件 schema 的一部分(阶段 0 产出)——匹配器语义的任何变更走协议版本化(§10)。
4. **未知元素宽容**:core 对未知 type/op/hook 的策略 = 透传/记录,绝不崩溃;
5. **方向约束**:扩展不得修改内核,内核不得依赖扩展(唯一例外:装配点注册工厂);
6. **扩展间通信(v1.5 定案)**:扩展间通信**唯一通道 = `SetExtra` 同步转发**(经快照,命名空间 `{extension_name}.{key}`);当前协议**不提供**扩展间异步消息/事件订阅;异步扩展间通信如有真实需求,走 RFC 三阶演进(§10.2)作为新增协议面——"当前无此协议"是显式契约而非空白;
7. **可落地**:每个协议条目都有宿主实现与可执行行为定义,无空头契约;
8. **异语言性能边界(诚实声明)**:异语言扩展天然在冷路径(stdio 序列化),**不享受 L1 热路径直传**;每次快照传递、观测通知都有序列化成本——这是解耦的现实代价,设计上接受;接入指南必须注明:高频小数据钩子(如 `inject_round`)不适合异语言扩展;同语言(零拷贝引用)与异语言(序列化)性能不对称是有意设计。

**安全轮(v1.12 已全部定案 → 见下)**:

> **分类原则(v1.12 定案)**:core 内核级安全 = core **直接经手数据/边界、不保证即出安全漏洞、且无法推给扩展**的部分;凡"扩展/外壳自实现更正确、或 core 内建即堵死覆盖可能(§0.3)"的安全问题,一律**显式声明边界、不设计**(与 §14.6"无此协议是显式契约而非空白"同风格)。贯彻:**core 完美主义 = 该做的做到极致无死角;core 最小实现 = 不该做的坚决不内建**。

**A. core 内核级安全(8 项,必须内置,不可推给扩展;散布各处者此处归口)**:

1. **协议边界 schema 校验(拒绝非法)**:core 在协议边界处对所有入站值对象(扩展返回的 action / transport 消息 / 快照字段)做 schema 校验,**非法拒绝 + error 级日志,绝不静默容忍**(§2 已定原则,此处归口为安全边界)——防恶意/缺陷扩展注入畸形结构的第一道闸;**含 revision 字段(v1.13 补)**:`revision` 由 host 独占生成、扩展只读(§18.2),扩展提交的 revision 值 / delta 帧 `base_revision` 非法(超界/非单调/伪造)一律拒绝——revision 是快照版本正确性根基,防伪造版本致 delta fallback 误判;
2. **标识符注入防护**:三个白名单从"功能正确性"升格为**安全边界**——`extension_name` `^[a-z0-9_]+$`、`kind` `^[a-z0-9_.]+$`、`SetExtra` key `^[a-z0-9_]+\.[a-z0-9_.]+$`(§2/§4.1/§6/§12);防 SQL 表注入、防前缀越权访问;core 在 schema 级强制,非法拒绝;**现状(v1.13 标注,v1.15 更新为已落地)**:三白名单均已落地——`kind` 字符白名单(storage.py `_validate_kind`)、`extension_name` 字符集校验(registry.py build 循环,非法名启动失败)、`SetExtra` key 白名单(hooks.py `BranchContext.set_extra` / actions.py 校验);
3. **kind 前缀读写隔离强制**:宿主通用存储的**访问控制点**——core 在 transport `storage_*` 消息层强制 `{extension_name}.` 前缀,**读写都隔离**,跨前缀访问拒绝(schema 级);这是 core 提供的存储通道唯一访问控制,不可推给扩展(§6);**现状(v1.13 标注,v1.15 更新为已落地)**:阶段 3 起 `storage_*` 消息经 `TransportBus`(`register_extension` 扩展身份模型 + `check_kind_prefix` 强制前缀,读写都隔离,跨前缀拒绝),storage_provider 不再经 SimpleNamespace 直接注入——前缀隔离已生效;
4. **capabilities 授权面强制(声明面 vs 行为面对拍)**:core 校验扩展行为与声明一致——**最小集合(v1.13 锁定) = 三项**:①未声明 `llm` 却发 `invoke_llm` → 拒绝;②未声明 `tool_executor` → 不派发 `invoke_tool`(按未声明处理);③声明 `observe` 却返回 action → 忽略+记录(§3.2 已定)。这是 core 的**最小权限基座(授权面)**,非策略面(§12);**边界锁定**:超出此三项的行为约束(如"某扩展只能 SetExtra 不能 SetSystem")归 B6(细粒度 RBAC),不属 A4;capabilities 声明模型的 schema 定义进阶段 0(§16),否则阶段 2 的对拍缺少可对拍的声明面;
5. **防重入 / 防递归不变量**:`invoke_llm` 走 LLMAdapter 直调、**绝不进 pipeline/钩子链**(§5 协议不变量),core 在协议级强制——防恶意/缺陷扩展递归重入拖垮 core;**与 A6 正交(v1.13)**:A5 防重入针对**调用图循环**(invoke_llm → 钩子链 → invoke_llm 的递归),A6 并发上限针对**同一通道的并发数量**;core 在 invoke_llm 入口分别执行"重入检测"与"并发计数"两套独立校验;
6. **资源上限(防 DoS)**:core 必须对单点恶意扩展设硬上限,**无界即漏洞**:
   - 快照体积上限 + 单条消息 content 体积上限(防超大注入/append 撑爆内存与上下文)→ **落地阶段 2**(随 Snapshot 实现);
   - 单次对话消息总条数上限(防无限 append)→ **落地阶段 2**;**注意与 `history_window_messages`(历史读取窗口)、`max_loops`(循环轮数)三者语义不同,须新增独立配置项,不得复用现有项顶替(v1.13)**;
   - 钩子超时(已定,默认 5s,§4.3,现状已落地 hooks.py);
   - StorageWriter 写队列容量上限 → **阶段 1** / L3 观测队列容量上限(§18.5 已定 1024 + 丢弃计数)→ **阶段 3**(§16 阶段 3 已补对拍锚点,v1.14);
   - `invoke_llm` 超时 + **并发上限**(硬边界,防 DoS,**非**配额策略)→ **阶段 3**(并发上限须实现为硬边界如信号量,非配置项,v1.13;**§16 阶段 3 已补对拍锚点,v1.14**);
   - 阈值**具体数值**进 types 域 schema(阶段 0 产出),但"**必设、不可无界**"是协议硬约束;
   - **现状(v1.13 标注,v1.15 更新为已落地)**:阶段 1-3 已落地——快照体积/单条消息/消息总条数上限(`core/snapshot.py` `_check_message_budget/_check_snapshot_budget` + `config.py` 独立配置项,默认 = `RESOURCE_LIMITS`)、StorageWriter 写队列容量上限(4096,满丢弃最旧+计数)、L3 观测队列容量上限(1024)、invoke_llm 超时+并发信号量上限(4);`history_window_messages`/`injection_budget_chars` 语义不同,不复用;
7. **序列化边界校验(transport 层)**:stdio 帧解析时的**帧长度上限、JSON 嵌套深度/体积上限、非法帧/超长帧拒绝、delta 帧 `base_revision` 合法性(≤ 当前 revision,§18.2)**——防畸形或恶意扩展进程发送数据导致 core 崩溃;core 只负责本地这一端(§9),边界校验是本地端责任;**与 B5 澄清(v1.13)**:B5 的"本地 stdio 信任边界"指**无需认证/加密**(不防身份伪装),A7 防的是"被信任进程内部缺陷/崩溃引发的畸形输出"(防健壮性/DoS,非防身份攻击)——两者不矛盾;
8. **core 敏感信息不泄漏**:core 在任何**对外输出通道(日志/事件/错误响应/诊断信息)不得泄漏密钥/token/内部路径**——这是内核级硬约束,不可推给扩展;配置的 `${VAR}` 占位注入 + `.env` 分离 + 脱敏函数(`config.py` 的 `mask_sensitive_config` 为承继老系统的函数资产——teage_liu2 无 `GET /config` 路由,该函数未接线为脱敏端点,属既有资产而非已落地端点)是**既有配置功能资产**,回指 §7 配置域、§17 保留项,**不再作为安全项重复声明**(v1.13 拆分:避免"配置功能"与"安全边界"混同;v1.14 表述精确化);验收锚点见 §16 阶段 4。

**B. 非 core 范围(6 项,扩展/外壳自实现,显式声明边界、不设计)**:

1. **异语言扩展进程隔离/沙箱/监管树/崩溃重启**:OS 级进程沙箱(容器/cgroup/权限降级)、监管树、崩溃自动重启是**部署/外壳层**运维职责;core 只保证"扩展进程崩溃不影响 core 主对话"(隔离语义 §4.3/§5 已定),不提供进程沙箱;
2. **自持存储沙箱边界**:路径白名单/网络白名单/进程权限——自持存储是扩展自管的(§6 三层模型),沙箱由扩展自身 + 部署层负责;core 不提供文件系统/网络沙箱;**迁移落地责任(v1.13 补)**:老系统 audit/memory/metrics 三案例迁入自持层时,其文件/路径访问的沙箱责任**显式落到各扩展自身**(非"部署层"空头——个人项目可能无独立部署层),迁移验收锚定"这些枝干不把路径当作可注入的 kind 使用"(§17);
3. **跨扩展敏感数据脱敏**:扩展间经 SetExtra/storage 传递的数据脱敏是**数据生产者扩展**的责任——core 无领域知识、无法识别"什么是敏感数据";core 内建脱敏 = 堵死覆盖可能(§0.3);
4. **invoke_llm 配额/计费/角色分池策略**:token 配额、计费、分池是**可枝干化策略**(§0.3),core 不内建;core 仅保留硬边界(超时 + 并发上限,见 A6)防 DoS,不做配额策略;
5. **传输认证**:本地 stdio 子进程 = core 自己 spawn,**OS 进程边界即信任边界**,无需协议级认证;远程 A2A 认证由扩展自实现(§9 已定)——故"传输认证"不属 core 协议范围;
6. **细粒度 action 权限/RBAC**:core 不做"某扩展只能 SetExtra 不能 SetSystem"的细粒度 RBAC——那是**可枝干化策略**,内建即违背 core 最小实现;core 只保证两个硬边界:action 结构合法性(A1)+ observe 只读强制(A4)。更细的授权是外壳/配置层策略。

**安全项 ↔ 协议域归口(v1.13 补,与 §16 九域全覆盖呼应)**:A1→types/errors、A2/A3→storage、A4→§12 capabilities、A5→lifecycle/transport、A6→types(schema)/storage/transport 三域、A7→transport、A8→config/errors——实现时按归口落点,不散落无处落点。

**架构层(已定/待确认)**:
- **stdio 通道已定(2026-08-20)**:本地扩展唯一通道;A2A 归扩展自实现(core 零感知);
- **稳定面冻结 vs 演进面开放(§10)**:默认采纳,待用户最终确认;
- `protocol_version` 冻结为 v1.0 的时机(建议:语言无关行为套件全绿后冻结稳定面)。

- **setup 签名迁移影响(v1.6 标注,v1.11 术语定案)**:`setup(config, core)`(现状,core = 宿主上下文对象引用)→ `setup(config, host)`(协议,纯数据声明 = 宿主能力声明 + storage 通道)是 breaking change;既有枝干仅 guardrails 一个且未使用 core 参数,阶段 2/3 随迁,行为套件同用例锚定迁移前后语义一致;外壳 composition root(`server/app.py`)随之由"对象注入"改为"宿主能力声明构造 + storage 通道接线"(storage 访问改走 transport 消息,§6/§9);
- **迁移语义变更清单(v1.7 补全,"零漂移"断言的精确边界)**:
  - `inject_round`:首个非空返回(后注册扩展不被调用)→ **全收集合并**(§4.2 合并规则);返回类型 `str|None` → `Injection|none`——行为+签名双重变更;
  - `build_injections`:现状调用时 ctx.messages 为空列表 → 迁移后快照含完整消息列表——**语义增强**(扩展可基于全量上下文声明注入),非平移;
  - `before` 的 SetSystem:现状契约不允许改 system → 协议允许(全部 6 种 action)——**能力扩展**;
  - 轮中语义校验:现状轮中注入/追加不过 validate_messages → 协议增量收口不变量——**缺陷修复**;
  - `capability` 单值(v1.5)→ `capabilities` 集合(§12)——声明模型升级;
  - `BranchContext.extra` 无校验 → SetExtra key 白名单(§8 范围标注)——**新增校验**;
  - `registry` 不校验枝干名/`extension_name` 字符集(仅配置驱动注册)→ `extension_name` 字符集 `^[a-z0-9_]+$` 校验(§6/§12/§15-A2)——**新增校验**(v1.14 补,与 A2 对齐);

## 18. 性能定案(性能轮,2026-08-20 起定案,v1.10 收口)

> 量化基线(定案依据):典型负载 = 100 条历史 × 2KB ≈ 200KB 快照全量;全量序列化单次 ~1-3ms、`copy.deepcopy` ~10-50ms;高频钩子 × 全量快照 × 异语言 = 秒级累计开销(不可接受)。**所有定案不触动协议语义**(消息传递内核/语言无关/扩展全权不变)——性能优化全部落在宿主实现层与传输层。

### 18.1 存储性能:StorageWriter 异步单写者(最核心定案)

**问题(现状真实缺陷)**:`pipeline._persist` 同步调用 `sqlite3`(含 fsync)于请求路径——阻塞事件循环,违反项目 async 铁律;历史库与 StorageProvider 共用 db 文件,多连接并发写互相排队(单写者锁)。

**定案:StorageWriter 异步单写者架构**——
- **单一写队列 + 专用写连接**:全部 SQLite 写(消息落盘 + 扩展 `storage_write` + FTS 同步)入队,单写连接串行执行;**队列 FIFO 保序**(user 的 flush 不插队,同 session 落盘顺序 = 入队顺序,消息时间线不乱);读连接并发(WAL);写队列深度/延迟可观测(计数器);
- **落地形态(v1.10 定案,零新依赖路线)**:**专用写线程 + `queue.Queue` + Future 桥接**——启动一个常驻写线程独占写连接(`check_same_thread` 回退默认 True,更安全),`flush` 提交 `Future` 供事件循环 await、`background` 入队即返;天然单写者 + 天然 FIFO(不采用 `run_in_executor` 线程池——多线程会破坏 FIFO 保序;不采用 `aiosqlite`——引入新依赖且与现有连接模型不兼容)。项目现有 `requirements.txt` 无 aiosqlite/pyrsistent,本定案保持零新增依赖;
- **持久性分级**:
  - `flush`:调用方 `await` 该写操作在队列中**执行完毕的 Future**(事件循环仅挂起协程、不阻塞线程;fsync 在写线程内执行)——仅 user 前置落盘用(保"断连不丢输入"契约);
  - `background`:fire-and-forget,入队即返回,失败重试 + error 日志——assistant / tool_result / 审计 / 扩展低频写全部走此级;
- **PRAGMA 定案**:`journal_mode=WAL`(已有)+ `synchronous=NORMAL`(WAL 下安全性可接受,大幅减少 fsync);**flush 语义 = await commit(NORMAL 下 WAL 已写,保证进程崩溃不丢,非逐次 FULL fsync)**;断电级持久性走显式 `WAL checkpoint` 或 `synchronous=FULL`(归部署配置,非常规请求路径)——NORMAL 保证"进程崩溃不丢"(客户端断连 ≠ 进程崩溃,§6 契约以进程崩溃为界);
- **现状缺陷标注**:同步落盘阻塞事件循环 = 阶段 1(宿主数据层)必修项,非平移项(§17);
- 模块归位:§11 新增 `StorageWriter`(异步写编排)。

### 18.2 快照传递:三层性能模型(主题一 COW 定案)

**协议层(语言无关,进 v1.0)**:
- snapshot 新增 `revision: int`(对话内单调递增)——既是行为套件"快照递增可见性"的断言锚点,也是传输层 delta 的引用基准;
- **revision 递增主体(v1.10 定案)**:**由 host 独占递增,扩展侧只读**;粒度 = **每次 action 批次应用后 +1**(快照每推进一次即 +1,与 §4.4"立即应用 + 原子批次"对齐——每次批次推进快照即递增,是最精确的"快照版本"粒度);轮次(round)与 revision 不同源:round 表"第几轮 LLM 调用",revision 表"快照第几个版本"(轮内 post_tool_call/after_step 的 action 应用也递增 revision);
- 快照语义**不变**(全量只读视图)——协议对扩展永远呈现完整快照,delta 是传输层内部重组,扩展侧透明。

**宿主实现层(同语言,进程内绑定)**:
- **禁止 `copy.deepcopy`**(强制:deepcopy 200KB ~10-50ms,是最大性能陷阱);
- **结构共享 + 受控复制(v1.10 诚实降级)**:不可变快照直接传**引用**(零拷贝);action 应用时只复制被修改路径(messages 尾部追加 → 新列表+共享元素引用;extra/tools 覆盖 → 新容器)。**落地形态诚实声明**:Python 内建 list/dict 无持久化数据结构,真正的 O(变更) append-only 结构共享需引入 `pyrsistent` 或自写持久化容器——本项目**默认零新依赖路线**,v1.0 落地形态 = **O(n) 浅拷贝(n = 消息条数,仅指针复制,非字节深拷贝)+ 尾部追加新容器 + 共享元素引用**(现状 `loop.py:160-161`(assistant 追加)/`:276-278`(tool_results 回喂) `list(messages) + [...]` 即此形态);100 条消息的 O(100) 指针复制微秒级,远轻于 deepcopy 的 10-50ms;真正的 O(变更) 持久化结构**降级为 future 优化**(仅当消息体积极大且实测成为瓶颈时再评估,不属 v1.0 范围);
- 每轮增量收口(§4.4)的 merge/validate 与快照同源结构,同享 O(变更) 复杂度;
- **零拷贝豁免边界**:仅快照与值对象可引用直传;扩展**不得**持有宿主可变对象引用(消息语义保留——扩展侧接口仍是快照+action,传输零成本不等于协议豁免)。

**传输层(跨进程,stdio)**:
- 帧新增 `encoding: full | delta` 标识(握手协商能力);
- **delta 格式 = 极简增量**(与 action 语义对齐,非 RFC 6902):`{ base_revision, ops: [append_messages[] | overwrite{tools|system|extra_kv|stop} ] }`——消息序列在钩子间近似 append-only,天然高效;
- **delta fallback 语义(v1.9 补)**:接收方 base_revision 不匹配(进程重启/断链重连)→ 请求 `full` 重发;delta 仅优化传输、**不承载正确性**(正确性由 revision 与快照全量语义保证);
- **分层实施(诚实定案)**:v1.0 宿主实现 = `full` 编码 + **轻量通道组合**(异语言扩展避免高频钩子(§14.8)+ invoke_tool 免快照 + storage 批量 + invoke_llm 非流式)——该组合已把异语言全量快照传输压缩到低频钩子(before/after 级),单次 1-3ms 可接受;`delta` 编码为 v1.x minor 演进(协议 v1.0 即定义格式,实现渐进,非空头能力);
- **量化依据**:不优化时高频钩子全量快照 ≈ 1.2s/百轮(不可接受);轻量通道组合后全量传输仅剩低频钩子(≈ 10 次 × 3ms = 30ms,可接受);delta 后再降一个量级(锦上添花,非必需)。

### 18.3 编码层选型(定案)

- **JSON = v1.0 唯一基线编码**:零依赖、全语言原生、调试友好;帧头带 encoding 标识(为演进留口);
- **MessagePack = v1.x minor 选项**:二进制紧凑(~30-50% 体积),帧头协商后可换;
- **protobuf 砍掉(记取舍)**:需要 schema 编译链与代码生成,违背"语言无关、零工具链轻量接入"的协议理念——体积收益(MessagePack 已覆盖大半)不抵接入成本。

### 18.4 通用存储 SPI 的性能契约(定案)

- **`storage_write` 支持批量**:payload 允许 `docs[]`(一次消息携带多条,单次往返)——审计类高频写的宿主侧通道优化;
- **`query` 补 `limit` 参数**(SPI 小扩展,防全量加载);
- **性能契约显式化**:宿主通用存储定位 = **低频小量结构化数据**;高频写(每工具调用级)/向量检索/轮转游标 → 自持存储 capability(§6 三层模型)——SPI 不为重负载膨胀;
- **审计分流定案(v1.7 议题闭环)**:审计扩展推荐**同语言进程内绑定**(写队列零序列化成本,经 StorageWriter 串行化,SQLite WAL 顺序写正是强项);必须异语言时走自持存储;宿主 storage_write 批量接口作为两者的中间档。

### 18.5 L3 观测:批处理与背压参数(定案)

- **批处理窗口**:**50ms 或 64 条,先到者触发**(时延与吞吐的平衡点:观测者体感"近实时"阈值内,批量化摊薄帧开销);
- **实现形态(v1.10 定案)**:EventStream 引擎内单例 `BatchBuffer` + **每观测扩展一个独立有界队列**;事件产生即入队并检查 64 条阈值,`asyncio.create_task` 定时 50ms 冲刷;L3 拦截点 = EventStream 引擎内(`tool_use`/`tool_result`/`step_end` 进批处理旁路,`text_delta`/`reasoning_delta` 走 L1 不入 L3)——阶段 3 落地,阶段 2 仅 schema 对拍;
- **背压**:每观测扩展一个**有界队列**(容量 1024,宿主侧,传输前);满 → **丢弃最旧 + 丢弃计数**(观测 best-effort 契约,§3.2),计数随心跳上报——**绝不阻塞主对话流**(L3 是旁路,丢帧不影响正确性);
- 丢弃计数本身是可观测信号:持续丢弃 = 观测扩展消费过慢,运维告警依据。

### 18.6 对话延迟:首 token 前开销预算(定案)

- **预算**:core 侧首 token 前路径(读历史 + user flush 落盘 + 钩子链 + 组装收口 + 校验)目标 **<10ms(P95)**;
- **达标路径(v1.10 分项细化,诚实标注)**:① get_session_messages SQL 查询 + dict 构造(~1-2ms)② normalize_history 逐条 json.loads content_blocks(100 条 × 2KB ≈ 200KB,~2-5ms)③ **user flush = ensure_session(INSERT+commit)+ log_message(messages INSERT + FTS INSERT + sessions UPDATE + commit),~2-5ms(非 ~1ms,FTS trigram 索引同步写入是真实成本)**④ 进程内零拷贝钩子链(<0.5ms)⑤ O(n) 浅拷贝组装 + 校验(<1ms)。合计上界 ~13ms,**可能超出 10ms 预算**;
- **预算复核(v1.10)**:阶段 1 落地 StorageWriter 后用真实 benchmark 复核 P95(性能基准独立于行为套件);若 user flush 超标,可选优化 = FTS 同步降级为 background(代价:FTS 索引落后消息表,影响 /recall 即时可见性,需评估)——此为开放优化点,不属 v1.0 冻结项,预算目标保持 <10ms 作为努力基准;
- **性质**:宿主实现验收基准(性能基准独立于行为套件,黄金用例管功能正确性,预算管实现质量);阶段 2 验收入项;
- **L1 流式路径**:维持现状(async generator 直传 + SSE 每帧 json.dumps 微秒级)——达标,不动。

### 18.7 接入指南性能条款(协议文档随附)

1. **同语言扩展的 GIL/阻塞边界**:同语言扩展与宿主共进程——钩子实现必须非阻塞 async;**CPU 密集型工作(嵌入计算/OCR/压缩)必须**走异语言独立进程或扩展自管 worker(线程池/子进程),严禁在钩子内做同步 CPU 密集计算;
2. **invoke_llm 是冷路径通道**:用于 after / on_error / setup / 后台任务;**禁止用于 before / inject_round**(直接加首 token 延迟,违反 §18.6 预算);
3. **异语言扩展避免高频钩子**(§14.8 重申并量化):inject_round / after_step / post_tool_call 每轮触发,全量快照经 stdio 的累计成本秒级——异语言扩展只挂低频钩子 + observe(L3)+ tool_executor(invoke_tool)+ storage 批量;
4. **慢客户端背压**:SSE 消费慢 → async generator 天然背压(事件流暂停),LLM 流受 activity_timeout 保护——行为可接受,外壳部署时注意代理超时配置(nginx keep-alive,老系统 Q7 知识延续);
5. **SessionStore 长期运行内存**:core 显式无清理策略(§13 契约)——外壳必须配置会话清理(长期运行的内存责任在外壳,性能提示随 SPI 交付);
6. **会话并发互斥**:同 session 并发对话由**外壳串行化**(§5,阶段 4 出口前于 server 层补 session 级 `asyncio.Lock`)——core 不提供会话级锁,并发安全是外壳责任(快照 extra 会话延续的恢复/写回依赖此前提)。
