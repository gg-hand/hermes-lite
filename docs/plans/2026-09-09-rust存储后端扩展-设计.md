# Rust 存储后端扩展（teage-storage-rust）— 设计

> 日期：2026-09-09。状态：设计定案（用户逐项确认）。
> 关联：`docs/plans/2026-09-09-存储扩展接管落盘-设计.md`（P-4/P-5 前置设计）、
> `docs/plans/2026-09-08-统一扩展目录树-设计.md`（P-1 manifest 体系）、
> `teage_liu2/PROTOCOL/PENDING.md`（协议演进追踪）。

## 1. 目标

以 **Rust 实现的异语言存储后端扩展** 接管 liu2 全部落盘（`StorageProvider` +
`HistoryStore`/`MessageStore` 双通道），作为 **首个真实异语言后端** 兑现：

- **P-2**：异语言 stdio 扩展全链路实战验证（spawn→握手→钩子/落盘→shutdown）；
- **P-4**：storage-stdio 线协议语义条款逐条实战验证；
- **P-5**：宿主组件插槽契约经真实 backend 实战验证；
- **P-6（新登记）**：宿主组件 backend 目录发现——存储后端与普通枝干扩展一样
  纳入统一扩展目录树（manifest 体系）管理。

core 零改动铁律不动摇：core 不知道任何枝干/backend 名字，所有接线在
`server/`（host_components 装载器）与既有 `core/extension_loader.py` 扫描识别。

## 2. 决策记录（用户定案）

| 决策点 | 结论 |
|---|---|
| 存储引擎 | **rusqlite（SQLite）**，WAL 模式；schema 语义对照 core 的 `SQLiteHistoryStore`/`SQLiteStorageProvider`；FTS5 不启用（契约只要求子串匹配） |
| 源码落位 | **仓库内开发入库**（cargo 单 crate）；编译产物作为**正式扩展**安装到扩展目录 |
| 目录树关系 | **与普通扩展一样纳入管理**——放 `data2/extensions/storage_rust/`（manifest 白名单 `^[a-z0-9_]+$` 禁连字符），manifest 声明身份 |
| 宿主引用方式 | **extension 名引用（目录发现）**：config `options: {extension: storage_rust}`，宿主读 manifest 拿 command（参考 VSCode 扩展规范） |
| 数据文件 | 新库从零开始，不迁移存量（沿袭存储接管设计 §2）；路径由 config `args` 显式传入 |

## 3. 总体架构与源码落位

```
storage-rust/                     ← 仓库内源码（cargo 单 crate，正式入库）
├── Cargo.toml                    ← 依赖：rusqlite(bundled) / serde+derive / serde_json / uuid
├── README.md                     ← 构建/安装两步说明
├── manifest.yaml                 ← manifest 模板（安装时拷入扩展目录）
└── src/
    ├── main.rs                   ← 启动：--db 解析、建库建表、进入主循环
    ├── proto.rs                  ← P-4 帧读写（JSON Lines / UTF-8 / hello / bye）
    ├── dispatch.rs               ← op 分发 + 参数校验（缺字段/类型错 → ok:false）
    ├── docs.rs                   ← StorageProvider 语义（doc_* 表）
    └── history.rs                ← sessions/messages 语义（schema 与 core 兼容）

data2/extensions/storage_rust/    ← 安装态（gitignore，扩展目录树标准位置）
├── manifest.yaml                 ← 从源码树拷入
└── teage-storage-rust.exe        ← cargo build --release 产物
```

**安装流程**（两条命令，写进 crate README，不做安装脚本）：

```powershell
cargo build --release
Copy-Item target\release\teage-storage-rust.exe, manifest.yaml `
    D:\...\teage-liu\data2\extensions\storage_rust\
```

**SQLite schema 与 core 完全兼容**：sessions/messages/doc_* 表结构与
`core/history.py`、`core/storage.py` 同构（含 title/is_error/attachments/
message_type/reasoning/content_blocks 列）——新库从零开始不迁移，但保留
未来互查/回切 SQLite 默认后端的能力。

## 4. Rust 后端设计

### 4.1 并发模型（关键取舍）

**单线程同步循环，零 async**：

```
stdin 逐行读(BufRead) → serde_json 解析 → dispatch → 同步处理 → stdout 写帧 + flush
```

- P-4 条款⑥本就要求"单进程内串行应答（一请求一响应）"，单线程天然满足；
- rusqlite `Connection` 非 `Sync`，单线程恰好绕开该限制；
- 不引 tokio：编译产物小、出错面小、行为可预测。

SQLite 侧：`journal_mode=WAL` + 每请求事务提交——进程崩溃不损已确认数据。

### 4.2 模块划分（小单元，可独立理解）

| 模块 | 职责 | 依赖 |
|---|---|---|
| `main.rs` | 解析 `--db`（必填，缺参退出非 0）、打开 Connection、PRAGMA、建表、主循环收尾（EOF/bye → flush → exit 0） | 其余模块 |
| `proto.rs` | 帧编解码：请求 `{id,op,p}` / 响应 `{id,ok,r|e}`；hello 握手（上报自身 version，major 对齐 `0.x` 契约）；bye；非 UTF-8/非 JSON 行防御；UTF-8 显式写出（stdout 全程 `Write` byte 接口，无 Windows 编码坑） | serde_json |
| `dispatch.rs` | op → 处理函数映射；参数逐字段校验（缺字段/类型不符 → `ok:false` 可读错误）；未知 op → `ok:false`；单请求 `catch_unwind`（panic 转 `ok:false`，进程不崩） | docs/history |
| `docs.rs` | doc_* 表：kind 白名单校验（`^[a-z0-9_.]+$`，双重防线第二道）、表名映射（点转下划线）、write 单条/批量（同事务原子，恒返回 doc_id **数组**）、read/query（json_extract filters 精确匹配 + rowid 写入序 + limit）/delete | rusqlite, uuid |
| `history.rs` | sessions/messages：`ensure_session`(INSERT OR IGNORE)、`log_message`（全字段 + updated_at 同步）、`get_session_messages`（limit 取最近 N 条正序返回 / before_id 游标）、`update/get_session_title`、`search_messages`（LIKE 子串，`%_\` 转义） | rusqlite |

### 4.3 语义细节（对齐并澄清 P-4 条款）

1. **doc_id**：uuid v4 hex（32 字符小写），与 core 实现一致；
2. **write 响应 `r` 恒为 doc_id 数组**（条款④）：单条/批量统一数组，顺序对应 docs；
3. **query 的 filters 与 limit 先后序**：Rust 实现 = **先 filters 过滤、后 limit**
   （`WHERE json_extract(...)=? ... ORDER BY rowid ASC LIMIT ?`）——比 core 现实现
   （先 LIMIT 后内存过滤，可能返回少于 limit 条）更合理；**该差异作为 P-4 语义
   条款澄清项登记**，入协议时以"过滤在前"为准；
4. **search_messages**：LIKE 子串（条款⑤契约最低要求），FTS5/trigram 不启用，
   留作后续性能观察项；
5. **错误即 `ok:false`**：任何参数/SQL 错误都不终止进程，逐请求可读报错；
6. **启动快速失败**：`--db` 缺失/不可打开 → stderr 可读错误 + 退出非 0
   （宿主握手竞速立即失败）。

### 4.4 依赖清单（Cargo.toml）

| crate | 用途 | 说明 |
|---|---|---|
| `rusqlite`（feature `bundled`） | SQLite | 静态编译，免系统依赖 |
| `serde_json` | 帧编解码 | 逐字段手动校验（不用 derive/deny_unknown_fields，前向兼容） |
| `uuid`（feature `v4`） | doc_id 生成 | simple 格式 32 hex，对齐 core `uuid4().hex` |
| `chrono` | created_at 时间戳 | `%Y-%m-%dT%H:%M:%S%.6f` 对齐 Python `isoformat()` |

不引 tokio/async/runtime。

## 5. manifest 扩展与目录发现（协议候选 P-6）

### 5.1 manifest 新字段 `kind`

```yaml
# data2/extensions/storage_rust/manifest.yaml
name: storage_rust            # 目录名同名（白名单 ^[a-z0-9_]+$，禁连字符）
version: 0.1.0
kind: host-component          # 新字段：branch（缺省，兼容存量）| host-component
slots: [storage, history]     # host-component 必填：声明可接管插槽（值域 = SLOTS 白名单）
language: other
transport: stdio
command: [teage-storage-rust.exe]   # 相对 manifest 所在目录解析
capabilities: []              # host-component 必须为空（钩子授权面不适用）
description: Rust 存储后端（storage-stdio 线协议实现）
```

校验规则（在 P-1 既有规则上追加）：
- `kind: host-component` 时：`slots` 必填且 ⊆ 宿主 SLOTS 白名单；`capabilities`
  必须为空数组；`language: other`（transport: stdio + command 必填随 language
  校验强制）；
- `kind: branch`（缺省）：行为与 P-1 现状完全一致（audit/guardrails 零影响）；
- 未知字段拒绝（含 `kind`/`slots` 键本身在 branch 语境下的非法组合按规则报错）。

### 5.2 宿主侧改动（两处，均在既有机制上扩展）

**① `core/extension_loader.py`**（扫描识别，不装载）：
- 扫描时识别 `kind: host-component` → **不作为 branch 装载**、不进入 registry；
- config `core.branches` 声明了 host-component 扩展名 = 启动失败（防误配）；
- 发现结果可供 host_components 查询（ExtensionSpec 复用，server→core 方向合法）。

**② `server/host_components.py`**（stdio-proxy 工厂扩展）：
- `options.extension`（与 `options.command` **二选一**，同时给出 = 报错）；
- 按 `extensions_root/<extension>/manifest.yaml` 严格校验（kind=host-component、
  transport=stdio、slots 覆盖请求插槽）→ 组装
  `command = manifest.command（相对 manifest 目录解析）+ options.args` →
  交 `StdioStorageProxy`；
- `options.args`（可选，字符串数组）：追加到 command 后（如 `--db` 传参通道）。

### 5.3 配置形态

```yaml
core:
  extensions_root: data2/extensions
host_components:
  - slot: storage
    backend: stdio-proxy
    options:
      extension: storage_rust                 # 目录发现（替代直写 command）
      args: ["--db", "data2/storage_rust/sessions.db"]
      request_timeout_seconds: 10
```

## 7. 验收

1. **后端独立冒烟**（仓库外/命令行管道，临时件用完即删）：
   echo JSON 帧管道联调——hello → write（单条/批量）→ read → query（filters/limit）
   → log_message → get_session_messages → search_messages → delete → bye；
2. **端到端**：`extension: storage_rust` 启动 liu2 → 聊天若干轮 → 重启 →
   会话历史与 doc 数据由后端完整重建；
3. **快速失败**：manifest 坏 / kind=branch 被当 backend 引用 / slots 未声明 /
   握手 major 不匹配 / `--db` 缺参 / options.command 与 extension 同时给出 →
   全部启动失败且错误可读；
4. **回归**：不配 `host_components` 时默认 SQLite 行为与现状完全一致；
   audit/guardrails（kind 缺省 branch）装载不受影响。

### 验证边界（仓库纯净）

按仓库纯净原则，**不在仓库内写任何测试文件**（含 Rust `#[cfg(test)]` 内联测试）。
行为验证一律在仓库外临时目录（如 `d:/tmp/`）以管道/临时脚本完成，用完即删。
