# Agent 自主协作架构重设计

> 日期：2026-07-23
> 状态：设计已确认，待实现
> 背景：当前 Director 中心化任务分派模式偏离了"多 agent 间相互沟通与协作"的核心目标

## 1. 问题诊断

### 1.1 当前模式的问题

| 问题 | 根因 | 表现 |
|------|------|------|
| 协作消息侵占对话页面 | `appendCollabMessage` 直接 append 到主对话 `#messages` | 用户对话被 task/assign/result 消息打断 |
| Director 角色错位 | `_dispatch_tasks` 是中心化任务路由器 | Director 变成"掌控者"而非"指导者" |
| Agent 间无直接通信 | 所有协作经 Director 中转 | Agent 无法自主协作，依赖 Director 分派 |
| 工作台定位偏差 | 工作台=操作平台而非观察窗口 | 过度强调工作台作用，忽视 agent 自主性 |

### 1.2 核心偏差

当前是**中心化分派模式**：
```
用户 → Director(分派) → Worker(执行) → 结果返回
```

期望是**去中心化协作模式**：
```
         ┌──────────────────────────────────┐
         │       工作台（独立协作平台）        │
         │  collaboration.md · 观察窗口       │
         │  Director 接口 · 用户广播入口      │
         └──────┬───────────────┬───────────┘
                │ 接入           │ 接入
         ┌──────▼────┐    ┌─────▼─────┐    ┌─────────┐
         │  Agent A  │◄──►│  Agent B  │◄──►│ Agent C │  ...（平级）
         └───────────┘    └───────────┘    └─────────┘
                │               │               │
                └───────────────┴───────────────┘
                        ↑ 按需插入
                  Director（观察者/引导者）
                        ↑ 透明观察
                     用户（工作台窗口）
```

**关键**：工作台是脱离本地 agent 的独立协作平台，本地运行的 agent 只是附带了工作台入口（便利），不是工作台的主宰。所有接入工作台的 agent 严格平级。

## 2. 设计理念

### 2.1 四个角色的定位

| 角色 | 定位 | 默认状态 |
|------|------|---------|
| **工作台** | 独立协作平台，脱离本地 agent 存在 | 中立平台 |
| **Agent** | 协作主体，平级参与，自主通信协调 | 主动 |
| **Director** | 按需插入者，默认不介入 | 静默观察 |
| **用户** | 透明观察者 + 可直接发起广播/干预 | 观察为主 |

### 2.2 核心原则

1. **Agent 自主协作为主体**：agent 之间能自发通信、分工、协调，不依赖 Director 发起
2. **工作台首先是透明观察窗口**：让 agent 的交流在用户眼中透明，这是最基本的功能
3. **Director 是按需插入者**：默认不介入，只在需要时插入引导/规则/应急
4. **Director 是接口而非固定角色**：可以是 agent、用户、脚本，通过统一接口干预协作

### 2.3 工作台独立平台定位

工作台是**脱离本地 agent 的独立协作平台**：

- 工作台有自己的消息空间（collaboration.md）、观察窗口、Director 接口
- 本地运行的 agent 只是"附带工作台入口"的便利，不是工作台的主宰
- 任何 agent（本地/远程）都可以接入工作台，平级参与协作
- 用户可以直接在工作台发布广播消息，发起协作，不经过任何特定 agent
- 工作台是中立的协作空间，不偏向任何 agent

### 2.4 Agent 平级原则

工作台中所有挂载的 agent **严格平级**：

- 没有主从关系，没有"主 agent"概念
- 任何 agent 都可以自主发起协作（写 request 到 collaboration.md）
- 协作的分工由 agent 间自主协商，不由某个 agent 指挥
- 主对话的 agent 只是用户交互入口，进入工作台后与其他 agent 平级

### 2.5 协作发起方式

协作可以由多个主体发起（都是平级的）：

| 发起者 | 方式 | 场景 |
|--------|------|------|
| **任意 Agent** | 在 collaboration.md 写 `type=request` | agent 自主判断需要协作 |
| **用户** | 工作台"发布广播"入口，写 `type=request` from=user | 用户直接发起协作需求 |
| **Director** | 写 `type=directive` 引导协作方向 | Director 主动引导（少见） |

### 2.6 通信机制

采用**混合通信 + A2A 转发**：
- **黑板异步通信**（collaboration.md）：广播/异步协作，可审计，与现有架构兼容
- **A2A 点对点**（HTTP/JSON-RPC）：同步请求（如查询其他 agent 的能力/状态）
- **A2A 消息转发**：Agent 通过 A2A 收到消息后，转发一份带标识的消息到 collaboration.md，让工作台能观察到完整的 A2A 交流

#### A2A 消息转发机制

Agent 间的 A2A 直接通信不会被工作台阻断，但通过"转发"机制让工作台透明观察：

```
1. Agent A 通过 A2A 向 Agent B 发送消息（实时通信）
2. Agent B 收到后，转发一份到 collaboration.md，带标识：
   - from: agent_A（原始发送者）
   - to: agent_B（原始接收者）
   - via: a2a（通信方式标识）
   - forwarded_by: agent_B（谁转发的）
3. 工作台从 collaboration.md 看到完整的 A2A 交流过程
```

这样既保证了 A2A 的实时性，又让工作台能透明观察 agent 间的自主协作。

#### A2A 转发的消息去重

A2A 消息必须带 message_id，转发时保留原 ID。后端 append_collab_message 时检查 message_id 是否已存在，实现去重。

工作台提供标准转发 API 供外部 agent 调用：
```
POST /api/multiagent/collab/forward
{ message_id, from, to, content, via: "a2a" }
```

外部 agent 接入文档说明：调用此 API 即可让通信对工作台透明。单方转发即可观察（A 转发就能看到 A 视角的通信），但双方转发效果更好。

#### Director 注入对话上下文

Director 的引导不只写入 collaboration.md，而是**注入到 agent 的对话上下文**（LLM context），让 agent 自然感知：

```
1. Director 写 directive 到 collaboration.md（可审计记录）
2. 系统把 directive 注入相关 agent 的 LLM 对话上下文
3. Agent 的 LLM 在推理时"看到" Director 的引导
4. Agent 自主决定如何遵循引导
```

注入的上下文告知 agent：
- 当前协作中存在 Director 角色，其职责是协调和引导
- 当前的协作引导内容（如"按顺序读取弹幕"）
- Director 的规则是协调干预，agent 应适当遵循

这种方式让 Director 的引导对 agent 是"软约束"——像听到别人说话一样自然，agent 自主决定如何遵循。

#### 多通道 + 统一适配层

Agent 接入工作台后需要处理多个消息源（A2A、黑板、Director），通过内部的"消息适配层"统一处理：

协议栈层次：
```
┌─ 应用层：LLM 推理（看到统一消息格式）──────────────┐
│  "Agent A 说：..." | "Director 引导：按顺序读"      │
├─ 适配层：统一消息格式（工作台提供 SDK）─────────────┤
│  source/type/from/to/content/message_id             │
│  去重：相同 message_id 只处理一次                    │
│  合并：多通道同一消息只呈现一次                      │
├─ 协议层：A2A / 黑板轮询 / Director 推送 ────────────┤
│  HTTP/JSON-RPC | collaboration.md 轮询 | SSE/WebSocket│
└─ 传输层：HTTP / 文件系统 ───────────────────────────┘
```

统一消息格式（agent 内部处理用）：
```yaml
source: "a2a"          # 来源通道：a2a / blackboard / director
type: "relay"          # 消息类型
from: "agent_A"
to: "agent_B"
content: "..."
message_id: "msg_001"  # 去重用
via: "a2a"             # 通信方式（转发消息用）
rule_type: "ordering"  # directive 专用
task_op_id: "..."
```

工作台提供的接入支持：
- **SDK/工具库**：封装适配层、A2A、转发、黑板轮询（本地 agent 用）
- **标准 API**：HTTP 端点，远程 agent 调用
- **接入文档**：协议规范、消息格式、接入指南
- **A2A 扩展协议**：A2A 消息带 message_id 字段约定

#### 两个层面的明确分离

**层面 1：工作台协作空间（平级）**
- 所有 agent 在 collaboration.md 中平级参与协作
- Director 平等干预所有 agent
- 协作请求/响应/结果都在这个空间
- 不关心 agent 的用户服务

**层面 2：Agent 自身的用户服务（独立）**
- 每个 agent 可能有自己的用户服务（主对话）
- Agent 如何使用协作结果是 agent 自己的事
- 工作台不干预 agent 的用户服务

关键修正：协作结果注入的本质不是"工作台把结果注入 A 的主对话"，而是"A 在自己的主对话中引用协作结果"——这是 A 的用户服务行为，工作台只提供协作结果（在 collaboration.md 中）。

## 3. 消息物理分离

### 3.1 文件分离与拆分

| 文件 | 用途 | 消息类型 | SSE 通道 |
|------|------|---------|---------|
| `messages.md`（现有） | 主对话：用户 ↔ agent + 协作结果引用 | `chat`（含 `role: collab_progress/collab_result`） | `/api/multiagent/sse`（现有） |
| `collaboration.md`（新增） | 全局协作消息 | `announce`/广播 `request` | `/api/multiagent/collab/sse`（新增） |
| `collabs/{collab_id}.md`（新增） | 单个协作的消息 | `request`/`response`/`relay`/`result`/`directive`/`status` | `/api/multiagent/collab/{collab_id}/sse`（新增） |

文件结构：
```
data/blackboard/
├── messages.md              # 主对话
├── collaboration.md         # 全局协作消息（announce、广播）
└── collabs/
    ├── index.md             # 协作索引（collab_id → 标题/状态/参与者）
    ├── collab_001.md        # 协作 1 的消息
    └── collab_002.md        # 协作 2 的消息
```

### 3.2 分离原则

- 主对话页面渲染 `messages.md` 的 `type=chat` 消息（含协作结果注入的 `collab_progress`/`collab_result` 角色）
- 工作台渲染 `collaboration.md` 的完整协作消息
- 两套独立 SSE 通道，互不干扰
- 协作过程（relay/request/response）**不写入** messages.md，只在工作台可见
- 协作结果**摘要**注入 messages.md（以 agentB 角色消息形式），让主对话保持流畅
- `appendCollabMessage` **彻底删除**，不再侵入主对话

## 4. collaboration.md 消息类型

### 4.1 消息类型定义

```yaml
# relay：agent 间直接通信（自主协作的基础）
from: agent_A
to: agent_B          # 或 "*" 广播
type: relay
content: "我读完了第3条弹幕，内容是..."
target_agents: [agent_B]   # 定向或空=广播
seq: 1

# request：请求其他 agent 协作
from: agent_A
type: request
content: "需要有人分析弹幕情感"
capabilities_needed: [sentiment_analysis]
task_op_id: "xxx"
seq: 2

# request 消息扩展字段
collab_id: "collab_001"        # 协作会话 ID（关联所有相关消息）
collab_type: "continuous"      # continuous（持续型）/ task（任务型）/ instant（即时型）
timeout: 3600                  # 超时秒数（可选，instant 型用）
wait_for: "all"                # all（等所有响应）/ any（任一即可）
message_id: "msg_001"          # 消息唯一 ID（A2A 转发去重用）

# response：对协作请求的响应
from: agent_B
type: response
reply_to: 2          # 指向 request 的 seq
content: "我可以做，给我弹幕内容"
accept: true
seq: 3

# result：协作结果
from: agent_B
type: result
reply_to: 2
content: "情感分析完成：正面75%"
status: completed
seq: 4

# directive：Director 按需插入（默认不存在）
from: director
type: directive
content: "请按顺序读取弹幕，A 读完 B 再回应"
rule_type: ordering   # ordering/constraint/intervention
target: "*"           # 或特定 agent_id
seq: 5

# status：协作状态变更
from: agent_A
type: status
collab_id: "collab_001"
status: "suspended"            # initiated/active/suspended/completed/timeout/abandoned
reason: "任务阶段性完成"
seq: 6
```

### 4.2 schema 扩展

`messages_md.schema.yaml` 扩展 collaboration 类型：
- 新增 type 枚举值：`relay`, `request`, `response`, `directive`, `announce`
- 新增可选字段：`capabilities_needed`, `accept`, `rule_type`, `target`, `action`, `capabilities`, `endpoint`, `agent_name`, `via`, `forwarded_by`
- `via`：通信方式标识（`a2a`/`blackboard`），用于 A2A 消息转发
- `forwarded_by`：转发者 agent_id，标识谁把 A2A 消息转发到黑板
- `task_op_id` 用于关联协作请求链
- `reply_to` 指向原消息 seq
- `from` 字段允许 `user`（用户直接发起）和 `director`（Director 引导）
- `priority`：消息优先级（`high`/`normal`/`low`），用于 directive 字段级强化
- `deadline`：期望生效时限（秒），用于 directive 强化
- `issued_by`：directive 发出者标识（`AgentDirector`/`UserDirector`/`ScriptDirector`）

## 5. Agent 发现与接入机制

### 5.1 混合发现机制

Agent 之间通过三层机制相互发现：

| 层 | 机制 | 用途 |
|----|------|------|
| **Registry 目录** | Agent 注册 agent_id/endpoint/status/capabilities | 中心化目录，查询可用 agent |
| **黑板广播** | Agent 在 collaboration.md 写 `type=announce` | 动态上线/下线通知，能力声明 |
| **A2A 查询** | Agent 通过 A2A 协议查询 `/.well-known/agent.json` | 实时查询 agent card 详情 |

### 5.2 Agent 接入工作台流程

```
1. Agent 启动 → 向 registry 注册（agent_id, capabilities, endpoint, status=active）
2. Agent 在 collaboration.md 写 type=announce："我上线了，能力=[xxx]"
3. 工作台监听 registry 变化 + collaboration.md 的 announce 消息
4. 工作台自动将新 agent 纳入观察范围（显示在 agent 列表）
5. Agent 开始轮询 collaboration.md，参与协作
6. Agent 退出 → registry 更新 status=inactive + collaboration.md 写 announce："我下线了"
```

### 5.3 announce 消息类型（新增）

```yaml
# announce：agent 上线/下线/能力声明
from: agent_A
type: announce
action: online        # online/offline/capability_update
capabilities: [sentiment_analysis, text_summary]
endpoint: "http://localhost:8001"
agent_name: "情感分析助手"
seq: 1
```

### 5.4 工作台的 Agent 列表

工作台维护一个动态 agent 列表：
- 来源：registry + collaboration.md 的 announce 消息
- 显示：agent_id、名称、能力、状态（active/inactive）、endpoint
- 自动更新：监听 registry 变化和 announce 消息
- 用户可在工作台查看所有接入的 agent（平级展示，无主次）

## 6. Agent 自主协作机制

### 6.1 协作流程（读弹幕场景示例）

```
场景A：用户在工作台直接发起
1. 用户在工作台"发布广播"："帮我读直播间弹幕并讨论"
2. collaboration.md 写入 type=request, from=user
3. 接入工作台的 agent 轮询看到 request，自主决定参与
4. 参与的 agent 写 response（accept）
5. Agent 间通过 relay 直接协调："我读第1条" "好，我读第2条"
6. 如果协作混乱 → Director 检测到/被请求 → 写 directive："按顺序读"
7. Agent 遵循 directive 调整协作
8. 协作完成 → result
9. 用户在工作台观察全过程（透明）

场景B：agent 自主发起
1. 某个 agent 在工作中发现需要协作
2. 该 agent 在 collaboration.md 写 type=request："需要情感分析能力"
3. 其他 agent 看到后自主响应
4. 后续流程同上
```

### 6.2 Agent 协作轮询

Worker adapter 的 `_task_poll_loop` 改造为 `_collab_poll_loop`：
- 轮询 `collaboration.md` 而非 `messages.md`
- 扫描 `type=request` 且 `target_agents` 包含自己（或广播）的消息
- 扫描 `type=directive` 且 `target` 包含自己（或 "*"）的消息
- 自主决定是否参与协作请求
- 通过 relay/response 消息与其他 agent 直接通信

### 5.3 Agent 自主决策

Agent 收到协作请求后，自主判断：
1. 是否有能力处理（检查 `capabilities_needed`）
2. 是否有空闲（检查当前协作负载）
3. 决定是否参与（写 response，accept=true/false）
4. 参与后通过 relay 与其他 agent 协调

## 6.x 协作生命周期管理

### 三种协作模式

| 模式 | 生命周期 | 结束方式 | 示例 |
|------|---------|---------|------|
| **即时型（instant）** | 短暂，请求-响应-结果 | 自然结束 | A 调用 B 分析弹幕情感 |
| **任务型（task）** | 中等，完成大型任务 | 显式标记完成/暂停 | 多 agent 协作写报告 |
| **持续型（continuous）** | 长期，持续运行 | 显式结束 | 直播读弹幕互动 |

### 协作状态

通过 type=status 消息标记协作状态变更：
- initiated：发起协作请求
- active：有 agent 响应并参与
- suspended：暂时挂起（任务型协作中间停顿）
- completed：协作完成
- timeout：超时
- abandoned：放弃

### 超时与异常处理

| 场景 | 处理方 | 机制 |
|------|--------|------|
| 即时型超时 | 发起者 A | A 自主判断超时，写 status(timeout) |
| 参与者掉线 | Director(ScriptDirector) | 检测 agent 状态变更，通知发起者 |
| 协作死锁 | Director(ScriptDirector) | 检测无进展，写 directive(intervention) |
| 用户主动终止 | 用户/Agent | 写 status(abandoned) |

关键：超时和异常由发起者自主管理，Director 作为兜底干预。工作台不强制生命周期管理——agent 可以选择忽略 collab_id，每次 request 都独立处理。

## 6. Director 接口化

### 6.1 Director 协议接口

Director 不是固定角色，而是**可插拔的接口协议**：

```python
class DirectorProtocol(ABC):
    """Director 协议：定义干预 agent 协作的标准操作。"""

    @abstractmethod
    async def inject_directive(self, content: str, rule_type: str,
                               target: str = "*") -> None:
        """主动注入协作引导（双通道）。

        1. 写入 collaboration.md（可审计记录）
        2. 注入目标 agent 的 LLM 对话上下文（agent 自然感知）

        Args:
            content: 引导内容（自然语言描述的协作约束）
            rule_type: ordering（顺序约束）/ constraint（规则约束）/ intervention（应急干预）
            target: 目标 agent_id 或 "*"（全部）
        """

    @abstractmethod
    async def handle_arbitration(self, request: dict) -> dict:
        """处理 agent 的仲裁请求（被动响应）。

        当 agent 间出现分歧时，可向 Director 发起仲裁请求。
        """

    @abstractmethod
    async def observe(self) -> dict:
        """观察协作状态（用于异常检测）。"""
```

### 6.2 Director 双通道注入机制

Director 的引导通过两个通道同时传递：

```
通道1：collaboration.md（可审计）
  - 写入 type=directive 消息
  - 工作台可展示 Director 的引导
  - 历史可追溯

通道2：LLM 对话上下文注入（agent 自然感知）
  - 系统把 directive 注入目标 agent 的 LLM context
  - Agent 在推理时"看到" Director 的引导
  - 像听到别人说话一样自然
  - Agent 自主决定如何遵循（软约束）
```

**注入的上下文格式**：
```
[Director 引导]
角色提示：当前协作中存在 Director 角色，其职责是协调和引导协作。
当前引导：请按顺序读取弹幕，A 读完 B 再回应。
引导类型：ordering（顺序约束）
来源：AgentDirector | 时间：2026-07-23 15:30
```

这种双通道机制确保：
- 工作台用户能看到 Director 的引导（透明）
- Agent 的 LLM 能自然感知引导（无需轮询）
- 引导是软约束，agent 自主决定遵循程度

### Director directive 的"搭便车"机制

directive 不触发独立 LLM 调用，零额外成本：

1. 适配层收到 directive → 存入"待注入上下文"队列
2. Agent 因任何原因调用 LLM 时（处理 request、A2A 通信等）
3. 适配层自动把队列中的 directive 拼到 system prompt
4. 清空队列

这样 directive 是"搭便车"注入的，不需要额外 LLM 调用。

### 6.3 三种 Director 实现

| 实现 | 谁来充当 Director | 适用场景 | 干预方式 |
|------|-------------------|---------|---------|
| `AgentDirector` | LLM 驱动的 agent | 自动引导 | agent 自主判断何时注入 directive |
| `UserDirector` | 用户亲自坐镇 | 手动干预 | 用户通过工作台 UI 注入 directive |
| `ScriptDirector` | 脚本/规则引擎 | 异常检测 | 基于条件自动触发（超时/死锁/冲突） |

### 6.4 Director 插入时机

| 时机 | 触发方式 | directive 类型 | 谁触发 |
|------|---------|---------------|--------|
| 用户请求引导 | 工作台"注入引导"入口 | ordering / constraint | UserDirector |
| Agent 请求仲裁 | agent 写 request to director | intervention | 任意 Director |
| 异常检测 | Director 引擎检测死锁/冲突/超时 | intervention | ScriptDirector / AgentDirector |

### 6.5 关键设计

- Director 默认**不写入任何消息**，collaboration.md 纯粹是 agent 间的协作空间
- Director 只在上述时机插入 directive（双通道：collaboration.md + LLM 上下文注入）
- Agent 的 LLM 自然感知 directive，自主决定遵循程度（软约束）
- Director 类型可在配置中切换，甚至可以**混合**（如 ScriptDirector 做异常检测 + UserDirector 做手动干预）
- 切换 Director 实现不需要改协作机制，agent 端代码完全不变

## 10. 主对话协作结果注入机制

### 10.1 双视图模式

协作过程和结果在两个视图中有不同的表现：

| 视图 | 内容 | 目的 |
|------|------|------|
| **工作台** | 完整协作过程（relay/request/response/result/directive） | 透明观察 |
| **主对话** | 协作摘要 + 结果注入（以 agentB 角色消息形式） | 保持对话流畅 |

### 10.2 主对话中的协作表现

协作不侵入主对话的消息流，但协作结果以"角色消息"形式注入：

```
主对话视图（简洁，保持对话流畅）：

用户：帮我读直播间弹幕并讨论
AgentA：好的，我需要情感分析能力，调用 AgentB 协作...
[系统提示] AgentB 正在分析...           ← 协作进度提示
[AgentB] 情感分析完成，正面75%          ← 协作结果注入（角色消息）
AgentA：根据 AgentB 的分析，弹幕整体偏正面...
```

```
工作台视图（完整，透明观察）：

🎯 AgentA → request: "需要情感分析能力"
✅ AgentB → response: "我可以做情感分析"
💬 AgentA → relay: "这是弹幕内容..."
💬 AgentB → relay: "正在分析..."
💬 AgentB → relay: "正面75%"
📋 AgentB → result: "情感分析完成：正面75%"
```

### 10.3 协作结果引用流程（修正）

协作结果注入的本质不是"工作台把结果注入 A 的主对话"，而是"A 在自己的主对话中引用协作结果"：

1. AgentA 自主发起对 AgentB 的协作（写入 collaboration.md）
2. AgentA 在主对话中通知用户："调用 AgentB 协作..."
3. 系统在主对话显示进度提示："AgentB 正在分析..."
4. AgentB 协作完成，写入 result 到 collaboration.md
5. AgentA 读取 result，自主决定如何呈现给用户
6. AgentA 在主对话中以"AgentB 角色"形式展示协作结论
7. AgentA 继续与用户交流

这是 A 的用户服务行为，工作台只提供协作结果（在 collaboration.md 中），不主动"注入"到主对话。

### 10.4 主对话注入的消息格式

主对话中注入的协作消息使用特殊标识，区别于普通 chat：

```yaml
# 进度提示（协作中）
type: chat
from: system
role: collab_progress
content: "AgentB 正在分析..."
collab_with: agent_B
task_op_id: "xxx"

# 结果注入（协作完成）
type: chat
from: agent_B          # 以 agentB 角色显示
role: collab_result    # 标识：这是协作结果注入
content: "情感分析完成，正面75%"
reply_to: null         # 不需要回复
task_op_id: "xxx"      # 关联协作任务
```

前端根据 `role` 字段渲染：
- `collab_progress`：简洁的进度提示（灰色小字）
- `collab_result`：以 agentB 角色显示的消息（带 agent 标识）

## 12. LLM 调用成本控制：A2A 主泵 + 消息队列 + 紧急插队

### 12.1 核心思路

**A2A 是 LLM 主动决策的产物，这次 LLM 调用必然发生，其他协议消息搭它的便车是最省成本的方案。** 但完全按 A2A 频率传递会有三个边界问题需要处理：

1. **频率不同步**：A2A 频率由 LLM 推理决定，可能很活跃也可能长时间静默；黑板消息异步到达，可能滞留
2. **紧急消息被延迟**：Director 的 `intervention`（应急干预）、用户主动广播需要及时响应
3. **适配器的"何时送"决策缺失**：需要明确何时把累积消息送入 LLM

### 12.2 架构：A2A 主泵 + 双队列 + 紧急插队 + 空闲保护

```
┌─ Agent 内部 ─────────────────────────────────────┐
│                                                  │
│  ┌─ 协议层 ─────────────────────────────────┐    │
│  │ A2A 监听 │ 黑板轮询 │ Director 推送      │    │
│  └────┬──────────┬───────────┬──────────────┘    │
│       │          │           │                   │
│       ▼          ▼           ▼                   │
│  ┌─ 适配层：双队列（按优先级）──────────────┐    │
│  │  紧急队列：intervention / 用户广播       │    │
│  │  普通队列：relay / request / directive   │    │
│  └────┬────────────────────────┬─────────────┘    │
│       │ 搭便车                  │ 立即触发        │
│       │ （A2A 调用时）          │ （仅紧急）      │
│       ▼                        ▼                 │
│  ┌─ 应用层：LLM 推理 ──────────────────────┐     │
│  │ system prompt + 队列消息 + 对话上下文   │     │
│  └────┬────────────────────────────────────┘     │
│       │ LLM 决策                                │
│       ▼                                         │
│   A2A 调用（主泵）+ 队列清空                     │
│                                                  │
│  空闲超时保护：60s 无 A2A 且队列非空 → 触发调用  │
└──────────────────────────────────────────────────┘
```

### 12.3 消息分类与处理策略

| 消息类型 | 优先级 | 处理方式 | 是否触发 LLM 调用 |
|---------|--------|---------|:---:|
| `directive` + `rule_type=intervention` | 紧急 | 立即触发 LLM 调用 | ✅ 触发（例外） |
| 用户广播 `request` from=user | 紧急 | 立即触发 LLM 调用 | ✅ 触发（例外） |
| `directive` + `ordering`/`constraint` | 普通 | 入普通队列，搭便车 | ❌ 不调用 |
| `relay` / `request`（非用户）/ `response` / `result` | 普通 | 入普通队列，搭便车 | ❌ 不调用（已被 A2A 触发） |
| `announce` | 低 | 更新本地状态 | ❌ 不调用 |
| `status` | 低 | 更新协作状态 | ❌ 不调用 |

**关键：** `request` 和 `result` 的 LLM 调用是"不可避免的"（LLM 必须决策），它们本身就是 A2A 主泵的触发源，所以不算"额外"调用。普通队列中的其他消息（directive ordering、relay 记录）搭这些调用的便车。

### 12.4 A2A 作为"泵"的机制

A2A 调用必然伴随 LLM 调用，所以每次 A2A 调用前后：
1. **调用前**：适配器把普通队列消息拼到 system prompt
2. **LLM 推理**：同时看到 A2A 响应 + 队列累积消息
3. **调用后**：清空已注入的队列

这样 A2A 既是通信行为，也是消息泵，零额外成本。

### 12.5 紧急插队机制

只有以下两类消息允许触发额外 LLM 调用（非 A2A 触发）：

1. **`directive` + `rule_type=intervention`**：Director 应急干预（死锁、冲突、超时）
2. **用户主动广播 `request` from=user**：用户直接发起的协作需求

这两类消息很少见，成本可控。紧急消息不搭便车，直接触发 LLM 调用并置于 system prompt 顶部。

### 12.6 空闲超时保护

如果 agent 长时间不调用 A2A（如纯本地处理），但普通队列有消息：
- **阈值**：60 秒（可配置）
- **触发**：适配器主动触发一次 LLM 调用处理队列
- **目的**：防止消息长期滞留

### 12.7 Director directive 的字段级强化

普通 directive 搭便车可能被 LLM 忽略，通过字段级标识强化：

**消息字段强化**：
```yaml
type: directive
rule_type: ordering
content: "请按顺序读取弹幕"
priority: high          # 新增字段：标识重要性
issued_by: AgentDirector
deadline: 300           # 新增字段：期望生效时限（秒）
```

**注入格式强化**（搭便车时强化呈现）：
```
[⚠️ Director 引导 - 高优先级]
来源：AgentDirector | 类型：ordering（顺序约束）
内容：请按顺序读取弹幕，A 读完 B 再回应
期望生效：300 秒内
说明：当前协作中存在 Director 角色，其引导用于协调协作，请适当遵循。
```

`intervention` 类则不搭便车，直接触发 LLM 调用并置于 system prompt 顶部。

### 12.8 消息过滤

适配层过滤不需要 LLM 处理的消息：
- `target_agents` 不包含自己的广播 → 跳过
- 已通过 A2A 处理过的转发消息（相同 `message_id`） → 去重，只记录上下文
- `announce` 只更新本地状态，不传给 LLM
- `status` 只更新协作状态，不传给 LLM

### 12.9 成本估算

以直播读弹幕场景（持续型协作，1 小时）：
- A2A 通信触发 LLM 调用（主泵）：~60 次（每分钟一次决策）
- 紧急插队（intervention）：~2 次（少见，成本可控）
- 空闲超时触发：~5 次（agent 偶尔静默时）
- directive 搭便车注入：~5 次（零额外成本）
- relay 转发记录：~200 次（不调用 LLM）
- 总 LLM 调用：~67 次（可控）

## 13. 不做什么（YAGNI）

- **不做协作会话管理**（方案 C 的 sessions/<id>/messages.md）——过度设计
- **不做复杂协作 pattern 引擎**——directive 用自然语言描述，agent 自行理解
- **不做实时 agent 能力匹配**——agent 自主判断是否参与协作
- **不做协作回放**——collaboration.md 本身是审计日志
