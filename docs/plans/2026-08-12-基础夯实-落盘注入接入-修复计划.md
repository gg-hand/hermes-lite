## 1. D1:开放落盘平台(消息级落盘 + StorageProvider)(P0)

### 1.1 设计原则(定案)

> **核心提供极高自由度的落盘接口,子系统自主选择:经核心通道落盘,或自持存储。核心只保持最基本的稳定高效的最小实现。**

### 1.2 接口形态

```
core/storage.py(新)
├── StorageProvider(ABC)          # 通用持久化通道 —— 扩展接口
│     write(kind, doc) -> doc_id       # kind 命名空间:"messages" / "audit" /
│     read(kind, doc_id)               #   "memory.facts" / "collab" / 自定义…
│     query(kind, **filters)           # kind 白名单校验(^[a-z0-9_.]+$),防表注入
│     delete(kind, doc_id)
│     close()
├── SQLiteStorageProvider         # 默认实现(唯一实现):单库多 kind,
│                                  #   每 kind 一张 doc 表(doc JSON + created_at)
└── MessageStore                  # 主干最小实现:消息级落盘
                                   #   messages 专表:role/content(纯文本,FTS)/
                                   #   content_blocks(JSON,LLM 重建)/
                                   #   token_count/is_error/reasoning(D3 一并接线)
```

- 存储方案:加列 JSON(content_blocks TEXT;content 纯文本保 FTS;旧行回退);
- 共享 SQLite 连接(WAL + 锁);
- core 参数语义:`setup(config, core)` 的 core = 主干上下文对象(含 message_store / storage_provider / llm_client / hooks / pipeline / session_store / task_registry)。

### 1.3 消息级落盘触发(事件驱动,逐条即时写)

| 事件 | 落盘内容 |
|------|----------|
| (对话开始) | user 前置(已有) |
| step_end | assistant 消息(content_blocks JSON + 纯文本提取) |
| tool_result(本轮末) | user(tool_results)消息(配对 tool_use_id) |
| done | 收尾 |
| finally | 兜底(计数器跟踪已落盘数,断连不丢) |

## 2. I1:多层级注入平台(P0)

### 2.1 设计原则(定案)

> **核心提供多个层级的提示词注入接口,子系统按内容稳定度自主选择注入位置;核心只做收集、分层、预算裁剪、组装。**

### 2.2 注入层级(全定义全组装)

```
L0 STABLE_SYSTEM   system 稳定区(前缀缓存命中)     ← 画像主体/全局规则/工具说明
L1 SYSTEM          system 末位(缓存失效仍有效)     ← 会话级指令/临时全局上下文
L2 PREFIX          messages[0] 前置(缓存失效点)    ← 检索记忆/环境信息/任务状态
L3 MID             历史中间(按位插入)              ← 对话背景/长期上下文说明
L4 BEFORE_INPUT    当前输入前(最动态)              ← 意图引导/瞬时指令
```

### 2.3 接口形态

```python
# core/injection.py(新)
class Injection:
    layer: str          # STABLE_SYSTEM / SYSTEM / PREFIX / MID / BEFORE_INPUT
    content: str
    priority: int       # 同层内预算裁剪优先级(大者先保留)
    key: str            # 去重键(可选,同 key 后声明覆盖先声明)

async def build_injections(self, ctx) -> list[Injection]:
    """子系统声明注入项:位置 + 内容 + 优先级,自主控制。"""
    return []
```

- Branch.build_system/build_injection **直接替换**(不留兼容层);旧语义映射 STABLE_SYSTEM / PREFIX;
- 分层预算(默认可配):stable_system 4000 / system 2000 / prefix 8000 / mid 2000 / before_input 2000;层内 priority 降序 + 注册序稳定;整段丢弃不截半;
- 注入内容**永不落盘**(瞬时上下文,确认保持);
- **轮次间注入点(I2)**:loop 每轮 step 前调 `hooks.inject_round(ctx)`(骨架先加,M2 填内容)。

## 4. 编排定稿(审查 6 项完善 + 决策)(P1/P2)

### 4.1 时序全景图(定稿)

```
setup(启动,一次):
  registry 装配 → setup_all(失败 → 逆序 teardown 已成功枝干 → 抛错)   [E1]
│
chat_stream(每次对话):
  ① 读历史 → user 前置落盘
  ② BranchContext 构建(session_id/user_input/history/system_text/
     messages/tools/extra/stop/round/started_at)                    [E3]
  ③ build_injections_all → 多层级组装(L0→L4)
  ④ before_all(职责边界:追加消息/置 stop/改 tools,禁删改历史)       [E5]
  ⑤ 形态执行(接口化:m_mode 字典选择):                              [E6]
     loop 每轮: inject_round → step → [tool_use → dispatch_tool_call] → 消息落盘
  ⑥ done → after_all(AfterResponse);失败/断连/拦截 → on_error       [E2]
  ⑦ finally 兜底落盘
teardown(关闭,一次):
  shutdown():TaskRegistry 取消 → teardown 逆序 → storage.close       [E4]
```

## 6. 其余维度详细定稿(C1/S1/X1/L1/L2/O1/O2/F1/F2)

### 6.1 C1:消息合法性 —— core 的保证,双保险校验

- **文档契约**:before 只允许追加消息 / 置 stop / 改 tools;禁止删改历史与已组装注入;
- **运行时校验**(core 行为,~30 行):before 全部执行后 + 组装后,core 校验 `ctx.messages` 结构——角色顺序合法(首条非 tool、user/assistant 交替)、tool_result 配对 tool_use;
- 校验函数 `validate_messages()` 放 `core/types.py`;M1 做角色顺序校验,M2 工具消息接入时扩展配对校验;
- 不合法 → logger.error + 拒绝消息序列(发 error 事件,不发送给 LLM)。

### 6.2 S1:枝干状态三态模型(写入 SPI)

| 态 | 容器 | 生命周期 | 重启后 |
|----|------|----------|--------|
| 对话态 | `ctx.extra`(`{branch}.{key}`) | 一次对话 | 消失(契约) |
| 会话态 | `SessionStore`(core 提供,内存) | 一个会话 | **消失**(契约) |
| 持久态 | `StorageProvider`(自选 kind)或自持 | 枝干自管 | 保留(setup 时自恢复) |

- SessionStore 是**内存态**,跨重启状态必须经 StorageProvider/自持并在 setup 恢复;
- SessionStore 清理由调用方负责:core 提供 `session_store.drop(session_id)`,不自动清理。

### 6.3 X1:Branch 7 钩子契约表(SPI 主体)

| 钩子 | 时机 | 语义 | 超时 | 失败行为 | 约束 |
|------|------|------|------|----------|------|
| `setup(config, core)` | 启动一次 | 初始化启动必需资源 | 无 | 抛错=启动失败(逆序回滚) | 懒资源自管;顺序=注册序 |
| `teardown()` | 关闭/重建 | 释放资源+冲刷 | 无 | 仅告警(逆序继续) | **幂等可重入**(热重载) |
| `build_injections(ctx)` | 每次对话组装前 | 声明注入项 | 5s | 隔离跳过 | 注入永不落盘 |
| `before(ctx)` | 组装后 LLM 前 | 最后干预 | 5s | 隔离跳过 | 只追加/置 stop/改 tools |
| `on_tool_call(ctx, name, input)` | 工具请求 | 执行工具 | 无(工具自控) | 返回 error 结果回喂 LLM | 未实现返回 NotImplemented |
| `after(ctx, response)` | 正常完成 | 收尾(记忆/审计) | 5s | 隔离跳过 | 收 AfterResponse |
| `on_error(ctx, error)` | 失败/断连/拦截 | 失败通知 | 5s | 隔离跳过 | 逆序;不 yield;可 await |

**新增契约**:
1. **钩子内调 LLM 防递归**:枝干(after 记忆巩固)必须直调 `core.llm_client`,禁止调 `core.pipeline.chat_stream`(重入钩子链 → 递归);
2. **setup/teardown 可重建契约**:枝干必须幂等可重入(热重载反复调用)。

### 6.4 L1:shutdown 冲刷编排(幂等)

```
pipeline.shutdown()(幂等,可多次调用):
  ① TaskRegistry.cancel_all()   # 后台任务先停
  ② teardown_all()              # 枝干逆序,各自冲刷
  ③ message_store.close()
  ④ storage_provider.close()
```

- core 编排调用链,枝干负责自己的冲刷(teardown 内);core 不替枝干冲刷;
- M1 边界:活跃流优雅等待是 M2 项;幂等标志防重复执行。

### 6.5 L2:热重载 —— 被"枝干无依赖"化解的量级难题

- **M1 不实现热重载**,铺两条路:
  1. `registry.build(config)` 幂等可重入;
  2. 枝干 setup/teardown 可重建契约(6.3);
- **M2+ 提供 `registry.rebuild(config)`**(可选,~30 行):build 新链 → 成功则旧链 teardown+替换 → 失败保持旧链(回滚);
- 关键洞察:枝干间无依赖(SPI 铁律)→ 无级联重建问题,比老系统 container.reload(拓扑排序+级联+延迟关闭)简单一个量级。

### 6.6 O1/O2:观测完全枝干化 —— core 只供原材料

core 提供的观测原材料清单(不内置指标/审计):

| 原材料 | 形态 |
