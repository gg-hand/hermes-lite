## 2. 必须修复（4 项）

### FIX-1 [主要] 快照超限整批回滚 → 吞掉 `SetStop`，长会话安全拦截静默失效（**本次引入的回归**）

**证据（主 agent 实测，非推测）**
```
入参快照已超限(size=2616658) + 批次[SetExtra, SetStop] -> stop=False extra={} invalid=['快照体积…超上限…']
入参快照正常 (size=208)     + 批次[SetExtra, SetStop] -> stop=True  extra={'guardrails.denied': True}
```
`data2/extensions/guardrails/main.py` 的 block 批次正是 `[SetExtra, SetStop]`；`hooks.py` 仅在 `cur.stop` 为真时短路拦截。

**两条独立的失效路径**
1. **同批被整批丢弃**：批次里既有超限 `AppendMessage` 又有 `SetStop` 时，整批回滚 ⇒ 拦截连同标记一起丢。
2. **入参已超限 ⇒ 该会话所有钩子批次被永久拒绝**（更严重）：`core/pipeline.py` 构建初始快照时**不做**总体积校验（`messages = list(history) + [user]`，直接构造），而 `history_window_messages` 默认 100 × 单条可达 512 KiB ⇒ 初始快照理论上可达数十 MB。一旦超限，快照**永远不会缩回**，此后每一次 `apply_action_batch` 都被拒绝 ⇒ guardrails 拦截、`SetExtra` 全部无效，只剩一行 error 日志。

**定性**：修复前行为是"记 error 日志但照常应用"（拦截可用）；本次改动把告警升级为拒绝，却未处理"入参已超限"与"`stop` 语义"。**根因在计划（由本人编写）T5.1 的修复方向，实现者忠实执行**。

**修复建议**：只有当**入参快照本身未超限**时才判超限拒绝；入参已超限时记日志并放行（保留 set 类 action，尤其是 `stop`）。另加 2 条回归测试：①`[AppendMessage 超限, SetStop]` 同批 → `stop` 必须保留；②超限入参 + `[SetExtra, SetStop]` → 拦截必须生效。

### FIX-2 [主要] CI 首次运行必红：最小依赖缺 `python-dotenv`

**证据（主 agent 聚焦复测）**
```
$ python -c "import sys;sys.modules['dotenv']=None;import teage_liu2.core.config"
  File ".../teage_liu2/core/config.py", line 25, in <module>
    from dotenv import load_dotenv
ModuleNotFoundError
```
- `core/config.py:25` 是**模块级硬依赖**；
- `tests_core/test_config.py` 在模块级 `from teage_liu2.core.config import ...` ⇒ CI 的 pytest 步骤红；
- `runner.py` 在 `_run_config_case` 内 `from teage_liu2.core.config import core_config_from`，且该导入在 try 之外 ⇒ **用例 21 会抛 ImportError 中断整个套件进程**（不是单条 FAIL），CI 的套件步骤也红；
- `.github/workflows/liu2-audit.yml` 只安装 `pytest pyyaml jsonschema`。

**定性**：计划 T6.3 步骤 3 声称"可行性已核验：模块级三方依赖仅 `yaml`"——**该结论错误**（我的核验 grep 模式列表漏了 `dotenv`）。属主 agent 的核验方法缺陷。

**修复建议**：workflow 依赖加 `python-dotenv`；同步更正计划/开发日志中"最小依赖已核验"的表述（并注明 `llm.py` 的 config 导入是函数内懒加载，故用例 1~18 不受影响）。

### FIX-3 [主要] 新用例 19/20/21 违反 `suite.schema.json`（契约漂移，由本次改动引入）

**证据（主 agent 实测）**
```
suite.schema.json#/definitions/Expected: additionalProperties = False, properties = [event_stream, invocations, final]
19-hook-isolation.json  违反键=['error_codes']
20-error-codes.json     违反键=['error_codes']
21-config-domain.json   违反键=['error_codes']
18-storage-persist-timing.json  违反键=[]
```
`cases/*.json + suite.schema.json + matcher.schema.json` 是 `PROTOCOL/README.md` 明示的**语言无关交付物**：其他宿主按 schema 校验会直接拒绝这 3 个用例。

**修复建议**：`Expected` 增加 `error_codes` 定义（`must_include` / `must_exclude`：字符串数组，`additionalProperties: false`），并在 README 交付物说明里补一句断言键清单。

### FIX-4 [主要] `error` 事件的 `code` 零自动化锚定（契约已宣称"双通道对拍"）

**证据（主 agent 实测）**
- 全部用例的 `must_include` 中**没有** `LLM_TIMEOUT / LLM_CANCELED / LLM_STREAM_FAILED / LLM_API_ERROR / HOOK_INVALID_ACTION`（`cases/20-error-codes.json` 仅在**描述文本**里提到它们，不构成断言）；
- `tests_core/test_pipeline.py` 中 `code`/`LLM_*` 断言行数 = **0**（计划 T2.4 步骤 1 要求的测试未写）；
- 子智能体变异实测：把 `step.py` 产出的所有事件 `code` 键删除 → 套件仍 **21/21**、pytest 仍全绿。

**定性**：`errors.spec §5`「事件面」、`PENDING P-8`、开发日志均宣称事件面"已落地并对拍"，实际是"已实现、**无人验证**"——问题形态从"无发射点"变成了"有发射点但无锚定"。

**修复建议**：补 `test_pipeline.py` 断言（错误事件 `ev["code"] in ERROR_CODES`，覆盖 LLM_API_ERROR 与 HOOK_INVALID_ACTION 两条路径）；或让 case 16 的 error 场景带 `error_codes.must_include`。

## 5. 主 agent 自认的错误（本次工程）

1. **CI 可行性核验方法错误**：我用固定模式列表 grep 模块级三方 import，列表漏了 `dotenv`，却据此在计划里写下"最小依赖已核验"→ 直接导致 FIX-2。**教训：核验依赖完整性应基于"实际安装集 ⊆ 全部模块级 import"的差集，而非人工枚举。**

4. **过度承诺**：`errors.spec §5` / PENDING P-8 / 开发日志把"事件面已落地并对拍"写成了既成事实，实际零锚定 → FIX-4。**教训：契约措辞必须区分"已实现"与"已锚定"。**
