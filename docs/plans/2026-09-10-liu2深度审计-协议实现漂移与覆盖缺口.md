## 2. 发现详解

### F-1【高】行为套件的两处"假绿"断言：`persisted` 与 `isolation`

**事实**
- `suite.schema.json` 定义了 `FinalExpectation.persisted`（L66-69，注释"落盘断言（如消息已写入历史库）"）与 `InvocationExpectation.isolation`（L48-55，注释"隔离断言：timeout/error → skip"）。
- `runner.py:12` 的模块 docstring 明确承诺 `expected.final` 断言"termination_reason / is_complete / **persisted**"。
- 但实现里：
  - `_assert_final`（L321-336）**只**处理 `termination_reason` 与 `is_complete`，`persisted` 被完全忽略；
  - `_assert_invocations`（L290-318）只处理 `hook/extension/order/absent/snapshot_assert/actions_assert`，**无** `isolation`。
- 穷举 17 个用例：`persisted` 字段 **0 次使用**；`isolation` 字段 **0 次使用**（唯一 grep 命中是同名不同义的 `prefix_isolation`，见 `06-storage-spi.json`）。

**影响（为什么是"高"）**
1. **假绿风险**：用例作者按 schema 写 `"final": {"persisted": {...}}`，runner 不报错、不校验、直接 PASS —— 断言被吞掉，审计结论失真。这是比"缺覆盖"更危险的一类问题。
2. **后果性缺口**：storage 域 **S-1「落盘时机」**（user 前置 → step_end 落 assistant → tool_result 聚合落 user → finally 兜底；注入永不落盘）是整份协议里唯一**没有任何协议级用例**承载的核心行为条款，而它恰好是生产上出过事故的地方（`after` 钩子永不触发的历史缺陷）。
3. **同类缺口**：hooks 域 **H-6「钩子超时隔离」**（超时跳过该扩展并记日志）同样零覆盖。

### F-2【高】协议交付物依赖仓库测试目录

**事实**：`teage_liu2/PROTOCOL/behavior-suite/runner.py:61`

```python
from teage_liu2.tests_core.fake_llm import FakeLLMClient  # noqa: E402
```

**影响**
- 行为套件是 PROTOCOL 的交付物，定位为"语言无关黄金用例 + 新宿主验收门槛 + 漂移审计工具"；其**唯一参考执行器**却 import 了 Python 单测资产（`tests_core/`，13 个 test 文件 1836 行 + `fake_llm.py` 84 行 + `tests_branches/` 99 行）。
- 与「代码仓库纯净原则」直接冲突：若按规则移除 `tests_core`，协议审计工具立即不可运行；反之，若要保住套件，`tests_core` 就必须长期驻留仓库。
- 这是一个**需要用户裁决的结构性矛盾**：要么把 `FakeLLMClient` 提升为 PROTOCOL 自带的"中立桩"（推荐，形成自洽闭包），要么正式承认 `tests_core` 是协议交付物的一部分（豁免于纯净规则）。

### F-3【中高】错误码双轨、互不登记、覆盖严重不对称

**事实 A —— 存在两套并行的错误码族**

| 族 | 位置 | 命名风格 | 数量 | 入 spec 表格 |
|---|---|---|---|---|
| errors 域错误码全集 | `core/errors.py:63` `ERROR_CODES` | `SCREAMING_SNAKE` | 18 | errors.spec §2 全列 |
| transport 消息级错误码 | `core/transport.py:86-94` `ERR_*` | `snake_case` | 8 | **transport.spec 未列，errors.spec 未列** |

`transport.py:86` 的注释自称"语义与 errors 域 ErrorCode 对齐"，但两族**无一码重叠**（`invalid_payload` / `kind_prefix_violation` / `capability_not_declared` / `invalid_frame` / `unknown_message_type` / `unavailable` / `storage_failed` / `llm_call_failed` 均不在 `ERROR_CODES` 中）。

**事实 B —— 覆盖完全偏斜**
- 穷举 `PROTOCOL/behavior-suite/`：errors 域的 18 个错误码 **0 命中**；`"code"` 字段在 `cases/` 内 **0 命中**。
- 套件实际断言到的是 transport 族中的 3 个：`capability_not_declared`（12）、`kind_prefix_violation`（11/17）、`invalid_payload`（06）。
- 而 errors.spec.md §2 白纸黑字写着"**v1.0 错误码全集（落地时行为套件逐条锚定）**"——该协议义务未履行。
- 锚定实际散落在私有单测里：`tests_core/test_config.py` 7 处、`test_hooks.py` 3 处、`test_pipeline.py` 1 处。即：**义务被放在了错误的载体上**，而该载体又受 F-2 的纯净规则约束。

**影响**：新宿主实现按 behavior-suite 验收时，会通过全部 17 条用例，却完全无法证明其错误码语义与责任矩阵一致；协议-实现漂移在此域**不可审计**。

### F-4【中】冻结面"零升版"的真相：变更没有回流，而非没有变更

`PROTOCOL/VERSION` 停在 `v1.0.0`、PENDING"已并入记录"为空 —— 表面看是"冻结面从未变更"。逐条对拍后，实情是**发生了协议面变更但未回流登记**：

| 变更 | 应属 | 实际登记情况 |
|---|---|---|
| `core.extensions_root`（2026-09-08 新增 core 配置键） | config 域 §3"新增 core 配置键 = minor 演进" | P-1 仅在"涉及域"提了一句；`config.spec.md` §2 **至今未收录**该键 |
| `max_snapshot_bytes` / `max_message_bytes` / `max_messages_per_conversation` | 同上 | `config.spec.md` §2 未收录（仅 `CORE.md` §7 有）；`types.spec.md` §7 以"协议常量"形式覆盖 |
| **`HistoryStore.get_session_messages(before_id)` 游标** | 属 P-4 op 集 `get_session_messages` 的 **payload 变更** | **未登记 PENDING，任何 spec 未提及**；`CORE.md` §10 / `SPI` §7 亦未同步 |
| `manifest kind: host-component` / `slots` | P-1 扩展 | P-6 已登记（合规） |
| `host_components` config 段 | 新配置面 | P-5 已登记（合规） |
| `log_messages` op / `log_message_buffered` 双档 | P-4 op 集增补 | P-7 已登记（合规） |

**结论**：演进机制的**入口规范**（先写 PENDING）执行得不错，但**出口从未跑通**，且存在 1 处明确的漏登记（`before_id`）+ 1 处规格未回写（config 域 4 键）。所以"v1.0.0 零升版"不能解读为"契约稳定"，只能解读为"契约未随实现同步"。

### F-5【中】types T-8 三项资源上限只落实两项

`types.spec.md` §7 + 行为条款 T-8：「任一上限被突破 → 对应通道拒绝（`HOOK_INVALID_ACTION`），error 级日志」。

实现侧（`core/snapshot.py`）：

| 上限 | 实现 | 是否"拒绝" |
|---|---|---|
| `max_messages_per_conversation` | `_check_message_budget` L44-48 | 是（该 action 被跳过） |
| `max_message_bytes` | `_check_message_budget` L49-55 | 是（该 action 被跳过） |
| `max_snapshot_bytes` | `_check_snapshot_budget` L59-67 | **否** —— 仅 `logger.error`，超限快照照常 `return new_snapshot`（L139-145 注释自称"超限通道拒绝 + error 日志"，与代码行为不符） |

即第三项上限实际退化为"告警"，2 MiB 快照仍会推进并送 LLM。属 DoS 防护面的实打实缺口（严重度中：非功能路径，但契约明确要求拒绝）。

### F-6【中·正面结论】R-1「禁止裸 except 静默吞错」实际达标

**方法**：AST 扫描 `teage_liu2/core` + `teage_liu2/server` 全部 129 个 `except handler`，标出两类疑似：①handler 体仅 `pass`（绝对静默）；②体内既无日志调用也无 `raise`。初筛结果 **27 处疑似**。

**人工逐点复核后，真实违规 = 0**。27 处分布与性质：

| 性质 | 数量（约） | 说明 | 判定 |
|---|---|---|---|
| 回滚后 `raise`（rollback-then-reraise） | 8 | `hooks.setup_all`、`registry.rebuild`、`supervisor.launch_all/reload`、`stdio.open`、`extension_loader.load_python_extension` | 合规（异常未被吞，只是补齐清理） |
| 探测式建表（`try: SELECT ... except OperationalError: CREATE`） | 2 | `history._ensure_fts_table` 及其回填 | 合规（预期分支） |
| 清理期 best-effort（`close()` 里关 writer / kill / cancel） | 9 | `stdio.close`、`storage_stdio_proxy` 关闭路径 | 合规（带注释说明"尽力"） |
| 可选依赖 / 环境降级（`ImportError`、`queue.Empty`、`StopAsyncIteration`、`RuntimeError`（loop 已关闭） | 6 | `llm.py`、`storage_writer.py` | 合规（属降级优先约定） |
| 返回值即上报（非静默，只是不写日志） | 2 | `routes.py` 历史分页返回 500 JSONResponse、`snapshot._estimate_bytes` 返回 0 | 合规 |
| **建议补日志（唯一 2 处）** | 2 | `core/llm.py:914`（`await stream.close()` 失败静默）、`server/routes.py:224`（health 指标降级静默，有注释）；另 `stdio.close` 内 3 处 `except Exception: pass` 同属"零日志" | 建议 debug 级补日志 |

**审计方法论结论**：这类"疑似"若不人工复核，很容易被写成"27 处静默吞错"的假缺陷。正确姿势是**机器筛 + 读上下文判**。本次 F-6 因此记为正面结论。

### F-7【低中】幽灵外键约束（两后端一致地"声明不执行"）

- `core/history.py:128` 与 `storage-rust/src/history.rs:31` 均声明 `FOREIGN KEY (session_id) REFERENCES sessions(id)`。
- 但两处都**没有** `PRAGMA foreign_keys=ON`（core 只设了 `PRAGMA journal_mode=WAL`；Rust 侧 grep `foreign_keys` 无命中）。SQLite 默认外键**关闭** → 约束实际不生效。
- 影响：孤儿消息可写入（不报错，故无崩溃风险，与 P-4 条款③"批量失败整批回滚"场景无冲突）；但 schema 向接入者传递了错误的完整性承诺。
- 处置选择需**两后端同步**：要么同时启用 `PRAGMA foreign_keys=ON`（须验证批量原子性与迁移路径），要么删掉 DDL 中的 FK 声明。任一动作都会改变 P-4 两后端的语义等价前提，须纳入 P-4 评审。
