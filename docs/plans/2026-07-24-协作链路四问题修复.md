# 协作链路四问题修复 Implementation Plan

> **For agentic workers:** Use the java-dev-skills workflow to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修复多 agent 协作链路核查发现的 4 个问题，恢复 user 广播请求响应能力、消除 status 接口 500 错误、统一 director_status 初始值。

**Architecture:** 按问题严重度 P0→P1 分批修复。问题三（chat 接口契约不匹配）通过扩展 `Orchestrator.chat()` 增加 `extra_context` 参数，将协作上下文作为独立 system 消息注入 enhanced_history（缓存失效区），不污染 ContextManager 的缓存命中区。问题二（read_json 裸调用）通过 try/except + 重试机制加固。问题一（director_status 残值）通过统一 RecoveryCoordinator 的默认值修复。

```python
# teage_liu/multiagent/worker_adapter.py 第 601-625 行替换
    async def _trigger_urgent_llm(self, prompt: str, context_msg: dict) -> None:
        """紧急插队：立即触发 LLM 调用（不搭便车，但顺便清空普通队列）。

        使用独立 collab session（f"collab_{agent_id}"）与用户主对话隔离。
        协作上下文通过 extra_context 注入缓存失效区，不污染缓存命中区。
        """
        if self._orchestrator is None:
            logger.warning("Worker %s 紧急 LLM 调用跳过：orchestrator 未注入", self._agent_id)
            return

        collab_session_id = f"collab_{self._agent_id}"
        extra_context = self._build_urgent_system_prompt(context_msg)
        # 同时把普通队列消息也注入（顺便清空）
        extra_context = self._inject_normal_queue_to_context(extra_context)

        try:
            response = await self._orchestrator.chat(
                collab_session_id, prompt, extra_context=extra_context
            )
        except Exception as e:
            logger.exception("Worker %s 紧急 LLM 调用失败: %s", self._agent_id, e)
            # 异常时写 error 消息告知用户，不静默丢弃
            from teage_liu.multiagent.blackboard import append_collab_message
            await append_collab_message(self._bb_root, {
                "from": self._agent_id,
                "type": "response",
                "reply_to": context_msg.get("seq"),
                "content": f"[协作响应失败] {type(e).__name__}: {e}",
                "accept": False,
                "error": True,
            })
            return
        self._last_a2a_time = time.time()

        # 如果是 request，写 response
        if context_msg.get("type") == "request":
            from teage_liu.multiagent.blackboard import append_collab_message
            await append_collab_message(self._bb_root, {
                "from": self._agent_id,
                "type": "response",
                "reply_to": context_msg.get("seq"),
                "content": str(response),
                "accept": True,
            })
```

```python
# teage_liu/multiagent/blackboard.py 第 132-135 行替换
def read_json(path: Path, retries: int = 3, retry_delay: float = 0.05) -> dict:
    """读取 JSON 文件（带重试 + 异常保护）。

    并发写入（atomic_write 的 os.replace）的极小窗口内，同步读可能读到
    空内容或中间态。retries + retry_delay 覆盖该竞态窗口。

    Args:
        path: JSON 文件路径
        retries: 重试次数（默认 3）
        retry_delay: 重试间隔秒数（默认 50ms）

    Returns:
        解析后的 dict；文件不存在/损坏/空时返回空 dict（fail-open）
    """
    import logging
    _logger = logging.getLogger(__name__)

    if not path.exists():
        return {}

    for attempt in range(retries):
        try:
            with open(path, "r", encoding="utf-8") as f:
                content = f.read()
            if not content.strip():
                # 空内容（可能读到 rename 中间态），重试
                if attempt < retries - 1:
                    import time as _time
                    _time.sleep(retry_delay)
                    continue
                return {}
            return json.loads(content)
        except json.JSONDecodeError:
            if attempt < retries - 1:
                import time as _time
                _time.sleep(retry_delay)
                continue
            _logger.warning("read_json 解析失败（已重试 %d 次）: %s", retries, path)
            return {}
        except OSError as e:
            _logger.warning("read_json 读取失败: %s, error=%s", path, e)
            return {}
    return {}
```

```python
# teage_liu/multiagent/collaboration_routes.py 第 143-154 行替换
    @router.post("/broadcast")
    async def broadcast(req: BroadcastRequest):
        """用户发布广播（from=user, type=request, to=*）

        自动生成 message_id 实现去重，防止前端重复提交写入多条。
        """
        import hashlib
        bb_root = _get_bb_root()
        # message_id 基于内容 hash，相同内容短时间内重复提交会被去重
        content_hash = hashlib.md5(req.content.encode("utf-8")).hexdigest()[:16]
        message_id = f"user_broadcast_{content_hash}"
        message = {
            "from": "user",
            "type": "request",
            "content": req.content,
            "to": "*",
            "message_id": message_id,
        }
        seq, deduplicated = await append_collab_message(bb_root, message)
        return {"ok": True, "seq": seq, "deduplicated": deduplicated}
```

### 4. 其他合理改动说明

**为什么 Task 2 增加异常时写 error 消息？**
原代码 `_trigger_urgent_llm` 异常时 `logger.exception` + `return`，user 请求被静默丢弃，用户完全无感知。修复后写一条 `type: response, error: True` 的消息，让用户知道"agent 收到了请求但处理失败"，而非石沉大海。这符合用户偏好"失败原因应清晰返回给 LLM 以便其思考后执行"。

**为什么 Task 5 加 broadcast 去重？**
collaboration.md 实际数据中 seq=5/6 是相同内容 "ciallo~"（timestamp 差 10ms），是前端重复提交导致。虽然修复 Task 3 后 Worker 能正确响应，但重复消息仍会触发两次 LLM 调用浪费成本。message_id 去重复用现有 CollabWriter 机制，零侵入。

**为什么不修 lifespan.py 调用 init_blackboard？**
lifespan.py 当前手动 mkdir + 调用 RecoveryCoordinator 的流程已运行稳定，贸然改为调用 init_blackboard 可能引入新的副作用（如覆盖已有 status.json）。Task 4 只改 recovery.py 的默认值，最小改动且与 Blackboard.init_blackboard 语义对齐。
