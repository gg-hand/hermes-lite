# 统一扩展目录树设计（VSCode 式扩展管理）

> 日期：2026-09-08　状态：设计已获用户批准（对话定案），待实现
> 关联：`docs/plans/2026-08-20-终极解耦架构-设计.md`（v1.14 协议族）、`teage_liu2/docs/CORE.md`（主干契约）

## 0. 背景与问题

当前 teage_liu2 扩展机制存在结构性矛盾：**交互契约已是运行期的（Snapshot+Action、PROTOCOL 9 域），而扩展发现/装载仍是"编译期"的**。

| 维度 | 现状 | 问题 |
|------|------|------|
| 同语言扩展位置 | `teage_liu2/branches/`（audit.py、guardrails.py） | 在源码包内，加扩展 = 改源码 |
| 装载机制 | 名字 → 硬编码工厂映射（`server/app.py` import + register_factory） | registry 无动态加载能力，"放进去"不等于"被发现" |
| 异语言扩展位置 | `command: [...]` 任意路径 | 无统一目录约定，散落无管理 |
| 扩展元信息 | 无 manifest，capabilities 写死在代码 | 无法脱离代码了解身份/授权面 |
| 打包 | pyproject 只含 core/server | branches 事实游离 |

## 1. 定案决策（用户逐条确认）

| # | 决策点 | 定案 |
|---|--------|------|
| D1 | 目录树位置 | **完全仓库外独立目录**，路径由 config 指定（默认 `data2/extensions/`，已 gitignore） |
| D2 | 管理形态 | **VSCode 式**：目录为安装单位，manifest 为唯一事实源；简单扩展最小 `manifest.yaml + main.py` 两文件 |
| D3 | 配置分工 | **manifest 定安装态**（身份/装载方式/capabilities 声明面）；**config.yaml 定运行态**（`core.branches.<name>` 的 enabled + 配置覆盖）。集中控制面在 config.yaml，热重载与坏配置启动失败语义不变 |
| D4 | guardrails | **一并外迁**，`teage_liu2/branches/` 整个消亡，彻底统一（用户接受信任边界弱化的代价） |
| D5 | 同语言装载 | **进程内动态加载**（importlib）；强隔离需求走 stdio 形态；预留未来 `isolation: process` 演进（本次不实现） |

## 2. 目标架构

```
改造前:  server/app.py 硬编码 import branches/* → register_factory → registry
改造后:  config(extensions_root) → core 扫描目录读 manifest → 按类型装载 → registry
```

- **新增 `core/extension_loader.py`**：扫描 extensions_root → 解析/校验 manifest.yaml → 产出 `ExtensionSpec`。
  - `language: python` → importlib 动态装载（进程内）
  - `language: other` → 交 Supervisor 现成 stdio 通道（launcher 路径不变）
- **registry**：目录发现作为**生产唯一装载通道**注入；`register_factory` 通道**保留但重新定位**（见 §2.1），改造后生产路径零调用
- **`teage_liu2/branches/` 删除**；`server/app.py` 不再 import 任何枝干 —— **依赖铁律的"装配点例外"彻底消失**，外壳变纯 core 依赖
- pyproject 无需改动（branches 本就不在 packages 清单）
- manifest 发现规范写入 SPI 文档，**不进 PROTOCOL v1.0 冻结面**（不动协议版本；未来成熟经 RFC 升格）

### 2.1 `register_factory` 保留定位（强制标注，不得遗漏）

**定案（2026-09-08 用户确认）**：通道保留、生产路径零调用；其定位 = **测试/行为套件/编程式嵌入的内存注入通道，生产扩展一律走目录发现**。"外壳不知道任何枝干名"由代码事实保证（无 import、无注册调用），不靠删 API。

保留理由：①`PROTOCOL/behavior-suite/runner.py` 的 17 个黄金用例靠它注入内存 `ScriptedBranch` ②`tests_core/test_registry.py` 12 处单测注入 ③编程式嵌入 `create_app(config=...)` 前程序化注册 ④未来真内置扩展的通道。

**标注点清单（实现时逐处落实，验收时逐处核对）**：

| # | 位置 | 标注内容 |
|---|------|----------|
| 1 | `core/registry.py` `register_factory` docstring | 完整定位声明：非生产装载通道；生产扩展必须走目录发现（extension_loader）；当前合法使用方 = 行为套件/单测/编程式嵌入 |
| 2 | `core/extension_loader.py` 模块 docstring | 声明"生产扩展唯一装载通道"身份 |
| 3 | `server/app.py` 装配段注释 | 明示此处不再注册任何工厂、扩展全部来自 extensions_root 目录发现 |

| 6 | `teage_liu2/docs/INTERFACES.md` 接入指引 | "新增扩展 = 建目录 + manifest"，不引导用 register_factory |

## 3. 目录树与 manifest 规范

```
<extensions_root>/          ← 默认 data2/extensions/（仓库外、gitignore），config 可指任意路径
└── audit/
    ├── manifest.yaml       ← 唯一事实源
    ├── main.py             ← 简单扩展就这两个文件
    └── (resources/ 子模块/数据文件，自由)
```

`manifest.yaml` 字段（启动/重载时严格校验，坏 manifest = 该扩展装配失败）：

```yaml
name: audit                # 必填，^[a-z0-9_]+$，必须等于目录名
version: 0.1.0             # 必填，扩展自身版本（与宿主/协议版本无关）
language: python           # 必填：python（进程内）| other（必须配 transport）
entry: main.py             # language=python 必填，相对 manifest 目录
# language=other 时必填：
#   transport: stdio
#   command: [...]          # 相对路径一律相对 manifest 所在目录解析
#   protocol_version: v1.0.0（可选，缺省同现状）
capabilities: [observe]    # 必填，授权声明面，值域 = core/hooks.py 现有常量：
                           # observe | tool_executor | llm | self_hosted_storage
description: 对话审计观测   # 可选
# requirements:            # 可选，同语言扩展第三方依赖声明（仅作文档，不自动安装，见 §8）
```

校验规则：
- 未知键拒绝；name 与目录名不一致拒绝；name 不匹配 `^[a-z0-9_]+$` 拒绝
- `language: python` 无 entry 拒绝；`language: other` 无 transport/command 拒绝
- capabilities 值须在协议授权面枚举内（`observe | tool_executor | llm | self_hosted_storage`，与 `core/hooks.py` CAP_* 常量同源，新增 capability 须同步扩枚举）
- 同名扩展冲突（目录名重复不可能；config 声明未知名 = 启动失败）

## 4. 配置分工

```yaml
core:
  extensions_root: data2/extensions   # 新增配置项，走 core_config_from 严格校验
  branches:
    audit:                # 运行态：enabled + 配置覆盖（传给扩展 setup）
      enabled: true
      record_steps: true
    guardrails:
      enabled: true
```

- **安全默认**：目录里装了但 config 未声明的扩展 = **不启用**（安装 ≠ 激活），启动日志提示已装未启用的扩展名
- config 声明但目录/manifest 不存在 = **启动失败**（防 typo，沿用现语义）
- 运行配置合并顺序：manifest 不携带配置 → config `core.branches.<name>` 整段作为该扩展配置传入 `setup(cfg, host)`（现状一致）

## 5. 同语言动态装载细节

- `importlib.util.spec_from_file_location` 按路径加载 `entry`；模块名 `ext_<name>_<manifest内容hash>` —— 热重载时 hash 变化即全新模块对象，不留旧缓存污染
- `main.py` 约定导出工厂函数：`def create_branch(config: dict) -> Branch`
- 扩展 import 宿主接口：`from teage_liu2.core.hooks import Branch`（及 actions/types 等纯数据契约）——依赖方向"扩展 → core 接口"合法且是唯一被允许的宿主依赖；禁止扩展 import `teage_liu2.core` 内部实现模块与 `teage_liu2.server`
- 扩展子模块/资源经 `__file__` 相对定位；**不污染 `sys.path`**、不写宿主全局状态
- 信任边界如实文档化：进程内 = 信任执行；既有兜底 = `hook_timeout`（钩子链超时）+ 钩子异常隔离 + L3 旁路投递超时隔离（5s）；需要强隔离的扩展改用 stdio 形态

## 6. 不变量（改造中不得破坏）

- 主干不知道任何枝干名（core 无 import branches，改造后 server 亦然）
- 枝干间只经 `BranchContext.extra` 通信
- 11 钩子 Snapshot+Action 签名、capabilities 授权面、kind 前缀隔离、资源上限——全部原样
- 热重载语义：`/reload` 重扫目录 → 重读 manifest → rebuild 原子替换 + 回滚保旧链；L3 订阅重接线 + 退订闭环照旧
- E1 启动原子性：任一扩展 manifest/装载/setup 失败 → 逆序回滚 = 启动失败

## 7. 迁移步骤（概要，实现计划再细化）

1. core：`extension_loader.py`（manifest 解析校验 + ExtensionSpec + importlib 装载器）
2. core：registry 目录发现通道接线 + `core.extensions_root` 配置项（core_config_from 扩展）
3. server：app.py 去 branches import，接 loader（装配点例外消失）
4. `audit` 外迁为首个样板（`data2/extensions/audit/{manifest.yaml, main.py}`）
5. `guardrails` 外迁（tool_executor capability 进程内装载不受影响）
6. 删除 `teage_liu2/branches/`
7. 既有 tests_branches 用例适配新装载路径（改造现有测试文件，非新增）；**同步落实 §2.1 标注点清单 8 处**
8. 文档同步：SPI（扩展发现与 manifest 规范章节 + register_factory 定位专段）、CORE.md、INTERFACES.md、`teage_liu2/docs/plans/开发日志.md`、根 CHANGELOG
9. 验证门槛：行为套件 runner 17/17 + tests 全绿 + d:/tmp 端到端（目录发现 → 装载 → 钩子 → 落盘 → 热重载 → L3 退订闭环，临时脚本用完即删）；**验收含 §2.1 标注点清单逐项核对**

## 8. 风险与取舍

- **信任边界弱化**（D4 用户定案）：guardrails 外迁后安全拦截成为可删改的目录文件——个人自托管单用户场景可接受；文档明示"安全策略的完整性 = 扩展目录完整性"
- **进程内崩溃面**：扩展死循环/崩溃与宿主同进程——hook_timeout + 异常隔离兜底；强隔离走 stdio
- **manifest 不入 PROTOCOL v1.0**：发现规范属宿主实现细节，避免动冻结协议；未来若做扩展分发/市场，经 evolution 域 RFC 升格
- **第三方依赖**：同语言扩展的 pip 依赖声明在 manifest（`requirements` 可选字段，仅作文档），由用户手动装入宿主 venv——不做自动安装（YAGNI）
